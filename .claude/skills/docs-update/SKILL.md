# docs を方針どおりに更新する

方針の正本は `docs/README.md` である。この手順は、それを作業の区切りで実行する順番を決める。最初に `docs/README.md` を読む（同じ版を読んであれば読み直さない）。

## 1. 反映するものを集める

- `git status` と `git diff`（コミット済みなら前回 docs を直したコミットからの `git log -p`）で、変えたコードと文書を挙げる。
- 会話の中の出来事を挙げる：見つけた不具合、作者の指摘、決めたこと、捨てた案、測った数値、確かめた端末の振る舞い。

## 2. 出来事ごとに、構造と一般化を先に決める

出来事ごとに、作業メモに次の4行を書いてから文書を触る。書けない行があれば、文書を書く前に調べ直す。

```text
構造：何が起きたかではなく、どの仕組みから起きたか
一般化：同じ構造の別の失敗も防ぐ形。置き場は CLAUDE.md の規則／docs/設計/ の原則か差し込み口／試験 のどれか
今の姿：docs/設計/・手順/・資料/ のどの節を、どう書き換えるか
判断：docs/判断/ に残す題（今の形を縛る判断か、同じ案を試し直す無駄を防ぐ判断のときだけ）
```

症状に合わせた例外の判定やフラグで直した場合は、一般化ができていない。`CLAUDE.md`「設計の幹を守る」に戻る。

## 3. 今の姿の文書を書き換える

- 足す前に、同じ事実が既にどこに書かれているかを `git grep` で探し、その1か所を書き換える。2か所目を作らない。
- 現在形で今の姿を書く。経緯・日付・作者の指示の引用・試したことは書かない（`docs/README.md`「今の姿を書く文書の書き方」）。
- 節名を変えたら、`git grep` でコードのコメント・`CLAUDE.md`・`docs/` からの参照を直す。
- 1つの事実の置き場に迷ったら `docs/README.md`「1つの事実は1か所」に従う。

## 4. 判断の記録を足す

- `docs/判断/YYYY-MM-DD_題.md` に、`docs/README.md`「判断の記録の書き方」の書式で書く。「問題」には構造を、「再発を防ぐもの」には2で決めた一般化とその置き場を書く。
- 覆した判断があれば、古いファイルの「状態」を「置き換え（→ 新しいファイルへのリンク）」に変える。本文は直さない。

## 5. 作業中の文書を畳む

`docs/作業中/` の文書のうち作業が終わったものは、今の姿を `docs/設計/` に、判断を `docs/判断/` に、残りを `docs/バックログ.md` に移して消す。

## 6. 現在地とバックログを書き換える

- `docs/現在地.md` は100行以内で、状態・次の作業・未解決・固定した版だけを置く。前の版に書き足さず、全体を書き換える。完了した作業の一覧は作らない（Gitの履歴とリリースのノートが正本）。
- `docs/バックログ.md` の済んだ項目を消し、新しい項目を1〜3行で足す。

## 7. 検査を通す

`pwsh -NoProfile -File tools/check-docs.ps1` を回し、誤りを直す。注意（今の姿の文書の日付、作業中の残り）も、経緯が混ざった合図なので見直す。

## 8. 冷読させる

節を足した、組み替えた、新しい文書を作った、のどれかに当たる文書は、`docs-reader` エージェントに読ませる。渡すのは文書のパスだけにし、書いた意図は渡さない。返ってきた「止まった箇所」「方針に反する記述」「コードと合わない事実」を直す。直した後、幹が変わったなら同じエージェントに読み直させる。

## 9. 報告する

作者への報告には、出来事ごとに「構造」と「一般化した先」を1行ずつ書き、書き換えた文書と足した判断の記録を挙げる。工程を実施した記録は書かない。
