# 画面翻訳を工程と場面のプリセットにする

- 状態：有効
- 問題：行のまとめ方が読む部品（`core-ocr`）の中に1つ（吹き出し向け）だけ埋め込まれ、カメラ翻訳の文章・表のまとめ方は別の場所に別の型であった。枠の広げ方は単位の種類も隣との境も知らず、メニューの並びで広げると隣に重なるのを「ほかの文字にかかるなら広げない」という例外の判定で抑えていた。ゲームのUI・チャット・漫画で合うまとめ方が違うのに、選べなかった。
- 決めたこと：作者と合意した方針で、画面翻訳を工程（撮る → 読む → まとめる → 選ぶ → 枠を決める → 訳す → 流し込む）の並びとして固定し、差し替えるのはまとめ方と枠の決め方だけにする。まとめ方3つ（吹き出し・文章・メニュー）と占めてよい範囲は中核（`pipeline.layout`）に置き、カメラ翻訳も同じ部品を使う。訳の単位に種類と占めてよい範囲を持たせ、枠はそれだけを見て広げ、余白を足した後も範囲で切る。場面のプリセット（漫画・チャット・ゲーム）は工程の中身の組に名前を付けたデータにし、メニューで選ぶ。1回の翻訳のデータは、変わらない前提（`ScreenFrame`）と、工程ごとに1度だけ置く結果に分ける。今までの設定（吹き出し）でのまとまりは変えない。広げた枠は、ほかの文字にかかるとき広げないのでなく範囲で切る。
- 理由：まとめ方と枠の広げ方を独立に選べるようにしても、範囲で切れば組み合わせを禁止する規則が要らない。まとめ方は判断なので、Android に依存しない中核に置くと単体テストで約束（どの行も1つの単位に入る、範囲は原文を含み重ならない）を確かめられる。プリセットに処理の分岐を書かないので、アプリごとに場面を自動で切り替える部品も同じ組を当てるだけで足せる。
- 捨てた案：認識器やまとめ方を登録するプラグインのような汎用の仕組み（先回りして作らない）。撮り方・判定器もインターフェースにする（実装が1つで、値の違いで足りる）。組み合わせごとに禁止の規則を持つ（範囲で切れば要らない）。
- 再発を防ぐもの：差し替えはまとめ方と枠の決め方の差し込み口だけで行い、工程の並びは状態遷移に固定する（`docs/設計/画面翻訳.md`「工程とデータ」「将来の機能の差し込み口」）。描く枠は占めてよい範囲を出ない（`Rooms.drawn`、`RoomsTest`）。まとめ方は位置・縦書き・読む順を1か所で決め、どの行も1つの単位に入る（`TextLayout.unitOf`、`GroupersTest`）。場面は処理の分岐を持たないデータ（`ScreenPreset`、`ScreenPresetTest`）。
