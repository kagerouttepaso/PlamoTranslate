# 文書を役割で分け検査を仕組みにする

- 状態：有効
- 問題：`docs/` が作業のたびに書き足され、今の姿と経緯が混ざり、同じ主題が2か所に分かれていた（画面翻訳が、旧番号の05「画面翻訳」と13「画面翻訳の構成」の2本）。現在地の文書は日付ごとの段落が積もり、約1万8千字になっていた。こうなった構造は次の5つである。
  1. 作業の単位で文書を作り（作り替えの計画、リファクタリングの候補、機能テストの記録）、作業が終わっても主題の文書へ畳まなかった。
  2. 更新の操作が「書き足す」しかなかった。`CLAUDE.md` の規則自体が「完了したことを足す」「要約を現在地に、詳細を設計書に」と、追記と重複を求めていた。
  3. 書き手が自分の作業の経過（作者の指示の引用、試したこと）を書き、次の読者が要るものから書いていなかった。
  4. 文書の正しさと価値を確かめる工程が無く、もう無い文書への参照や実在しないクラス名が残った。量の多さが丁寧さに見えた。
  5. 番号だけの平らな置き場では、文書の役割が見えず、新しい文書の行き先が決まらなかった。
- 決めたこと：
  - 文書を役割で分け、置き場で役割を見せる：今の姿（`設計/`・`手順/`・`資料/`。書き換える）、作業の状態（`現在地.md`・`バックログ.md`。書き換える）、経緯（`判断/`。1件1ファイルで足すだけ）、作業の単位の文書（`作業中/`。終わったら畳んで消す）。番号はやめる。
  - 出来事は、構造の特定 → 一般化（規則・設計・試験）→ 今の姿の書き換え → 判断の記録1件、の順で文書に入れる。判断の記録の書式に「問題（構造）」と「再発を防ぐもの」を入れる。
  - 1つの事実は1か所。完了した作業の一覧は Git の履歴とリリースのノートを正本にし、`docs/` に置かない。
  - 規則を仕組みで支える：`tools/check-docs.ps1`（参照先の文書と節、置き場、現在地の長さ、判断の記録の書式、今の姿の文書への日付の混入、作業中の残り）を、コミットの前と AI が手を止める前に回す。区切りの手順は `docs-update` スキル、冷読は `docs-reader` エージェントに置く。
- 理由：役割が決まっていないと、区切りでできる操作が書き足すことしかなく、量が増えるほど今の事実が埋もれる。規則を書くだけでは次の作業者が読み飛ばすので、機械で判定できるものは止め、判断が要るものは手順と別の担当の通読にする。初めて回した検査で、作り替える前から壊れていたコードからの参照（もう無い文書や節を指すもの）が見つかった。
- 捨てた案：判断の記録を1つのファイルに日付順で書き足す。足すだけの文書がまた肥大し、覆った判断の扱いも本文の書き換えになる。
- 再発を防ぐもの：`docs/README.md`（方針と「この方針が防ぐもの」の表）、`CLAUDE.md`「文書は役割を守って更新する」「規則を支える仕組み」、`tools/check-docs.ps1`、`.githooks/pre-commit`、`.claude/settings.json` の Stop・SessionStart フック、`.claude/skills/docs-update`、`.claude/agents/docs-reader.md`。
