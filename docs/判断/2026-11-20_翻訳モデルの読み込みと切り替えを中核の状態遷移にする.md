# 翻訳モデルの読み込みと切り替えを中核の状態遷移にする

- 状態：有効
- 問題：翻訳モデルの読み込み・切り替え・読み直しの判断が、`app` の `object EngineHolder` に、Android の処理（OpenCL のキャッシュの場所、GPU を使うかの判定）と一緒に入っていた。判断を試験できなかった。使える状態（`ModelState.Ready`）がエンジンそのものを持っていたので、状態を購読するどこからでもエンジンを使えた。そのため、翻訳の契約を迂回する所が3か所できていた。カメラ翻訳がエンジンの同一性でモデルの切り替えを見分ける所、画面翻訳がモデル名のために読み込みを別に待つ所、評価がストリームを直接作る所である。試験が無かったので、読み込み中にモデルを選ぶと、設定には選んだモデルが残るのに、読み込まれるのは前のモデル、という食い違いにも気づいていなかった。
- 決めたこと：
  - 判断は中核の状態遷移 `ModelHost` に移し、読み込みの中身は `EngineLoader` の実装（`app` の `LlamaEngineLoader`）に置く。`EngineHolder` は、設定を保存して命令を渡す口にする。
  - 使える状態はエンジンを持たない。代わりに、世代の番号（読み込むたびに増える）・同時に訳す数・GPU で動いているかを持つ。
  - エンジンを受け取る口は `awaitEngine` の1つにする。使ってよい場所は、設計の点検（`tools/check-design.ps1`）で止める。
  - カメラ翻訳は、世代の番号でストリームを開き直すかを `CameraSession` が決める。画面翻訳のモデル名は、ストリームの結果の数（`TranslationStream.Stats.model`）から取る。
- 理由：判断を中核に置けば、読み込みの遅れ・失敗・選び直しを偽のローダーで試験できる（`docs/設計/アーキテクチャ.md`「設計の原則」）。状態からエンジンを外すと、エンジンを受け取る所が1つの口に集まり、迂回を機械で止められる。世代の番号を状態に持たせると、カメラ翻訳はエンジンの同一性を見ずに、中核の中だけで開き直すかを決められる。
- 変わった振る舞い：
  - 読み込み中に選び直した・読み直しを頼まれたら、今の読み込みが終わってから、そのときに選ばれているモデルを読み直す（作者の決定）。設定と読み込んだモデルが食い違わない。
  - 読み込み中に同時に訳す数を変えたら、読み込みの後に効く。以前は、次に読み込むまで設定と食い違った。
  - 比べるのも読むのも「選ばれているモデル」の1つにした。選んだモデルのファイルが無いと0.8Bを読む（以前は、ファイルが無いことを出した）。画面ではファイルの無いモデルを選べないので、普段は通らない。
  - 読み込みのどこで例外が出ても、失敗の状態で読み込みを終える。前のエンジンを閉じられなくても、読み込みへ進む。
- 捨てた案：
  - `EngineHolder` を `object` のまま、試験のためにローダーだけ差し替えられるようにする。状態がエンジンを持つ限り、迂回は残る。
  - 状態の型を `app` に残し、中核には判断だけを置く。カメラ翻訳の判断（世代で開き直す）が、状態の型を知らずに書けない。
- 残したこと：
  - 会話翻訳と、デバッグ版の画面翻訳（`DEBUG_CONFIG`）は、エンジンを受け取ってスレッド数を変えている。`ModelHost` の知らないところの変更なので、読み直した後のエンジンには効かない。バックログに置いた。
- 再発を防ぐもの：
  - 設計：`docs/設計/翻訳コア.md`「読み込み」「ストリームを通さない呼び出し」。
  - 試験：`ModelHostTest`、`CameraSessionTest`。
  - 点検：`tools/check-design.ps1`（エンジンを受け取ってよい場所）。
