# 変更のたびに構造を点検し小さく直す

- 状態：有効
- 問題：画面翻訳を、モジュールと翻訳の契約から作り替える必要が出た（`2026-11-12` の作り替え）。作り替えの直前、画面翻訳の状態は `ScreenTranslateService` の約15個の変数に散り、取り消しは14か所に分かれ、開始の判定と有効性の判定が結合していた。こうなった構造は次の4つである。
  1. 「一番簡単に動く方法で通し、不満が出た箇所だけ作り込む」という進め方に、設計の幹という歯止めが無かった。機能（自動で訳す、動く画面、訳の控え、同時に訳す、透けない枠）を、症状が出た場所にそれぞれ足した。
  2. 不具合を、仕組みを確かめずに症状に合わせた判定やしきい値で抑えた。端末に何の合図が届くか（戻る操作）も確かめず、画素の変化から推測していた。
  3. 変更の単位が大きく（1つのコミットに複数の機能）、変更ごとに構造を見る工程が無かった。確かめるのは作者が実機で触ることだけだった。
  4. 構造の崩れを見つける合図が無かった。リファクタリングの候補の一覧（2026-11-09）はあったが、手を付けるきっかけが無く、画面翻訳のサービスの肥大は載っていなかった。
- 決めたこと：大きな作り替えを要らなくするため、構造の崩れを、見つけたその変更の中で小さく直す。そのための流れと点検を、規則・手順・機械の検査・レビューの担当として置く。
  - 規則：`CLAUDE.md`「変更の進め方」（要望を望む状態として受ける、不具合は仕組みまで調べる、差し込み口が無ければ先に構造を直す）、「1つの目的を1つのコミットにする」、「一番簡単な方法は差し込み口の中で選ぶ」。
  - 手順：`change-flow` スキル。直す前に構造を点検する表（例外の判定・状態遷移の外の制御・Android 側の判断・契約の迂回・差し込み口の不在・大きいファイル）。リリースの前に前の版からの差分を点検する。
  - 機械の検査：`tools/check-design.ps1`。中核の依存、翻訳の契約を通らない呼び出し、JNIの使い場所を誤りとして止め、大きいファイルと何度も変わるファイルを合図として出す。コミットの前（`.githooks/pre-commit`）と、AIが手を止める前（Stop フック）に回る。
  - レビュー：`design-reviewer` エージェント。書いた意図を渡さず、差分を設計の幹に照らして読ませる。
- 理由：崩れは1つ1つの局所修正では見えず、積もってから見つかると直す範囲が大きい。人の注意に頼る規則だけでは、作業の区切りに読み飛ばされる。機械で判定できる約束は止め、判定に判断が要るものは手順とレビューの担当に分けると、毎回の変更で点検が回る。
- 捨てた案：
  - 定期的に大きく作り直す前提で、リファクタリングの候補の一覧を育てる。きっかけの無い一覧は、今回のように肥大を載せないまま残った。
  - アーキテクチャのテストのライブラリ（Konsist など）を入れる。大きな依存の追加になり、今の約束は `git grep` で足りる。約束が増えて足りなくなったら考える。
- 再発を防ぐもの：`CLAUDE.md`「変更の進め方」「規則を支える仕組み」、`.claude/skills/change-flow`、`.claude/agents/design-reviewer.md`、`tools/check-design.ps1`、`.githooks/pre-commit`、`.claude/settings.json` の Stop フック。
