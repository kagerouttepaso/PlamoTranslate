# AndroidのQwen3-ASRをGGUFに切り替え実行先を試走で選ぶ

- 状態：有効
- 問題：Android では PC と異なる Qwen3-ASR 認識器を使っており、途中の書き起こしの中断と確定文の言語判定を共用できなかった。
- 決めたこと：会話翻訳とテキスト翻訳の音声入力で PC と同じ GGUF Q8_0 の認識器を使う。CPU のスレッド数と OpenCL の採否は端末上の試走で決める。順7では旧 ONNX 認識器のコードと端末上の旧モデルを残す。
- 理由：NX809J では、CPU 専用でも OpenCL を許可しても CPU の 6/6/6 が選ばれた。2回目は保存した選択を使って3秒以内で音声認識の準備が終わった。OpenCL の準備中にプロセスが異常終了した場合も、次の起動で書き起こしを CPU に戻せた。
- 再発を防ぐもの：中核の `TranscriptionTuner` が既知音声で本文・言語と時間を比較する。実際の会話では正解の各発話と確定カードを順に照合し、長い発話の分割と発話全体の欠落を区別する。

## 実機での確認

NX809J（REDMAGIC 11 Pro、Adreno 840）の debug 版で各条件を1回ずつ確認した。スレッド数はエンコーダー／一括評価／生成の順。試走欄は採用した候補が既知の英語音声を書き起こした3回の中央値。準備時間は会話画面で音声認識全体が使えるまでを計測した。

| 書き起こしの条件 | 選ばれた実行先 | 試走 | 初回準備 | 2回目の準備 |
| --- | --- | ---: | ---: | ---: |
| CPU 専用・自動選択 | CPU 6/6/6 | 239 ms | 18.626秒 | 2.676秒 |
| OpenCL 許可・自動選択 | CPU 6/6/6 | 240 ms | 26.995秒 | 2.637秒 |
| OpenCL 準備中に SIGABRT で終了した次の起動 | CPU 6/6/6 | 247 ms | 21.569秒 | — |

自動選択の CPU 候補は 4/4/4、6/6/6、8/8/4 で、各段を使用可能な CPU 数で制限する。OpenCL 許可時のログでは、GPU の準備開始前に CPU で12回（3候補それぞれ、ならし1回と計測3回）書き起こし、最後に「GPU は CPU より十分には速くありません」と記録した。候補別のスレッド数と中央値をすべて出すログはない。

FLEURS の日韓8発話を82秒の WAV にして会話翻訳に実時間で入力した（OpenCL 許可、2回目の準備後）。第1発話が2枚に分かれ、第3発話の日本語と第8発話の韓国語に対応するカードはなく、6発話から7枚が確定した。この2区間の入力音量はそれぞれ −59.4、−53.3 dBFS（RMS）だった。音量と欠落の因果関係はこの1回では判定できない。

7枚の確定訳はカード順に届いた。区切りから原文確定までは中央値202 ms・最大1,460 ms、確定訳までは中央値533 ms・最大2,494 ms。テキスト翻訳では、端末のマイクで英語音声を取り込み、原文欄に「The door is open.」が一致した。
