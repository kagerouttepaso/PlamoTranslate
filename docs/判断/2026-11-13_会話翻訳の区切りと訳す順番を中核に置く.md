# 会話翻訳の区切りと訳す順番を中核に置く

- 状態：有効
- 問題：会話翻訳だけが、画面翻訳・カメラ翻訳の設計の幹（判断は中核、制御は状態遷移の1か所）から外れていた。音声の区切り方（文とカードの2段、言語の見張り、区切る位置）が `core-asr` の `SenseVoiceAsr.accept` に sherpa-onnx の呼び出しと一緒に入っていて、モデル無しでは試験できなかった。訳す順番（確定訳の優先、途中訳の最新の1件、古い途中訳を捨てる）は `ConversationViewModel` が2つのスレッドから待ち行列・数・世代番号を触って決めていた。作者の会話の録音で、ぶつ切り・確定が途中と違う・言い始めが消える、の原因が、言語の判定の使い方・確定の範囲・区切る位置・話し始めの前に足す長さと分かり、直す場所が区切りの処理の中に散っていた。
- 決めたこと：作者と合意した計画（直す場所を考えて先に設計をきれいにし、その上で改善する）で、区切りを中核の `SpeechSegmenter`（`pipeline.speech`）に移し、VAD と認識を差し込み口（`VoiceActivity`・`SpeechRecognizer`）にした。`core-asr` はその実装になり、`core-llm` と同じく中核に依存する。区切りの中の判断を、`LanguageEvidence`（交代の根拠になる言語か）・`CutPoint`（区切る位置）・`TranscriptCleanup`（後処理）と、値の組 `SegmentationProfile` に分けた。訳す順番と方向は中核の `ConversationSession`・`LanguageRouter`（`pipeline.conversation`）に移した。音声認識の契約（`AsrEngine` など）は中核の `SpeechEngine`・`SpeechEvent`・`Utterance` にした。振る舞いは変えていない。
- 理由：録音で分かった直しが、それぞれ1つの判定の中身か1つの値に収まり、偽の VAD と認識で単体テストできる。訳す順番の決まりも、出来事と作業で試験できる。差し込み口を中核に置き、外の部品がそれを実装する形は、翻訳のエンジン（`JobEngine` と `core-llm`）と同じで、依存の向きが1つの決まりにそろう。
- 捨てた案：先に4つの直しを今の作りに入れる（作者が、設計をきれいにしてから改善を入れる方を選んだ）。`core-asr` を中核に依存させず、`app` が VAD と認識の部品を組んで中核に渡す（`core-asr` の返す型がばらばらになり、テキスト翻訳の音声入力と会話翻訳で組み立てが2か所になる）。
- 再発を防ぐもの：`SpeechSegmenterTest`（話し終わり・言いよどみ・間ありと話し中の交代・長い発話・雑音・中国語の扱い・停止）、`ConversationSessionTest`（確定訳の順番と優先、途中訳の最新の1件、古い途中訳）。端末では、録音を移す前後で流し、区切りのログを比べた（`docs/設計/会話翻訳.md`「動作確認」）。`tools/check-design.ps1` の中核の依存の約束。`docs/設計/会話翻訳.md`「音声認識」「翻訳への渡し方」、`docs/設計/アーキテクチャ.md`。
