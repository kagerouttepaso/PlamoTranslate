# Qwen3-ASRの途中認識を中断し翻訳と同じGPUの推論を直列にする

- 状態：有効
- 問題：旧 sherpa-onnx 版は途中の認識を止められず、確定に使う文が待たされた。モデルが判定した言語も取り出せなかった。
- 決めたこと：Android と Windows で翻訳と同じ llama.cpp の JNI を使い、Qwen の途中認識を取り消せるようにする。翻訳と書き起こしが同じ GPU を使うときは準備も推論も直列にする。確定文は言語を指定せずに書き起こし、話し中の話者判定には Whisper tiny を使う。
- 理由：Android で PLaMo と Qwen を同じ OpenCL で同時に動かすと、12組中で書き起こしが2〜7件、訳が1件変わり、翻訳時間も0.6秒から3.2秒に延びた。順に実行すると毎回一致した。CPU の書き起こしと GPU の翻訳は同時でも一致した。
- 捨てた案：sherpa-onnx に言語ラベルを戻すだけでは推論を止められず、ONNX Runtime の中断処理を両 OS 向けに保守する必要がある。モデル自体を替えると認識精度の評価もやり直すことになる。
- 再発を防ぐもの：`LlamaRuntime` がプロセス内で同じ GPU の利用権を管理する。`QwenAudioJniTest` が認識を中断し、同じコンテキストで次の音声の本文と言語が再現することを確かめる。

## 実行先と中断の比較

FLEURS の日・英・韓を4スレッドで書き起こした。Windows は Core i3-12100 と RTX 4060（各20文）、Android は REDMAGIC 11 Pro と Adreno 840（各3文、熱制御下を含む）。中断時間は試作時の実測である。

| 環境と実行先 | 1文の中央値 | 旧 sherpa-onnx 版との時間比 | 止めるまで |
| --- | --- | --- | --- |
| Windows CPU | 2.60秒 | 1.05倍 | 20〜80 ms |
| Windows Vulkan | 0.22秒（最初の1文は11秒） | 0.09倍 | 6〜17 ms。音声入力の段だけ最初の1回に1.5秒 |
| Android CPU | 2.58秒 | 1.2〜1.5倍（文ごとの比の中央値は1.54倍） | 4〜31 ms |
| Android OpenCL | 3.94秒 | CPU より遅い | 9〜133 ms |
| Android Vulkan | 動かない（落ちる、またはラベルが出ない） | — | — |

Android の OpenCL の初回準備は22秒、キャッシュ再利用時は2.4秒。CPU のエンコーダーと一括評価を8スレッド、生成を4スレッドにすると9文の平均は2.06秒で、交互に測った旧版は2.35秒だった（7文で先着、本文は全段4スレッドの場合と9文とも一致）。全段8スレッドでは生成が0.6秒から1.9秒に延びた。Q8_0 の行列計算には i8mm が使われ、音声エンコーダーの重い F16 の畳み込みは KleidiAI を通らなかった。旧 Android 版の日韓8文では確定用の書き起こしの待ちが中央値0 ms・最大1.2秒、区切りから確定までは中央値2.1秒・最大4.0秒だった。

文全体の言語ラベルは日英韓の60文すべてで正しく、旧版との書き起こしの誤り率は同程度だった。言語指定の有無で誤り率はほぼ変わらなかった（旧 Windows 版の日本語のみ0.5ポイント差）。日本語の1〜2秒の区間でラベルが正しかった割合は55〜60%。候補外を保留する判定では、1.5秒の日英・日韓各40件で誤確定0件、保留8〜9件だったが、2秒の日韓では候補内の誤確定が2件あった。
