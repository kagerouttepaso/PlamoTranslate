# 訳の控えを多層の控えとして定める

作者の合意を取るための計画。翻訳の契約（`TranslationStream`）と差し込み口の名前・形を変えるので、合意の後に進める。

## 望む状態

- 訳の控えを、翻訳の契約の「多層の控え」として1つのポリシーで定める。どの層も同じ鍵・同じ約束に従い、約束ごとに契約の試験がある。
- 層の名前がそろっていて、名前から層の位置が読める。
- 機能が決めるのは「どの層を使うか・どれだけ長く持つか」だけで、鍵の範囲・引き方・書き方は契約が決める。

## 今の構造の問題

控えが契約の添え物として足されてきたため、層ごとに鍵と約束がばらばらで、書かれていない約束は改修で漏れる（`docs/判断/2026-11-13_流れを閉じても訳し終えた片は控えに書く.md`）。

1. **名前**：1次は `MemoryCache`（メモリの控え）、2次の差し込み口は `TranslationMemory`（長く残す控え）、2次の実装は `TranslationCache`。2層であることも、どれが永続かも名前から読めない。
2. **鍵の範囲が場当たり**：
   - 1次の中身は片の原文だけを鍵にする。原文の言語・訳す先・背景をそろえるのは「共有する流れどうしでそろえる」という呼ぶ側の注意だけで、契約は守らない。
   - 2次の範囲は、画面翻訳のサービスが `Options` とは別に `(source, SCREEN_TARGET)` から組み直す。背景（context）を渡しておらず、`Options` と食い違い得る。
   - 訳を変える `Options.form`（です・ます／だ・である）が、どちらの層の鍵にも無い。今はどの機能も既定のままなので表に出ていない。
3. **モデルの扱いが層で違う**：1次はエンジンが変わると全部捨てる（同じモデルを読み直しても捨てる）。2次はモデルをまたいで持ち、訳の確かさの順位（0.8B＜2B）で優先する。
4. **約束の置き場**：「訳し終えた片は閉じても書く」は今回の修正で入った。「消した後に、消す前に始めた翻訳の訳を書かない」は2次の実装（`TranslationCache.Scope` の `born`）にあり、契約には無い。

## 直した後の構造

### 名前

| 層 | 今 | 後 |
| --- | --- | --- |
| 1次 | `MemoryCache`・メモリの控え | `MemoryCache`・メモリの控え（変えない） |
| 2次の差し込み口 | `TranslationMemory`・長く残す控え | `PersistentCache`・永続の控え |
| 2次の実装 | `TranslationCache` | `SqlitePersistentCache` |
| 層の全体 | なし | 訳の控え（多層） |

カメラ翻訳の `LiveTranslator` が持つ表は、控えでなく表示の状態なので「訳の対応表」と呼ぶ（このブランチで名前だけ変えた）。

### 鍵

- **範囲** `CacheScope`（中核）：原文の言語（自動は自動のまま別の範囲）・訳す先・`form`・背景。契約が `Options` から作り、機能も2次の実装も範囲を組まない。
- **鍵**：範囲と片の原文の組。1次も2次も同じ鍵で引く。
- **値**：訳と、訳したモデル `ModelOrigin`（重みの識別子と確かさの順位）。

### 約束（ポリシー）

`docs/設計/翻訳コア.md`「控え」をこの一覧に書き直し、項目ごとに `TranslationStreamTest` の試験を置く。

1. **引く順番**：1次 → 2次 → エンジン。2次で当たった片は1次にも入れる。エンジンを動かしている途中に頼まれた片は1次だけを引く（推論を待たせない）。
2. **確かさ**：どの層も、今のモデル以上の順位の訳だけを使う。同じ鍵に自分以上の訳があれば書かない。モデルを切り替えても層を捨てない。
3. **書く約束**：エンジンで訳し終えた片は、閉じても取り消されても書く。空の訳と原文の写しは書かない。
4. **消す**：2次を消したら世代が進み、1次も捨てる。世代が進む前に始めた翻訳の訳は、どの層にも書かない（2次の実装でなく契約が世代を渡して守らせる）。
5. **容量**：1次は件数の上限で最後に使ったものから捨てる。2次の上限と捨て方は実装が決める。
6. **持ち主**：どの層を使うか、1次をどの流れと共有するかは機能が決める。範囲が鍵に入るので、範囲の違う流れどうしで共有しても混ざらない。

### 差し込み口の形

```kotlin
data class CacheScope(val source: Language?, val target: Language, val form: JapaneseForm, val context: String?)
data class ModelOrigin(val id: String, val rank: Int)

interface PersistentCache {
    /** 消した回数。進んだら1次も捨て、それより前に始めた翻訳の訳は書かない。 */
    val generation: Int
    suspend fun lookup(scope: CacheScope, minRank: Int, texts: Collection<String>): Map<String, String>
    /** [generation] が今と違えば書かない。 */
    suspend fun store(scope: CacheScope, origin: ModelOrigin, generation: Int, translations: Map<String, String>)
}

class Backend(val engine: JobEngine, val origin: ModelOrigin, val persistent: PersistentCache? = null)
```

`Translations.open` の `persistent` は、モデルごとの `Scope` を作る関数をやめ、`PersistentCache` を受け取るだけにする。

## 移す順番

1つずつコミットし、各段で単体テストを通す。

1. **名前だけ変える**：`TranslationMemory`→`PersistentCache`、`TranslationCache`→`SqlitePersistentCache`、文書の「長く残す控え」→「永続の控え」。振る舞いは変えない。
2. **鍵の範囲を契約に移す**：`CacheScope`・`ModelOrigin` を足し、2次の差し込み口を上の形にする。画面翻訳のサービスは範囲を組まなくなる。データベースは版を3に上げて作り直す（今の中身は今回の不具合でほぼ空）。
3. **1次を同じ鍵と確かさにそろえる**：1次の中身を「鍵 → 訳と順位」にし、捨てる条件を世代だけにする。
4. **ポリシーを文書と試験に置く**：`翻訳コア.md`「控え」を約束の一覧に書き直し、約束ごとの試験を足す。判断の記録を1件足す。
5. **カメラ翻訳の訳の対応表を見直す**（ロジックの変更。下の「決めること」の答えしだい）。

## 決めること（作者）

- **モデルを切り替えたときの1次**：上の案では捨てず、確かさの順位で選ぶ。0.8B→2Bでは0.8Bの訳を使わず訳し直し、2B→0.8Bでは2Bの訳をそのまま使う。2次と同じ振る舞いになる。
- **原文の言語の自動と明示**：自動で訳した訳と、言語を指定して訳した訳を別の範囲にする案にした。同じ範囲にまとめると当たりは増えるが、言語の取り違えた訳が混ざり得る。
- **カメラ翻訳の訳の対応表**：モデルを切り替えたときに確定した訳の表を捨てる今の振る舞いを、1次の確かさの約束に合わせるか。表は表示の状態なので、合わせなくても契約とは矛盾しない。
