# Qwen3-ASR を llama.cpp で動かす計画

会話翻訳の Qwen3-ASR を、sherpa-onnx（ONNX、int8）から llama.cpp（GGUF Q8_0、mtmd）に移す。Silero VAD・SenseVoice・読み上げは sherpa-onnx のまま残す。特定の PC や端末に合わせず、GPU がある環境・無い環境のどちらでも動く形にする。

## 何を直すか

sherpa-onnx の Qwen3-ASR には、次の2つの不足がある。

- **書き起こしを途中で止められない。** 文が終わっても、走っている途中の書き起こしが終わるまで、確定用の書き起こしが待つ（`docs/判断/2026-11-23_文末の無音では途中の書き起こしを頼まない.md`）。
- **モデルが判定した言語を返さない。** 言語は Whisper tiny で別に識別し、カードの言語を決めるまで2秒待つ（`docs/判断/2026-11-23_新しいカードの言語は話し始めの2秒を待って決める.md`）。

llama.cpp では書き起こしの処理を自分のコードで回すので、止めることも、言語のラベルを受け取ることもできる。llama.cpp は翻訳のためにすでにソースからビルドしており、新しいビルドの経路は増えない。

## 確かめたこと

固定した submodule の版のまま、FLEURS の日・英・韓で測った。Windows は Core i3-12100 と RTX 4060（各20文）、Android は REDMAGIC 11 Pro（Adreno 840、各3文。熱の制御が働いた状態を含む）。推論は4スレッド。

| 環境と実行先 | 1文の中央値 | 今の sherpa-onnx との比 | 止めるまで |
| --- | --- | --- | --- |
| Windows CPU | 2.60秒 | 1.05倍 | 20〜80 ms |
| Windows Vulkan | 0.22秒（最初の1文は11秒） | 0.09倍 | 6〜17 ms。音声入力の段だけ最初の1回に1.5秒 |
| Android CPU | 2.58秒 | 1.2〜1.5倍（文ごとの比の中央値は1.54倍） | 4〜31 ms |
| Android OpenCL | 3.94秒 | CPU より遅い | 9〜133 ms |
| Android Vulkan | 動かない（落ちる、またはラベルが出ない） | — | — |

- **CPU だけで動く。** Android でも Windows でも、GPU を使わずに書き起こしと翻訳が最後まで動いた。Windows で Vulkan の DLL が無い場合も、CPU で続けた。
- **翻訳と同じ GPU を同時に使うと、結果が変わる。** Android で PLaMo と書き起こしを両方 OpenCL に同時に投げると、翻訳が 0.6秒から 3.2秒に延びた。それだけでなく、書き起こしと訳の文字も変わった（12組中、書き起こし2〜7件、訳1件）。順に投げたときは毎回一致した。書き起こしを CPU にすると、同時でも結果は変わらず、翻訳もほぼ延びない。
- **言語のラベル**は、文の全体なら全言語で正しい。短い日本語では当たらないことが多い（1〜2秒で55〜60%）。
- **誤り率**は、今の sherpa-onnx とほぼ同じ（Windows で20文ずつ比べた）。
- **GPU の準備に失敗したとき**：OpenCL のドライバーが無ければ、CPU で続けた。カーネルの組み立てに失敗するとプロセスごと落ち、次の起動で CPU に戻した。今の `GpuGuard` が守るのは翻訳の読み込みまでなので、後から読み込む書き起こしも守る必要がある。
- **OpenCL の最初の準備**は22秒かかり、キャッシュが効けば2.4秒で済む。
- **今のアプリの基準値**（Android、C1・C2 入り、Qwen3-ASR、日韓8文）：確定用の書き起こしの待ちは中央値0 ms・最大1.2秒。区切ってから確定までは中央値2.1秒・最大4.0秒。

## 実行先の選び方

1. **GPU は1つの推論だけが使う。** 翻訳と書き起こしが同じ GPU を使うときは、推論を1本の順番待ちに並べる。上の、結果が変わる問題を避けるためで、性能ではなく正しさの決まりである。
2. **翻訳と書き起こしで、実行先を別々に持つ。** 翻訳は今の決まり（GPU を使える環境は GPU）のまま。書き起こしは CPU か GPU のどちらかにする。
3. **書き起こしの実行先は、その環境で短く試して決める。** 準備のときに参考の音声1本を CPU と GPU で書き起こし、GPU が CPU よりはっきり速いときだけ GPU にする。比べるのは最初の1回を除いた値。結果はモデル・実行先・環境の組ごとに保存し、利用者が設定で上書きできる。今の測定では、Windows の RTX 4060 では GPU、Android の Adreno では CPU が選ばれる。端末ごとの値は埋め込まない。
4. **CPU を基準の構成にする。** GPU が無い環境、GPU の準備に失敗した環境、利用者が「CPU だけ」を選んだ環境は、すべて CPU で動く。試験では毎回 CPU だけの条件を入れる。
5. **落ちたときの戻し方は、翻訳と同じ仕組みを役割ごとに持つ。** `GpuGuard`・`GpuStartupPolicy` の退避の状態を翻訳用と書き起こし用に分け、書き起こしの GPU の準備も守る。戻した後は、利用者が「GPU をもう一度試す」を押すまで CPU のまま。
6. **ネイティブのライブラリは1つにし、バックエンドは実行時に読み込む。** 書き起こしを翻訳と同じ llama.cpp のライブラリに載せ、ggml を二重に持たない。アプリ全体で GPU を使うかは、最初の初期化の前に決める（今の JNI は初期化を1回しか行わない）。
7. **最初の1回が遅い分は、準備のときのならし運転とキャッシュで吸収する**（`docs/判断/2026-11-22_PCの会話画面は取り込み前に使う認識器を準備する.md`）。Vulkan のカーネルと OpenCL の `cl-cache/` が対象。

## 進め方

各段の後で作者と結果を確かめ、次へ進むかを決める。

1. **共通の実装を作り、PC 版を替える。**
   - `SpeechRecognizer` の実装を `core-llm-jvm` に置く（Android と PC で共有）。
   - 書き起こしを止める命令を足し、言語のラベルを結果に載せる。言語を指定した結果のラベルは、言語を決める根拠にしない（今の決まりのまま）。
   - 確定用の書き起こしは言語を指定せずに行い、モデルのラベルを「書き起こしの言語」の根拠にする（`docs/判断/2026-11-19_会話のカードの言語を書き起こしの言語と利用者の指定でも決める.md` の順位のまま）。文の全体ならラベルは60文すべて正しかった。誤り率は言語を指定したときと変わらなかった（Windows の sherpa-onnx で日本語のみ +0.5 ポイント）。
   - 確定用の書き起こしが来たら、走っている途中の書き起こしを止める。
   - 「実行先の選び方」の1〜7を入れる。
   - PC 版は sherpa-onnx の Qwen3-ASR を消して、こちらに替える。見立ての会話で、GPU と CPU だけの両方の条件で、変更の前後を比べる。
2. **Android も同じ実装に替え、CPU での遅さの原因を直す。** Qwen3-ASR の実装は PC と Android で1つにし、sherpa-onnx の Qwen3-ASR は両方から消す（作者の決定。PC と Android で書き起こしの振る舞いを分けない）。Android の CPU で1.2〜1.5倍遅い原因は次の段で調べる。
   - 遅いのは、音声エンコーダー（9文の平均1.16秒）と、音声をデコーダーに入れる段（0.92秒）で、文字の生成（0.61秒）ではない。どちらも行列をまとめて計算する段である。
   - この端末では、llama.cpp の CPU 版は armv9.2 の版を読み込み、Q8_0 の行列計算に KleidiAI の SME のカーネルを選ぶ。SME の計算は、端末が示す SME の計算器の数（この端末は2）までのスレッドに制限される（`ggml-cpu/kleidiai/kleidiai.cpp`）。4スレッドを頼んでも、まとめて計算する段は2スレッド分で動いている可能性がある（推定）。
   - 確かめ方：`GGML_KLEIDIAI_SME=0`（SME を使わず、i8mm のカーネルを4スレッドで使う）、KleidiAI を使わない場合、スレッド数を変えた場合を、同じ文で交互に流して段ごとの時間を比べる。熱の状態の差を避けるため、方式を交互に並べる。
   - 直し方は、端末の名前で分けず、準備のときの試走（「実行先の選び方」の3）で、SME の有無も含めて速い方を選ぶ。翻訳を CPU で動かす端末にも同じ選び方を使う。
   - 見立ての会話で、話し終わりから確定訳までの時間を、上の「今のアプリの基準値」と比べる。
3. **カードの言語の決め方を変えるか（別の判断）。** 言語を指定せずに書き起こし、モデルが出したラベルを根拠にすれば、2秒を待たずに書き起こしを始められる。ただし、短い日本語ではラベルが無いことが多く、誤りもある。会話の候補にあるラベルだけを仮に採り、無い・候補外なら決めない、という決まりで 1.5秒を採点し直すと、日英・日韓の各40件で誤った確定は0件、保留は8〜9件だった。それでも 2.0秒の日韓では、候補内の誤りが2件あった。長い音声の結果でカードの言語を後から直せる形にしてから決める。話し中の区間（直近1.5秒）での話し手の判定は、今のまま Whisper tiny で行う。

## 後で確かめること

- ほかの Android 端末での速さとメモリ。
- Windows で、翻訳と書き起こしを同じ Vulkan の GPU で同時に動かしたときに、結果が変わるか（順番待ちにするので、作りには影響しない）。
- Vulkan のランタイムが入っていない別の PC での起動。
- 止める確認を常に入れたときに、どれだけ遅くなるか。

## 採らない案

- **sherpa-onnx を改修する。** 言語を返すだけなら、こちらの方が小さい（Qwen3-ASR の実装で、捨てているラベルを結果に入れるだけ）。ただし、止める仕組みには ONNX Runtime の `RunOptions` の作り替えが要り、効き方は測っていない。Android と Windows の両方を自分たちでビルドし、版を上げるたびに改修を当て直す負担も残る。
- **別のモデルにする（whisper.cpp など）。** 精度の評価をやり直すことになり、依存も増える。Qwen3-ASR のままで2つの不足を直せるので採らない。
- **Android の書き起こしを Vulkan で動かす。** この端末では落ちるか、ラベルが出なかった。

## 詳しい設計（実装前のレビュー案）

PC と Android で共用するのは、音声から本文と言語を得る処理と、推論をどこでどの順に実行するかの判断である。OS ごとに変えるのは、モデルの場所、GPU の検出、設定の保存、画面への表示に限る。以下は実装済みの仕様ではない。第1段階の完了条件は、PC の実際の会話で、途中結果を捨てて確定文を取りこぼさず、GPU がなくても同じカードを最後まで訳せることとする。

### モジュールと依存

| 置き場所 | 責務と変更 |
| --- | --- |
| `core-pipeline` | `RecognitionRequests` が書き起こしの用途と言語指定を決める。`RecognitionQueue` は従来の順位、`SpeechPipeline` は実行中のジョブと中断を管理する。GPU の選択・退避・待ち順の判定もここに置く。JNI、設定ファイル、スレッドの待機を判定に持ち込まない。 |
| `core-llm-jvm` | `QwenAudioRecognizer` が PCM を渡し、モデルの出力を `Recognition` に変換する。`LlamaRuntime` がバックエンドの初期化と GPU の利用権を管理し、`TranslationEngine` と認識器の全インスタンスが同じものを使う。`LlamaNative` だけが JNI を呼ぶ。 |
| `core-llm`・`desktop-native` | `plamo-llm` の ASR 用 C++ ソースを翻訳用と分け、両方の CMake から同じソースをビルドする。固定版の `LLAMA_BUILD_MTMD=ON`、CLI は無効のまま。`mtmd` と既存の `llama`・`ggml` をリンクする。別の JNI ライブラリや、もう一組の ggml は作らない。 |
| `desktop`・`app`・`core-asr` | PC は `DesktopAsr`、Android は `SpeechEngines` で、VAD・書き起こし・言語の識別を組み立てる。書き起こしの生成関数を `app` から `SpeechEngines` に渡す。設定とクラッシュの情報を渡すのは `DesktopSettings` と Android の `GpuGuard`。取り込み側や画面は GPU を取得しない。 |
| `core-asr-sherpa` | 第1段階では Android 用の旧 Qwen が残る。第2段階で取り除く。Silero VAD と、それに必要な sherpa の配布は残す。 |

アーキテクチャの **Gradle の依存表は変更不要**。既に `app → core-llm → core-llm-jvm → core-pipeline`、`desktop → core-llm-jvm`、`core-asr → core-pipeline` がある。`core-asr → core-llm` を追加すると認識の組み立てがネイティブの配布方法まで選ぶため採らない。実装時には同文書の「各モジュールに置くもの」を上表に合わせて直す。`check-design.ps1` の JNI・翻訳の呼び出し・ログの例外は増やさない。Android では `libmtmd.so` と縮小後の JNI の名前、Windows では `Main.kt` の DLL 読み込み順（ggml → llama → mtmd → JNI）と配布物への同梱を実物で確認する。Vulkan の DLL は必須 DLL にしない。

### 書き起こしの命令と結果

書き起こしと、話し手のスコアを取る操作を分ける。`IdentifiedRecognizer.recognize(samples, languages, fallback)` は、引数の言語がなくても Whisper の結果を Qwen に指定する。単に `null` を渡す変更では確定文を自動判定できない。中核で「指定なし」「この言語を指定」を明示し、指定なしは識別器を通さずモデルの自動判定を呼ぶ。スコアの取得、スコアのない SenseVoice の書き起こし再利用、セグメンターと識別ワーカーの並行動作は維持する。

| ジョブ・操作 | Qwen に渡す言語 | 結果を使う場所 |
| --- | --- | --- |
| 自動判定の会話の `PHRASE` と `FINAL` | 指定なし。区切った残りだけでなく確定文を構成する各文が対象。カード全体を二重に書き起こさない | 本文を `CardTranscript` へ、モデルが返した言語を `LanguageSource.JUDGED` として `SpeechSegmenter.noteTranscript` へ |
| `PARTIAL` | 今の話し手の言語。新しいカードでは従来どおり話し始めの判定を待ち、文末の無音では頼まない | 途中の本文だけ。指定の写しは `SPECIFIED` で、根拠にしない |
| 利用者が入力言語を固定した場合、カードを入れ替えた `RETRANSCRIBE` | 利用者の指定。固定入力は自動判定の確定とは別の操作で、識別しない | 指定を維持する。指定不能は `UNSUPPORTED` とし、推定した言語で成功にしない |
| `LANGUAGE`・`PHRASE_LANGUAGE`・`Seam` | Qwen には渡さない（Qwen と識別器を組み合わせた場合） | Whisper tiny のスコアで区間・文・境界を判定する。書き起こしのラベルではカードを区切らない |

モデルの生成結果は UTF-8 で受け、先頭の `language Japanese<asr_text>` などを本文から分ける。名称を言語コードにして返し、指定した要求なら、ラベルが一致しても必ず `SPECIFIED`。未知・欠落ラベルは言語なしとし、識別できる本文は残す。制御トークンと役の名前だけの誤認識は本文に混ぜない。`LanguageEvidence` の文字種・語数・会話の候補と、`SpeakerTrack` の音声長による多数決（同じ開始位置の結果は置換）を通す。利用者の指定 ＞ 有効な書き起こしの言語 ＞ 区間・文で決めた話し手、の順で表示する。候補外・短いラベルを `finishIfReady` の `label ?: r.lang` で無条件に復活させない。`GUESSED` は音声の根拠にしない。2秒の条件を短くする案、途中結果で次の話し手を変更する案は今回採らない。

部品間の契約は `submit(request)`・`cancel(id)`（どちらも結果を返さない）と `results: Flow` にする。要求は世代、ジョブ番号、カード番号、音声範囲、用途、PCM（16 kHz・モノラル）、言語指定を持つ。終了は同じ番号の「成功（本文・言語・出どころ）」「取消」「失敗」のいずれか1回。成功した空文字は取消と区別する。`SpeechPipeline` が購読を確立してから要求を受け、購読側が一時的に遅れても終了を捨てない。同期する JNI や sherpa の呼び出しはワーカー内部に限定する。公開する `SpeechEngine` の音声・区切り・停止の命令は変えず、`listener`・`loadListener` は順序を保つイベントの `Flow` と最新の混雑状態の `StateFlow` に置き換え、両 OS とテキスト音声入力の利用側を同じ変更で移す。UI にキャンセル用ハンドルを渡さない。

ワーカーを二重に作らない。書き起こし用の要求は `SpeechPipeline` の既存の書き起こしワーカーが取り出し、認識器の内部で同期 JNI を実行する。識別ワーカーは別のままにする。既存の sherpa を使う間は実行中の演算は止められないため、同じ取消契約で結果だけを捨てる。中断時間の改善を約束するのは新しい Qwen 実装だけである。

### 推論の順番と中断

`RecognitionQueue` は「どの音声を次に処理するか」を今までどおり決める。確定に必要な処理は古いカードから、同じカードでは既存の順位を使う。`FINAL` または `PHRASE` の登録時に、実行中または GPU 待ちの `PARTIAL` の番号を `SpeechPipeline` が取り消す。確定文、書き起こし直し、識別ワーカーは中断しない。逆の競合（確定が先に登録されたところへ途中結果が来る）は待ち行列の既存の順位で防ぐ。`RecognitionLoad.urgent` で途中訳を待たせる制御も残す。

GPU の順番はモデルごとではなく `LlamaRuntime` が選んだ同じデバイスにつき利用権1つとする。翻訳の全機能・初回の準備・`ParallelTuner` の計測・ASR の試走も対象。同じ GPU に対するモデル準備と推論も重ねない。別々の PC プロセスから使える場合は、同じデバイスに対応する Windows の名前付き mutex も使い、所有者終了時には取得を回復する。CPU と GPU、CPU 同士にはこの制限を掛けない。個々のモデルのコンテキストを同時に使わない制限と、既存の CPU スレッド数の設定は別に守る。

実行中の翻訳を途中で破棄しない。待っている確定書き起こしを次の利用者とし、ほかは到着順。同じ優先度の依頼は追い越さない。翻訳では1回の `nativeTranslateJobs` に複数の文をまとめてよいが、他の GPU 待ちがある間は `nextJob` が新しい文を取り出さず、開始済みのシーケンスだけを完了して利用権を返す。`TranslationEngine.run` は未着手の文を失わず再取得して続け、元の `JobEngine.run` の契約を守る。再取得時に少なくとも先頭の組は開始してから譲る。単に `run` 全体をロックすると、翻訳が供給され続けるときに確定文が待ち続ける。CPU まで直列にする案では、CPU の ASR と GPU の翻訳を正しく並行できた検証結果を生かせない。

JNI の中断は、要求ごとの ID と寿命を持つ `atomic<bool>` で伝える。登録と取消を先に照合できるよう、要求をワーカーに渡す前に取消状態を作る。`nativeCancel` は番号で生存中の要求を参照し、フラグを立ててすぐ戻る。翻訳や認識の実行ロック・ワーカーのディスパッチャーを待たない。GPU 待ちは待ち行列から外す。開始と競合したら、取得直後と JNI に入る直前にも取消を調べる。ハンドルを生ポインターのまま別スレッドへ渡さない。`close` は新規要求を拒み、実行を止めて参加を待ち、コールバックが終わった後にだけ解放する。

| 確認する段階 | いつ打ち切れるか |
| --- | --- |
| 音声エンコーダー | 音声チャンクの前後に加え、`mtmd_context_params.cb_eval` の選択した評価点で確認する。打ち切っても `mtmd_encode_chunk` が成功を返した実測があるため、要求フラグを調べ、未完の埋め込みは渡さない。確認点を増やすと同期も増えるので、有効にした実装で測る。 |
| デコーダーへの音声入力 | 埋め込みを制限したサイズのバッチで評価し、各バッチの前後に確認。CPU では `llama_set_abort_callback` も設定する。Vulkan・OpenCL で発行済みの GPU 演算が即座に止まるとは仮定しない。 |
| 文字の生成と後始末 | 各トークンの `llama_decode` の前後と結果の公開前に確認。出力を破棄し、実行を同期して KV・位置・サンプラー・チャンクを次の要求に持ち越さない。GPU 利用権は後始末を終えてから返す。 |

結果はセグメンターのスレッドに戻す。世代・ジョブ番号・カード番号と対象範囲が一致する保留中の要求だけを完了し、一度取り除いた要求の遅着を無視する。閉じたカードの確定結果は受けるが、途中結果は反映しない。取消でも `partialInFlight` と待ち件数を解放し、既に表示した途中の本文や言語票を書き換えない。`reset` は世代を進めて旧要求を忘れ、保持した音声の書き起こし直しは既存どおり新たに頼む。`flush` は確定文を取り消さず、すべての `CardFinished` の後に `Flushed` を出す。

### 実行先の選択と退避

設定上の希望、準備で実際に使えた実行先、GPU 失敗による退避を混同しない。`Translation` と `Transcription` の役割ごとに準備状態（未準備・準備中・使用可・失敗）と実行先・選択理由を `StateFlow` で出す。上限はアプリ全体の「CPU だけ」。PC の Vulkan 無効・Android の GPU 不許可も越えない。次にその役割の退避を適用し、その後で利用者の ASR 設定（自動・CPU・GPU）を見る。GPU 指定でも使えなければ理由を表示して CPU。翻訳の自動選択と `ParallelTuner` の同時翻訳数は変えない。ASR の速度比較を `ParallelTuner` に混ぜない。

1. 最初の JNI 呼び出しの前に、プロセス共通の GPU 使用許可を両役割の設定から一度決める。翻訳を最初に開いたか、ASR を最初に開いたかで結果を変えない。`LlamaRuntime` は CPU バックエンドと `llama_backend_init` を一度だけ初期化し、GPU 登録は許可があり、初めて GPU を必要とした役割の保護区間で一度だけ行う。Windows は既存の `g_backend_once` と `g_vulkan_once` の分離を使い、Android は `nativeInit(loadGpu)` の最初の引数で CPU/OpenCL の組が固定される構造を改める。CPU の版を先に選び、必要時に同じレジストリに OpenCL だけを登録する。登録中はほかのネイティブ実行を開始しない。共通の初期化を二度行う案や、ロード順に依存する案は採らない。CPU の版・GPU 使用許可を変えて既にある登録と両立しない場合は、再起動後に適用する。
2. ロードはモデルごとに独立させる。CPU は GPU レイヤー数を 0、デバイス一覧を空、KV・演算のオフロードを無効、`mtmd.use_gpu=false` とする。GPU の ASR はデコーダーと `mtmd` に同じデバイスを明示する。GPU が登録されたというだけで使用中と報告しない。実際にデバイスが使えたことと既知音声の結果を確認する。
3. ASR の自動選択はモデルが揃い、取り込みを始める前に行う。再配布可能な短い固定音声（16 kHz、既知の本文と言語）と正解を両 OS が同じ資源から読む。各候補を順にロードし、同じスレッド数・生成条件・中断確認で、ウォームアップ1回の後に3回測る。計測は PCM 受領から言語と全文の返却までで、ロード・GPU 待ちは除く。本文の正規化とラベルを正解と比較する。GPU が3回とも正しく、経過時間の中央値が CPU の80%以下の場合だけ GPU にする（20%は測定結果ではなく、小差なら競合しない CPU を優先する採用基準案）。同時に候補2つを常駐させず、残す候補だけ使用可にする。CPU の出力も不正ならモデル破損などを報告し、自動選択の成功を保存しない。
4. 自動選択のキーには本体と mmproj の SHA-256、アプリの推論実装・llama.cpp の版、OS・ABI、CPU の版とスレッド数、GPU デバイス・バックエンド・ドライバーの版、試走用音声と判定方法の版を入れる。判別できない環境を別端末と共有しない。保存するのは実行先・時間・理由。音声・認識文は記録しない。キーが一致すれば比較を省き、採用した実行先だけをウォームアップする。GPU が遅いだけなら退避ではない。CPU 指定・GPU 不可・退避中は GPU を試走しない。強制 GPU は速度比較だけを省き、正しさの確認を省かない。重複する準備要求は1回にまとめ、画面を閉じた後の試走で現在の選択を書き換えない。
5. `GpuStartupPolicy.decide` の終了理由・意図した終了・連続中断回数の判定は共通のまま、状態の読み書きは役割をキーにする。最初の GPU 登録・モデルと投影部のロード・初回推論・自動試走までを1回の準備とし、その直前に役割・プロセスを永続化し、完了後にだけ準備中の記録を消す。試走を含む GPU 準備は直列にし、クラッシュ時に2役割を同時に退避させない。Android は終了記録、PC は PID の生存と既存の連続中断判定を使う。復帰可能な GPU 障害は資源を解放して同じ役割を CPU で再準備する。プロセス終了なら次の起動で判定する。モデル自体の不足・破損は GPU 障害にしない。
6. 旧 `gpuFallback`・`gpuDisabled` 等の記録は翻訳用として引き継ぎ、ASR は未試行から始める。退避中はアプリ更新・試走キャッシュの失効・強制 GPU でも復帰しない。「GPU をもう一度試す」は選んだ役割だけの退避と試走結果を消して準備し直す。プロセスの再起動が必要ならその理由を示す。利用者の「CPU だけ」はこの操作で解除しない。Vulkan と OpenCL のカーネルキャッシュはアプリ専用領域で再利用し、ウォームアップの時間を初回の取り込みに含めない。

PC の起動指定 `mockingword.cpuOnly=true` は保存設定よりも強く、両役割とも Vulkan DLL の読み込みを試さない。Android の `cl-cache/` は OpenCL の登録より先に場所を設定する。端末名を速度の代わりに使わない。入力言語を固定し Whisper が不要な PC の構成では、GGUF の取得や準備を理由に Whisper の読み込みを強制しない。

### 実装の順序と試験

各行を独立した目的のコミットとする。構造を直す行では前後で同じ振る舞いを確認してから、次の行で機能を変える。設計の依存表と各モジュールの説明は実装と同時に更新する。

| 順 | 変更の目的 | その変更を通す試験 |
| ---: | --- | --- |
| 1 | 構造：認識結果・混雑状態を購読に移し、識別と書き起こしを分離する。旧両 OS の出力は維持する | 偽の認識器で区間のジョブ順、本文、指定・判定・推定、固定入力、入れ替え、`reset`・`flush` の既存試験。テキスト音声入力もイベントを失わない |
| 2 | 構造：ネイティブ初期化とデバイス利用権を `LlamaRuntime` に集め、退避の保存を役割別にする | ASR が先／翻訳が先、CPU だけなら GPU の DLL を開かない、旧退避の引継ぎ、別役割への影響なし。同じ GPU の同時実行数が常に1、CPU は並行可。翻訳継続投入時の順番、取り消した待機、チューナー・初回準備も試す |
| 3 | 共通実装：固定版 mtmd と ASR 用 JNI を追加する（まだ製品の選択を変えない） | 製品と同じ JNI に 16 kHz の `FloatArray` を渡し、日本語・英語・韓国語の UTF-8、言語未指定と指定、無音、役の名前、未知ラベル、末尾トークンを確認。単なる CLI 経由の試験では代用しない |
| 4 | 中断：途中結果を確定用ジョブで取り消し、取消と遅着を区別する | 偽のワーカーで開始前・実行中・結果配信直前・閉じたカード・再開始・解放との競合を再現。各要求の終了は1回、確定順は不変。JNI でエンコーダー・埋め込み入力・生成を別々に止め、次の音声が同じコンテキストで非中断時と同じ本文・ラベルになることを CPU と GPU で確認 |
| 5 | 実行先：試走とウォームアップ、設定の上書き、役割を指定した GPU 再試行を追加する | 偽時計と保存先で基準付近、正解不一致、キャッシュ失効・一致、CPU 指定、退避の永続化を確認。GPU ロードと試走中の異常終了、準備を中止した場合、CPU 再準備を実プロセスでも試す |
| 6 | PC を切り替える：モデル配布・更新案内・DLL を接続し、自動判定の確定文を言語未指定にする | 旧版のみ・一方だけ・破損・手動配置・ネットワークなし、GPU の DLL なしで配布物を起動。複数の取り込み元、入力言語固定、会話画面を開き直す場合も含め、下記の前後比較を通す。旧版の Android が旧一覧のまま動くことも確認 |
| 7 | Android を切り替える：同じ認識器とカタログに接続する | CPU・OpenCL・ドライバーなし・失敗後の再起動。会話とテキストの音声入力、バックグラウンドからの再開、翻訳との同時要求、APK 内の共有ライブラリと正式版の縮小後の JNI を確認。CPU の原因調査で変更が必要なら独立した性能改善として検証する |
| 8 | 旧実装と不要になった設定・説明を削除する | 旧形式への参照を検索。両 OS の対象試験、Silero・SenseVoice・Whisper・読み上げの起動、`tools/check-design.ps1`・`tools/check-docs.ps1` を通す |

**PC の前後比較。** 同じ日英・日韓の録音、話者順と正解文、同じ翻訳モデル・CPU スレッド数・カード設定で、変更前の sherpa と変更後を比較する。Vulkan を許可した構成と、GPU を無効にした CPU だけの構成を別々に測る。初回・キャッシュ後・取り込み中を分け、同じスタート位置から複数回リプレイする。途中認識の最中に文末を置く例、長文・交代・短い返事・強制区切り・停止、翻訳を流し続ける例を含める。

採否はまず、終了したジョブが別カードを更新しない、発話の欠落・重複がない、確定訳がカード順に届く、同一 GPU では単独実行時に対し同時要求による出力の変化がない、CPU だけでも完走すること。次に原文の CER（日韓）・WER（英）、言語と訳す向きの正誤、確定待ちと話し終わりから確定訳までの中央値・最大値を旧版と比較する。遅い発話は ASR の待機・処理・翻訳待ちを分けて示す。単文の速さだけでは採用しない。Android の 2.1 秒は区切りから認識確定までの参考値で、PC や確定訳までの合格値にはしない。中断の待ちは要求時刻から後始末後の再利用可能時刻までとし、初回約1.5秒を含む GPU 実測を保証値にはしない。

`ConversationReplayTest` の仮想時間はカードの比較に使い、実時間の改善の根拠には使わない。PC 配布物の取り込み経路に同じ録音を実時間で入れ、`tools/conversation_log.py` と実行時刻で発声終了から確定訳までを照合する。Android の CPU は熱状態を記録し、同じ文を交互に測る。SME の有無がプロセス単位で決まる場合は別プロセスで比較し、翻訳中に環境変数を書き換えない。

### 移行後に消すものと作者の確認

第2段階を通した時点で、`core-asr-sherpa/Qwen3Asr.kt` の旧認識器・ONNX 設定・専用トークナイザー一覧、PC と Android の旧生成処理、配布カタログの旧 Qwen URL と段階移行用の形式選択を消す。旧実装を直接生成する `AsrBenchActivity`・`AsrTest`・`ConversationReplayTest` は新しい生成経路に移し、`Qwen3RoleLeakTest` の振る舞いは共通の出力解析試験へ移す。旧 GPU 保存キーを読み続ける実行分岐は残さない（既存設定の取り込み時のみ変換）。設計書・取得手順・容量表示・モデルの説明から「Qwen はラベルを返さない」「sherpa で Qwen を動かす」を現行仕様としては消す。過去の比較値と判断の記録は事実として残す。本計画は両段階の完了後、採用内容を設計書と判断の記録に移して整理する。sherpa の AAR・DLL 自体、Whisper のモデルと識別、SenseVoice、Silero、読み上げは削除対象ではない。

**実装前に確認すること。** 移行先・PC を先にする順序・GPU の排他は合意済みで、再決定しない。今回の確認対象は、①同期認識とリスナーを命令と `Flow` に替える契約（確定の自動判定と、明示的な入力言語固定の区別を含む）、②アプリ全体の「CPU だけ」を最優先にした役割別設定・退避と、試走の20%基準、③約972 MiB の明示的な再取得と旧ファイルの任意削除、の3点である。新しい外部ライブラリや submodule 更新は不要。試走音声には再配布条件を確認したものを使う。Android の CPU 最適化と、話し始めの2秒を待たずにカードの言語を決める変更はこの承認に含めない。
