# Qwen3-ASR を llama.cpp で動かす計画

会話翻訳の Qwen3-ASR を、sherpa-onnx（ONNX、int8）から llama.cpp（GGUF Q8_0、mtmd）に移す。Silero VAD・SenseVoice・読み上げは sherpa-onnx のまま残す。

## 何を直すか

sherpa-onnx の Qwen3-ASR には、次の2つの不足がある。

- **書き起こしを途中で止められない。** 文が終わっても、走っている途中の書き起こしが終わるまで、確定用の書き起こしが待つ（`docs/判断/2026-11-23_文末の無音では途中の書き起こしを頼まない.md`）。
- **モデルが判定した言語を返さない。** 言語は Whisper tiny で別に識別し、カードの言語を決めるまで2秒待つ（`docs/判断/2026-11-23_新しいカードの言語は話し始めの2秒を待って決める.md`）。

llama.cpp では書き起こしの処理を自分のコードで回すので、止めることも、言語のラベルを受け取ることもできる。llama.cpp は翻訳のためにすでにソースからビルドしており、新しいビルドの経路は増えない。

## Windows で確かめたこと

測った条件：Core i3-12100（推論は4スレッド）と RTX 4060。llama.cpp は固定した submodule の版のまま。FLEURS の日・英・韓を各20文。

| 確かめたこと | 結果 |
| --- | --- |
| 速さ（CPU） | 1文の中央値は Q8_0 が 2.60秒、今の sherpa-onnx が 2.48秒（1.05倍）。Vulkan では 0.22秒。Vulkan は最初の1文だけ11秒かかる |
| 止める | CPU は `llama_set_abort_callback` と mtmd の `cb_eval` で、20〜80 ms で止まる。Vulkan は文字の生成と音声エンコーダーなら 6〜17 ms。デコーダーへの音声入力の段では公式の中断が効かず、最初の呼び出しで 1.5秒待った |
| 言語のラベル | 文全体なら60文すべて正解。日本語は 1.0〜1.5秒で 55〜60%、2.0秒で 60%（Whisper tiny は 75%）。外れの多くは「ラベル無し」だが、2.0秒で韓国語・ロシア語と誤った例もある |
| 誤り率 | 日本語 CER は 12.6% 対 11.9%、英語 WER は 5.7% 対 4.6%、韓国語 CER は 6.1% 対 6.8%。20文では差を言い切れない |
| 組み込み | Windows で Java から PCM を渡して書き起こすところまで動いた。Android の arm64 向けにも `libmtmd.so` をビルドしてリンクできた（24 MB、strip 前） |
| 配布量 | 本体と mmproj の2ファイルで 972 MiB。今の ONNX 一式より 30.6 MiB 多い |

## 進め方

ここでは、どの段で何を決めるかだけを書く。各段の後で作者と結果を確かめ、次へ進むかを決める。

1. **PC 版で Qwen3-ASR を llama.cpp に替える。**
   - `SpeechRecognizer` の実装を `core-llm-jvm` に置く。ネイティブ側は翻訳と同じ llama.cpp のライブラリに入れ、ggml を二重に持たない。
   - 書き起こしを止める命令を足す。言語のラベルは結果に載せる。言語を指定した結果のラベルは、言語を決める根拠にしない（今の決まりのまま）。
   - Vulkan の最初の1文が遅い分は、会話画面を開いたときの認識器の準備（`docs/判断/2026-11-22_PCの会話画面は取り込み前に使う認識器を準備する.md`）でならし運転をして吸収する。
   - 確定用の書き起こしが来たら、走っている途中の書き起こしを止める（C2 の待ちをなくす）。
   - 見立ての会話で、変更の前後を比べる。
2. **Android で同じ実装を確かめる（実機が要る）。** REDMAGIC で、読み込み、OpenCL に載る割合、PLaMo と同時に読み込んだときのメモリと遅れ、発熱を見る。CPU で今と同じくらいの速さが出れば、Android も替える。出なければ、Android だけ sherpa-onnx を残す。
3. **カードの言語の決め方を変えるか（別の判断）。** 言語を指定せずに書き起こし、モデルが出したラベルを根拠にすれば、2秒を待たずに書き起こしを始められる。ただし、短い日本語ではラベルが無いことが多く、誤りもある。会話の候補にあるラベルだけを仮に採り、無い・候補外なら決めない、という決まりで 1.5秒を採点し直すと、日英・日韓の各40件で誤った確定は0件、保留は8〜9件だった。それでも 2.0秒の日韓では、候補内の誤りが2件あった。長い音声の結果でカードの言語を後から直せる形にしてから決める。話し中の区間（直近1.5秒）での話し手の判定は、今のまま Whisper tiny で行う。

## 採らない案

- **sherpa-onnx を改修する。** 言語を返すだけなら、こちらの方が小さい（Qwen3-ASR の実装で、捨てているラベルを結果に入れるだけ）。ただし、止める仕組みには ONNX Runtime の `RunOptions` の作り替えが要り、効き方は測っていない。Android と Windows の両方を自分たちでビルドし、版を上げるたびに改修を当て直す負担も残る。2で Android の llama.cpp が使えないと分かったときの代わりとして残す。
- **別のモデルにする（whisper.cpp など）。** 精度の評価をやり直すことになり、依存も増える。Qwen3-ASR のままで2つの不足を直せるので採らない。
