# 計算資源をプロセスで1つの割り当てにまとめる計画

## 問題

推論の部品（翻訳・書き起こし・言語の識別・文字認識・読み上げ）は、それぞれが端末の CPU を自分だけで使える前提でスレッド数を決めている。数は、手元の2機種で測った定数から決まる。

| 場所 | 今の決め方 |
| --- | --- |
| 翻訳の既定 `TranslationEngine.threadsFor` | 最高周波数が一番低いコアが半分以下なら残りのコアの数、そうでなければコア数−2。2〜6に収める |
| 書き起こしの試走の候補 `TranscriptionTuner.cpuCandidates` | 4/4/4、6/6/6、8/8/4 を翻訳の既定で切る。ならしが首位の4倍を超えたら閉じる |
| 会話中の翻訳 `ConversationViewModel.configureTranslation` | 聞いている間だけ詳細設定の値に替える |
| 言語の識別・PP-OCR・SenseVoice・読み上げ | 2・4・4・4 の固定 |

Xiaomi 15T Pro（MT6991、8コア）で、画面に出ている会話翻訳を測った。

- **許された CPU は4つ**：アプリの作業スレッドは、画面に出ているとき（cpuset `/top-app`）も CPU 4〜7 にしか載れない（`/proc/<pid>/task/*/status` の `Cpus_allowed_list`）。0〜7 に載れるのはメインスレッドと作られた直後のスレッドだけで、作られた直後のスレッドも後で 4〜7 に移される。画面を消すと 0〜3 になる。`Runtime.availableProcessors()` は8を返す。
- **超えると崩れる**：書き起こしの見本の音声1回は、4スレッドで約0.6秒、6で36.6秒、8で39.0秒だった（画面を消した 0〜3 でも 5で36秒）。llama.cpp は演算ごとに全スレッドの終わりを待ち合わせ、待つ間はスピンするので、CPU に載れないスレッドを全員が待つ。0.14.0 の試走は 6 と 8 を4回ずつ試すので、準備に約5分かかった。
- **部品どうしでも崩れる**：会話中、翻訳（4本）と書き起こし（4本）が同じ4つの CPU に載ると、翻訳は 136 から 8.0・3.3・2.2 トークン/秒に落ち、書き起こしは1文に49秒かかった（試験音声を会話翻訳に流した）。

どの部品も自分の数だけを見て決めているので、部品ごとに数を直しても、別の部品と重なれば同じことが起きる。ほかの端末では、許された CPU もコアの構成も違う。

## 決めること

計算の重い処理は、プロセスで1つの割り当て（`ComputeScheduler`）から計算資源を借りてから動く。CPU は「今許された CPU の数」を予算とし、同時に貸すスレッドの合計を予算に収める。GPU は今と同じく1つずつ貸す。部品は借りた数のスレッドで動き、自分で数を決めない。

### 部品と置き場

| 部品 | モジュール | 責務 |
| --- | --- | --- |
| `CpuTopology` | `core-pipeline` | 許された CPU の番号と、各コアの所属グループ・並びの値。グループごとの性能の段と、候補のスレッド数（速い段から足した数）を返す規則を持つ |
| `ComputeScheduler` | `core-pipeline` | 借りる依頼（計算資源・作業の種類・欲しいスレッド数）を受け、予算と優先度で貸す。返却・取り消し・予算の変化を扱う。今の `LlamaRuntime` の GPU の待ち行列と `InferencePolicy.next` をここへ移す |
| 作業の種類 `ComputeWork` | `core-pipeline` | 今の `GpuWork` を改名し、CPU の依頼にも使う。確定の書き起こしを先に、同じ種類は到着順（今の規則のまま） |
| スレッド数の選び方 | `core-pipeline` | 今の `TranscriptionTuner` を一般にし、候補（`CpuTopology` の段から）を測って選ぶ。打ち切りは、本計測のうち2回が首位の最も遅い回より遅く、中央値で負けが決まったら閉じる（定数を持たない。ならしにはスレッド数ごとに違う初回の費用が入るので比べない。15T Pro で、4本のならしが初回の用意で1本より遅かった回と、本計測の1回目がメモリの回収と重なった回に、本計測では速い4本を閉じていた）。結果は CPU の組（許された番号と段の順位）を含むキーで保存する。翻訳と書き起こしが使う |
| 予算を読む部品 | `core-llm-jvm` | Android：呼んだスレッドの `/proc/thread-self/status` の `Cpus_allowed_list` と、cpufreq の `related_cpus`・`cpuinfo_max_freq`。Windows：プロセスのアフィニティと `EfficiencyClass`。借りるたびに読む |
| 借りて動く側 | `core-llm-jvm`・`app`・`desktop` | 翻訳は借りた数を `llama_set_n_threads` で当ててから計算する。書き起こしは、試走で選んだ数か明示設定の数を毎回要求する。貸出数がエンコーダーのスレッド数と異なるときは、旧モデルを解放してから読み直す。ONNX Runtime の部品（言語の識別・SenseVoice・読み上げ）は自分のスレッド数を借りる。文字認識は、スレッド数を指定できない ML Kit を含むので、1回分（並べて動かす認識器すべて）で CPU の予算を全部借り、中は0.14.0と同じく並列に動かす（PP-OCR は4スレッドのまま）。`core-ocr`・`core-tts` は中核に依存しないので、`app` が呼び出しを包んで借りる |

### 貸し方の規則（最初の版）

1. **予算**は、借りるときに読んだ許された CPU の数。予算が減って、貸している合計が予算を超えたら、新しく貸さず、返却を待つ。
2. **llama.cpp の依頼**（翻訳・書き起こし）は、選んだスレッド数を予算で切った数を借りる。予算が空くまで待つ。翻訳は、今の GPU と同じく、ほかの依頼が待っていれば区切り（`TranslationTurn`）で返して並び直す。
3. **ONNX Runtime の依頼**は、決めたスレッド数を借りる。予算より多ければ予算で切って、セッションを作り直す。
4. **借りない処理**：Silero VAD（1スレッド、0.1秒ごとの短い計算）、録音、画面の制御。止まってはいけない処理を推論の待ちに並べない（アーキテクチャ「計算資源の割り当て」）。
5. **GPU の依頼**は今と同じく1つずつ貸し、CPU の予算は使わない。

貸し方は `ComputeScheduler` の中の規則にまとめる。今後、翻訳と書き起こしを分けて同時に動かすなどの割り当てに変えるときは、この規則だけを変え、部品は変えない。

### スレッド数の選び方

- 候補は、許された CPU を性能の段に分け、速い段から足した数。段が1つなら全部の1候補。端末ごとの数は書かない。
- 書き起こしは今の試走（見本の音声）で選ぶ。各段のスレッド数は同じ数にする。
- 翻訳は、読み込み後の準備で、決まった短い文の生成速度を候補ごとに `llama_set_n_threads` で測って選ぶ（読み直さない）。
- 設定の「スレッド数」と詳細設定の「書き起こしのスレッド数」は、指定したときはその1候補にし、予算で切る。
- 会話中に翻訳のスレッド数を替える仕組み（`configureTranslation`、詳細設定の「会話中の翻訳のスレッド数」）は、割り当てが重なりを防ぐので外す。

### 外すもの

`TranslationEngine.threadsFor`・`threadsForWindows`・`DEFAULT_THREADS`、`TranscriptionTuner.cpuCandidates` の 4/6/8 と `WARMUP_RATIO`、`LlamaRuntime` の GPU の待ち行列（`ComputeScheduler` へ移す）、`configureTranslation` と `translateThreads` の設定。

## 第2段：タスクの性質で貸すスケジューラーにする

第1段（上）で、会話中の翻訳は 104〜155 トークン/秒、話し終わりから確定までは 0〜4.9秒に戻った（15T Pro、画面を点けた状態）。残った遅れは、貸し方がタスクの性質を知らないことから来ている。

- 長い発話の途中の書き起こしが4つのコアを7.3秒使い続け、その間、言語の識別が7.3秒待ち、確定の書き起こしも後ろに並んだ。途中の書き起こしは確定が始まれば捨てる結果なのに、取り消されない。
- 1つの依頼が借りられる数を全部借りるので、短い依頼（言語の識別）まで待たされる。
- スレッド数の決め方が、翻訳（`TranslationEngine` の中の試走）、書き起こし（`TranscriptionTuner`）、ONNX Runtime の部品（「最速の段のコア数」。15T Pro では1）、明示設定で別々になっている。

### タスクが申告すること

借りるときに、数だけでなく次を申告する。申告の型は中核（`core-pipeline` の compute パッケージ）に置き、`ComputeResources` の口で渡す。

| 項目 | 中身 |
| --- | --- |
| 優先度の組 | 下の表の4つ。機能に依らない名前にする |
| 止め方 | 取り消してよい（スケジューラーが取り消し、呼び手は取り消された結果として扱う）／区切りで譲れる（今の `TranslationTurn` のように区切りで返して並び直す）／止めない |
| スレッド数の測り方 | 部品の名前と版、見本の入力で1回動かす口。測った「スレッド数と時間の関係」から、渡す数をスケジューラーが決める |
| 数を変える手間 | 軽い（`llama_set_n_threads` で毎回変えられる翻訳）／重い（読み直しが要る Qwen3-ASR のエンコーダー・ONNX Runtime のセッション） |

| 優先度の組（高い順） | 例 |
| --- | --- |
| 確定 | 確定に要る書き起こしと判定（`RecognitionPriority` の urgent）、利用者が頼んだ書き起こし直し |
| 識別 | 話している間の言語の識別（`LANGUAGE`） |
| 翻訳 | 翻訳、文字認識 |
| 途中 | 途中の書き起こし（`PARTIAL`） |

音声認識の今の優先度（`RecognitionPriority`）は、ワーカーの中の順番として残し、プロセスの優先度の組へ対応させる。対応は中核の1か所に置く。

### 貸し方の規則

1. **合計は予算以内**（第1段のまま）。
2. **高い組から貸す**。同じ組は到着順。区切りで譲った依頼は、同じ組の後から来た依頼より先にする。
3. **横取り**：高い組の依頼が待っていて CPU が足りないとき、低い組で走っている依頼に止めるよう求める。取り消してよい依頼は取り消し、区切りで譲れる依頼は次の区切りで返させる。止めない依頼は終わるのを待つ。
4. **渡す数**：測った関係で、一番速い数と時間の差が計測のばらつきに収まる最小の数を渡す（速くならないスレッドは渡さない）。空いている数がそれより少なければ、軽い依頼には空いている数を渡す。重い依頼には決めた数を渡し、空くまで待たせる（毎回読み直さない）。
5. **測る時期**：初めて使うとき（今の準備の試走）に測り、CPU の組を含む鍵で保存する。明示設定は、その数の1候補にする。ML Kit のように数を指定できない部品は、測らずに予算を全部借りる。
6. **低い組の待ち**：低い組は、高い組の依頼が無い間に進む。高い組の依頼は発話や画面の変化があるときにしか来ないので、低い組が止まり続けることはない。時間の定数で優先度を上げる仕組みは入れない（必要が実測で見えたら足す）。

### 新しい依頼で古い結果が要らなくなる処理

途中の書き起こしと同じく、新しい依頼が来ると古い結果が要らなくなる処理を、今の扱いとともに調べて、同じ取り消しの仕組みに載せる。候補（推定）：画面翻訳で見えなくなった文の文字認識と翻訳、カメラ翻訳の古いコマの文字認識、会話の途中の訳。今の仕組み（`RecognitionQueue.dropStale`、`ScreenSession` の `Effect.Cancel`、`TranslationStream` の取り消し）で足りているものは、その対応を設計書に書く。

## 確かめること

- 第2段の単体試験：高い組の依頼が来たら取り消してよい依頼が取り消される、区切りで譲る依頼が区切りで返す、止めない依頼は止まらない、渡す数が規則4どおり、重い依頼の数が揺れない、譲った依頼が同じ組の後続より先。
- 第2段の実機（15T Pro、画面を点けた状態）：試験音声を会話翻訳に流し、話し終わりから確定までの時間、言語の識別の待ち、途中の書き起こしが取り消されるまでの時間を、第1段（確定まで 0〜4.9秒、識別の待ち最大7.3秒）と比べる。
- 単体試験（規則に対する期待で書く。機種の型番に合わせた期待値は書かない）
  - `CpuTopology`：段が1つ・2つ・3つ、許された CPU が一部だけ、所属や並びが読めない構成で、段と候補が規則どおりか。
  - `ComputeScheduler`：合計が予算を超えない、確定の書き起こしが先、予算が減ったときに新しく貸さない、取り消した依頼が並びに残らない、GPU は1つずつ。
  - スレッド数の選び方：遅い候補を閉じる、保存した選択を CPU の組が同じときだけ使う。
- 実機（15T Pro、画面を点けた状態）
  - 入れ直した後の初回の準備時間と2回目の準備時間。
  - 試験音声を会話翻訳に流し、翻訳の速さと書き起こしの時間が、重なっても崩れないか（変更前：翻訳 2.2〜8.0 トークン/秒、書き起こし1文49秒）。
  - ログに、許された CPU・予算・借りた数・待った時間を出す。
- 実機（15T Pro、画面を点けた状態）で画面翻訳とカメラ翻訳も確かめる。翻訳を CPU で動かす端末では、文字認識（ML Kit・PP-OCR）と翻訳が同じ CPU に載るので、会話翻訳と同じ崩れ方が起きうる（推定、変更前は未計測）。ログで文字認識と翻訳の時間、借りるまでに待った時間を見る。
- 実機（REDMAGIC 11 Pro）：画面に出ているときの許された CPU を読み、会話翻訳と画面翻訳が変更前より遅くならないか。

## 0.14.1-beta.1 のリリース前の点検で残したこと

設計のレビュー（`design-reviewer`）で、正式版の前に直すか判断するものとして残した。文字認識の認識器を1つずつ全部借りて順に動かしていた崩れは、1回分でまとめて借りて中を並列に戻す形で直した。

- PP-OCR のスレッド数は0.14.0の4のまま。変えるなら `tools/run-bench.ps1` で前後を比べてから決める。
- 「単独で借りる」を `Int.MAX_VALUE` でも表している（`ComputeScheduler`、`AndroidCpuCompute`）。`ComputeWork.exclusiveCpu` に寄せる。
- 横取りできるかの規則が3か所（`SpeechPipeline` の取り消し、`ComputeScheduler.preempt`、GPU の側）にある。`ComputeWork` の1つの判定に寄せる。
- Qwen3-ASR だけスレッド数の選び方の入口が別（`TranscriptionTuner` が `ThreadBenchmark` を直接呼ぶ）。CPU の組が変わったときの扱いが3通りあり、貸出数が候補より少ない場合の判定が無い。`ComputeResources` の選び方に寄せる。
- 貸出数が変わったら読み直す処理が `ScheduledSpeech`・`QwenAudioSession`・`SupertonicSpeaker` に分かれている（`core-tts` は中核に依存できないので、置き場の判断が要る）。
- `TranslationEngine` と `QwenAudioRecognizer.load` が `ProcessCompute` を直接使う。貸すたびに CPU の組を `/proc` と sysfs から読み直している（時間は未計測）。
- 許された CPU（`Cpus_allowed_list`）の前面・背面・フォアグラウンドサービスでの変わり方と、`related_cpus` での段の分け方を、`featurelab` で確かめて `docs/資料/端末の能力.md` に載せていない。Windows は今のプロセッサグループだけを数える。
- `ThreadBenchmark` が中核の中でファイルを直接読み書きし、静的なキャッシュを持つ。保存はインターフェースで受け取る。
- GPU の試走を CPU の試走の記録に混ぜている（`TranscriptionTuner`）。
- `SpeechPipeline` の取り消しの広がり（`RETRANSCRIBE`・`PHRASE_LANGUAGE`）と、GPU の側の横取りに試験が無い。

## 第3段：使える CPU をプロセスの組で揃え、全体の指標で本数を決める

### 測った事実

- **候補の規則が外れた**：段の境目の合計だけを候補にすると、REDMAGIC 11 Pro では書き起こしの候補が2と8になった。8は極端に遅いので2が選ばれ、長い発話の確定に4〜6秒かかった。手で4本・6本に固定すると、発話1秒あたりの処理は約411msから約267msに縮んだ（約35%速い）。段の境目は、速さの曲線の山の位置と関係が無い。
- **スレッドごとに使える CPU が違う**：15T Pro（HyperOS、MT6991）では、起動から約0.3秒の間、メインスレッドの CPU の指定（affinity）が4〜7番に絞られる。その間に作られたスレッド（約37本。コルーチンの作業スレッド、推論のスレッドなど）は指定を引き継ぎ、ずっと4〜7番のままになる。後から作られたスレッドは0〜7番を使える。どのスレッドも cgroup は `/top-app` で同じなので、Android の組（cpuset）の入れ替えではなく、端末側が起動時にスレッドの指定を絞った名残である。今の予算は「呼んだスレッドの指定」から読むので、スレッドが作られた時期という偶然で4にも8にもなる。
- **部品単体の曲線は全体の中でも使える**：15T Pro で会話翻訳の制御全体を回すと、書き起こし1〜4本の処理時間は、部品単体で測った曲線より3〜12%長いだけだった。
- **全体で見ないと分からないかね合いがある**：書き起こしの本数を増やすと確定は速くなるが、訳が出るまでの待ちの最大は1.0秒（1本）から2.1秒（4本）に延びる。
- **ほかの実装の例**：Android はアプリの重要度で組を入れ替え、組の CPU は機種ごとに違う（Galaxy Z Fold8 は前面0〜5・最前面0〜7、Galaxy S25 は画面を消すと4コア）。ExecuTorch は、Android では組が後から変わるので、作成時の CPU 数でスレッドプールを決めない。特定のコアに固定することは、多くの機種に配るアプリでは勧められていない（Unity）。

### 全体の指標

上から順に優先する。会話翻訳は次の4つ。画面翻訳とカメラ翻訳は「文字を読んでから訳が出るまで」を同じ扱いにする。

1. 話し終えてから、確定した書き起こしが出るまで
2. 言語の識別の待ち
3. 訳が出るまで
4. 途中の書き起こしの更新（ほかに譲ってよい）

### 決めること

1. **使える CPU はプロセスの組で決める**：推論を動かすスレッドは、計算の直前に自分の CPU の指定を「端末の全 CPU」に設定し直す。カーネルはこの指定を、プロセスの組（cpuset）の CPU との重なりに切る。予算は、設定し直した後に読んだ数とする。特定のコアには固定しない。前面と裏の行き来や画面の点灯で組が変わったときは、カーネルが指定を組に収めるので、次に借りたときの予算に表れる。
   - llama.cpp：スレッドプールは読み込みのときに作られ、作ったスレッドの指定を引き継ぐ。プールの作成の前に、作るスレッドの指定を設定し直す。計算を呼ぶスレッドも、計算の前に設定し直す。
   - ONNX Runtime：セッションのスレッドは、作ったスレッドの指定を引き継ぐ。セッションの作成と計算の前に、呼ぶスレッドの指定を設定し直す。
   - ML Kit：内部のスレッドには手が届かない。呼ぶスレッドだけ設定し直す。
   - Windows：今のプロセスのアフィニティのままにし、何もしない。
   - 端末で確かめること（`featurelab`）：アプリのスレッドが自分の指定を広げられるか、広げた結果がプロセスの組の CPU と一致するか、裏へ回したときや画面を消したときに組へ切られるか。結果は `docs/資料/端末の能力.md` に載せる。
2. **速さの曲線は1から予算までの全部の本数から探す**：段の境目の合計は、最初に試す順番にだけ使う。境目で一番速かった本数から両側へ1本ずつ広げる。少ない側は、最速との差がばらつきを超えたら止める。多い側は、最速を更新しなくなったら止める。選ぶ数は今のまま、最速との差がばらつきに収まる最小の数とする。翻訳、書き起こし、ONNX Runtime の部品で同じ探し方を使う。
3. **貸し方は優先度の順と曲線の「効く本数」で全体を決める**：優先度の組を全体の指標の順に対応させる（第2段の組のまま）。重い依頼（書き起こしなど）には、曲線で効く最小の本数だけを渡し、速くならない CPU を抱え込ませない。軽い依頼（翻訳）は、空いている数を効く本数まで使う。書き起こしの本数と訳の待ちのかね合いは、指標の順（確定を先にする）で決まる。部品ごとの本数の組み合わせを全体で探すことはしない。組み合わせが爆発し、試した会話に合わせ込むことになるからである。
4. **初回の試走を画面で見せる**：試走の進み具合を、プロセスで1つの購読できる状態として出す。中身は、試している部品、試した本数ごとの時間、打ち切った本数、選んだ本数。会話翻訳の画面など、試走を待つ画面は、試走が実際に走っている間だけダイアログを出す。本数ごとの時間を棒で並べ、選んだ本数を強調し、打ち切った本数を薄く表示する。保存した結果を使うときは出さない。

### 外すもの

`CpuTopology.candidates` の「段の境目の合計だけを候補にする」規則（試す順番の規則に替える）。呼んだスレッドの指定をそのまま予算にする読み方。

### 確かめること（第3段）

- 単体試験：探し方が、山が1つの曲線で山の本数を選ぶこと、少ない側と多い側の止め方、境目の外に山がある曲線（REDMAGIC の形：2が遅く、4〜6が速く、8が極端に遅い）で4〜6を選ぶこと。試走の進み具合が購読できること。
- `featurelab` で、CPU の指定を広げられることと、組との関係。
- 実機（15T Pro と REDMAGIC 11 Pro、画面を点けた状態）：試験音声を会話翻訳に流し、全体の指標の1〜3を、書き起こしの本数を手で固定したときの一番よい結果と比べる。差がばらつきを超えて悪いときは、動かしながら合わせる仕組み（実行中の待ち時間から本数を直す）を足すことを考える。初回の試走の時間とダイアログの表示も見る。

### 第3段の15T Pro での結果

試験音声を会話翻訳に流した（画面を点けた状態、自動設定）。

| 指標 | 変更前（予算4） | 変更後・2回目（予算8） |
| --- | --- | --- |
| 話し終えてから確定まで（中央／最大） | 0.0秒／1.7秒 | 0.2秒／1.6秒 |
| 書き起こしの処理（発話1秒あたり） | 307ms | 301ms |
| 言語の識別の待ち（最大） | 0秒 | 0.5秒 |
| 訳8件の時間の合計／最大 | 7.1秒／2.2秒 | 6.8秒／1.4秒 |

- 選ばれた本数：書き起こし3（3本 590ms、4本 580ms、5本 594ms、2本と8本は打ち切り）、翻訳3、言語の識別8（4本 243ms、7本 220ms、8本 196ms）。
- 初回の準備（試走を含む）は、書き起こしが58秒だった。2回目は6.6秒。
- 15T Pro は変更前から速い4コアを使えていたので、全体はほぼ同じだった。言語の識別が予算を全部借りるため、確定の書き起こしが識別の終わりを待つ回があった（1回、1.3秒）。識別の数を「効く最小」で選んでも、4本から8本で1.24倍速くなるので8になる。ほかの依頼の待ちを延ばす分を、本数の選び方に入れるかは、REDMAGIC の結果を見て決める。

### 第3段の REDMAGIC 11 Pro での結果（0.14.1-beta.2、作者の会話、Qwen3-ASR）

作者が会話翻訳を約2分半使った記録（画面を点けた状態、自動設定）。

- 選ばれた本数：書き起こし6（CPU。GPU は CPU より十分には速くなかった）、翻訳2（GPU）、言語の識別8（2本 233ms、7本 164ms、8本 155ms）。初回の準備は、書き起こしが64秒だった。
- 確定までの待ち：16件のうち12件が0.6秒以内、最大2.8秒。訳の時間は最大1.9秒。
- 途中の書き起こし（`PARTIAL`、優先度 Speculative、止め方 Cancel）40回のうち34回を、話している間の言語の識別（`LANGUAGE`、優先度 Interactive）が横取りで止めた。識別は0.8秒ほどおきに予算の8本を借り、途中の書き起こしは1回に0.6秒以上かかるので、ほとんど終わらない。話している間に文字がほとんど出ず、書き起こしが遅いと感じる状態になった。
- 確定までの待ちが長かった3件（1.6〜2.8秒）は、長い発話で、話し終えた時点に書き起こしていない音声が10〜13秒残っていたものだった。
- 試走のダイアログは、部品ごとの試走で閉じたそばから出直した（直した）。

言語の識別が予算を全部借りることは、15T Pro では確定の待ち（指標の1）を1回延ばし、REDMAGIC では途中の書き起こし（指標の4）をほぼ止めた。Whisper は ONNX Runtime のセッションを作るときにスレッド数を決めるので、呼ぶたびに空いた数で動かす（`ResizeCost.Cheap`）ことはできない。

### 言語の識別を書き起こしの残りで選んだ後（0.14.1-beta.3 の候補、15T Pro、試験音声）

言語の識別は、書き起こしの4本を残した1〜4本で試走し、4本を選んだ（1本 490ms、3本は打ち切り、4本 233ms）。

| 指標 | 変更前（第3段の直し後） | 1回目（試走あり） | 2回目 |
| --- | --- | --- | --- |
| 話し終えてから確定まで（中央／最大） | 0.1秒／1.9秒 | 0.9秒／1.9秒 | 0.6秒／1.6秒 |
| 途中の書き起こしを止めた回数 | — | 8 | 9 |
| 訳8件の時間の合計 | 7.3秒 | 6.9秒 | 6.5秒 |

- 話している間の識別は毎回4本で、途中の書き起こしと並んで走った。会話の画面の図でも、識別と途中の書き起こしが重なって走り、止めた回数は0のまま進む区間を確かめた。
- 確定までの待ちの中央値は延びた。話し終えた後の文の言語の識別（`PHRASE_LANGUAGE`）も同じ4本のセッションで動くので、0.2秒ほどから0.3〜0.4秒になり、確定の前に並ぶ。Whisper のセッションは本数を変えると作り直すので、確定のときだけ全部借りることはしていない。REDMAGIC での途中の書き起こしの戻りと合わせて、この見返りを判断する。
