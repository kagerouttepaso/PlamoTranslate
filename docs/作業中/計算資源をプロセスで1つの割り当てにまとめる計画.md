# 計算資源をプロセスで1つの割り当てにまとめる計画

## 問題

推論の部品（翻訳・書き起こし・言語の識別・文字認識・読み上げ）は、それぞれが端末の CPU を自分だけで使える前提でスレッド数を決めている。数は、手元の2機種で測った定数から決まる。

| 場所 | 今の決め方 |
| --- | --- |
| 翻訳の既定 `TranslationEngine.threadsFor` | 最高周波数が一番低いコアが半分以下なら残りのコアの数、そうでなければコア数−2。2〜6に収める |
| 書き起こしの試走の候補 `TranscriptionTuner.cpuCandidates` | 4/4/4、6/6/6、8/8/4 を翻訳の既定で切る。ならしが首位の4倍を超えたら閉じる |
| 会話中の翻訳 `ConversationViewModel.configureTranslation` | 聞いている間だけ詳細設定の値に替える |
| 言語の識別・PP-OCR・SenseVoice・読み上げ | 2・4・4・4 の固定 |

Xiaomi 15T Pro（MT6991、8コア）で、画面に出ている会話翻訳を測った。

- **許された CPU は4つ**：アプリの作業スレッドは、画面に出ているとき（cpuset `/top-app`）も CPU 4〜7 にしか載れない（`/proc/<pid>/task/*/status` の `Cpus_allowed_list`）。0〜7 に載れるのはメインスレッドと作られた直後のスレッドだけで、作られた直後のスレッドも後で 4〜7 に移される。画面を消すと 0〜3 になる。`Runtime.availableProcessors()` は8を返す。
- **超えると崩れる**：書き起こしの見本の音声1回は、4スレッドで約0.6秒、6で36.6秒、8で39.0秒だった（画面を消した 0〜3 でも 5で36秒）。llama.cpp は演算ごとに全スレッドの終わりを待ち合わせ、待つ間はスピンするので、CPU に載れないスレッドを全員が待つ。0.14.0 の試走は 6 と 8 を4回ずつ試すので、準備に約5分かかった。
- **部品どうしでも崩れる**：会話中、翻訳（4本）と書き起こし（4本）が同じ4つの CPU に載ると、翻訳は 136 から 8.0・3.3・2.2 トークン/秒に落ち、書き起こしは1文に49秒かかった（試験音声を会話翻訳に流した）。

どの部品も自分の数だけを見て決めているので、部品ごとに数を直しても、別の部品と重なれば同じことが起きる。ほかの端末では、許された CPU もコアの構成も違う。

## 決めること

計算の重い処理は、プロセスで1つの割り当て（`ComputeScheduler`）から計算資源を借りてから動く。CPU は「今許された CPU の数」を予算とし、同時に貸すスレッドの合計を予算に収める。GPU は今と同じく1つずつ貸す。部品は借りた数のスレッドで動き、自分で数を決めない。

### 部品と置き場

| 部品 | モジュール | 責務 |
| --- | --- | --- |
| `CpuTopology` | `core-pipeline` | 許された CPU の番号と、各コアの所属グループ・並びの値。グループごとの性能の段と、候補のスレッド数（速い段から足した数）を返す規則を持つ |
| `ComputeScheduler` | `core-pipeline` | 借りる依頼（計算資源・作業の種類・欲しいスレッド数）を受け、予算と優先度で貸す。返却・取り消し・予算の変化を扱う。今の `LlamaRuntime` の GPU の待ち行列と `InferencePolicy.next` をここへ移す |
| 作業の種類 `ComputeWork` | `core-pipeline` | 今の `GpuWork` を改名し、CPU の依頼にも使う。確定の書き起こしを先に、同じ種類は到着順（今の規則のまま） |
| スレッド数の選び方 | `core-pipeline` | 今の `TranscriptionTuner` を一般にし、候補（`CpuTopology` の段から）を測って選ぶ。打ち切りは、ならしが首位のならしより遅ければ閉じる（定数を持たない）。結果は CPU の組（許された番号と段の順位）を含むキーで保存する。翻訳と書き起こしが使う |
| 予算を読む部品 | `core-llm-jvm` | Android：呼んだスレッドの `/proc/thread-self/status` の `Cpus_allowed_list` と、cpufreq の `related_cpus`・`cpuinfo_max_freq`。Windows：プロセスのアフィニティと `EfficiencyClass`。借りるたびに読む |
| 借りて動く側 | `core-llm-jvm`・`app`・`desktop` | 翻訳は借りた数を `llama_set_n_threads` で当ててから計算する。書き起こしは、試走で選んだ数か明示設定の数を毎回要求する。貸出数がエンコーダーのスレッド数と異なるときは、旧モデルを解放してから読み直す。ONNX Runtime の部品（言語の識別・SenseVoice・PP-OCR・読み上げ）は自分のスレッド数を借りる。スレッド数を指定できない ML Kit は CPU の予算を全部借りる。`core-ocr`・`core-tts` は中核に依存しないので、`app` が呼び出しを包んで借りる |

### 貸し方の規則（最初の版）

1. **予算**は、借りるときに読んだ許された CPU の数。予算が減って、貸している合計が予算を超えたら、新しく貸さず、返却を待つ。
2. **llama.cpp の依頼**（翻訳・書き起こし）は、選んだスレッド数を予算で切った数を借りる。予算が空くまで待つ。翻訳は、今の GPU と同じく、ほかの依頼が待っていれば区切り（`TranslationTurn`）で返して並び直す。
3. **ONNX Runtime の依頼**は、決めたスレッド数を借りる。予算より多ければ予算で切って、セッションを作り直す。
4. **借りない処理**：Silero VAD（1スレッド、0.1秒ごとの短い計算）、録音、画面の制御。止まってはいけない処理を推論の待ちに並べない（アーキテクチャ「計算資源の割り当て」）。
5. **GPU の依頼**は今と同じく1つずつ貸し、CPU の予算は使わない。

貸し方は `ComputeScheduler` の中の規則にまとめる。今後、翻訳と書き起こしを分けて同時に動かすなどの割り当てに変えるときは、この規則だけを変え、部品は変えない。

### スレッド数の選び方

- 候補は、許された CPU を性能の段に分け、速い段から足した数。段が1つなら全部の1候補。端末ごとの数は書かない。
- 書き起こしは今の試走（見本の音声）で選ぶ。各段のスレッド数は同じ数にする。
- 翻訳は、読み込み後の準備で、決まった短い文の生成速度を候補ごとに `llama_set_n_threads` で測って選ぶ（読み直さない）。
- 設定の「スレッド数」と詳細設定の「書き起こしのスレッド数」は、指定したときはその1候補にし、予算で切る。
- 会話中に翻訳のスレッド数を替える仕組み（`configureTranslation`、詳細設定の「会話中の翻訳のスレッド数」）は、割り当てが重なりを防ぐので外す。

### 外すもの

`TranslationEngine.threadsFor`・`threadsForWindows`・`DEFAULT_THREADS`、`TranscriptionTuner.cpuCandidates` の 4/6/8 と `WARMUP_RATIO`、`LlamaRuntime` の GPU の待ち行列（`ComputeScheduler` へ移す）、`configureTranslation` と `translateThreads` の設定。

## 確かめること

- 単体試験（規則に対する期待で書く。機種の型番に合わせた期待値は書かない）
  - `CpuTopology`：段が1つ・2つ・3つ、許された CPU が一部だけ、所属や並びが読めない構成で、段と候補が規則どおりか。
  - `ComputeScheduler`：合計が予算を超えない、確定の書き起こしが先、予算が減ったときに新しく貸さない、取り消した依頼が並びに残らない、GPU は1つずつ。
  - スレッド数の選び方：遅い候補を閉じる、保存した選択を CPU の組が同じときだけ使う。
- 実機（15T Pro、画面を点けた状態）
  - 入れ直した後の初回の準備時間と2回目の準備時間。
  - 試験音声を会話翻訳に流し、翻訳の速さと書き起こしの時間が、重なっても崩れないか（変更前：翻訳 2.2〜8.0 トークン/秒、書き起こし1文49秒）。
  - ログに、許された CPU・予算・借りた数・待った時間を出す。
- 実機（15T Pro、画面を点けた状態）で画面翻訳とカメラ翻訳も確かめる。翻訳を CPU で動かす端末では、文字認識（ML Kit・PP-OCR）と翻訳が同じ CPU に載るので、会話翻訳と同じ崩れ方が起きうる（推定、変更前は未計測）。ログで文字認識と翻訳の時間、借りるまでに待った時間を見る。
- 実機（REDMAGIC 11 Pro）：画面に出ているときの許された CPU を読み、会話翻訳と画面翻訳が変更前より遅くならないか。
