# 韓国語の認識器を足し、文字認識の部品を分ける

作者の合意を取るための計画。`core-ocr` の中の部品の分け方と、行を選ぶ処理の入力の形を変える。外から使う契約（`OcrEngine`・`MultiScriptOcr`・`OcrBlock`）は変えない。

## 望む状態

- 韓国語を指定したとき、トリッカルのメニューやロゴのような飾り文字を読める（作者の要望）。
- 認識器を1つ足すときに、足す部品と選び方の規則だけを書けばよく、ほかの部品の引数や分岐を書き換えなくて済む。
- 「行ごとにどの読みを採るか」の判断を、端末なしの単体テストで確かめられる。

## PCで確かめたこと

トリッカルのスクリーンショット1枚（作者の提供）で、検出に今の漫画用OCRの検出、認識に `korean_PP-OCRv5_mobile_rec` を使った（`tools/ocr-spike.py` と同じ前処理）。

| 文字 | 今（ML Kit 韓国語） | 韓国語の認識器（確信度） |
| --- | --- | --- |
| 업적 | 読めない | 업적（1.00） |
| 전투 | 전}（訳は「前}」） | 전투（1.00） |
| 모집 | 一部だけ（訳は「-モ」） | 모집（1.00） |
| 두두랑 노는 거두! | 1行目だけ | 두두랑노는（1.00）・거두!（0.89） |
| ロゴ「공룡 대침공! 대폭망의 도시!」 | 読めない | 공룡대공（0.92）・대폭망의도시!（0.93） |
| 이세계픽셀・상점・스토리・이벤트 가이드 | 読める | 読める（0.97〜1.00） |

- 外れは、画素画の飾り（確信度0.16）と、ロゴの「침」の抜けだけ。確信度0.8で切ると、外れの行は落ち、読めた行は残る。
- 弱いところ：字の間の空白が抜けることがある（「두두랑노는」）。ML Kit は空白を保つ。
- モデル：公式の重み（Paddle 形式）を PC で ONNX に変換したものと、Hugging Face の `mxaln/docscanner-ocr`（Apache-2.0、公式から変換したもの）の `korean/rec_model.onnx` は、出力が一致した（差は最大1e-6）。後者をコミットと SHA-256 で固定して取る（13.4MB と文字の表83KB）。自前でファイルを公開しなくて済む。

## 今の構造の問題

1. **漫画用OCRが検出と認識を1つのクラスに持つ**（`MangaOcr`）。韓国語の認識器は同じ検出を使いたいが、検出だけを取り出せない。
2. **認識器を足すたびに、3か所の形が変わる**：
   - `Recognizers` が認識器ごとの真偽の欄を持つ。
   - `MultiScriptOcr.read` が認識器ごとに `async` を書く。
   - `BlockMerger.merge` が認識器ごとの引数（`ja`・`ko`・`zh`・`manga`・`latin`）を持つ。
3. **認識器の知識が選び方に漏れている**：漫画用OCRが中国語・日本語しか読めないこと、確信度0.8で採ることが `BlockMerger` に書かれ、`LineGroup.pick` の規則にも `Source.KO` などの名前が直接出てくる。
4. **行の選び方が Android の型に依存し、単体テストが無い**：`LineGroup.pick` は `android.graphics.Rect` を持つ型の中にあり、JVM の試験で動かせない。

## 直した後の構造

```
MultiScriptOcr（言語 → 読み手の組 → 並列に読む → 選ぶ → 束ねる）
 ├ 読み手 LineReader：画像 → 読み手ごとの行の候補（Source つき）
 │   ├ ML Kit の読み手（中国語・日本語・韓国語・英字。1つのクラスを4つ作る）
 │   └ PaddleReader：検出1回 → 行ごとに認識器を当てる
 │        ├ PaddleDetector（DB の検出）
 │        └ PaddleRecognizer（CTC の認識・文字の表）× 漫画用・韓国語
 ├ 選び方 LineChoice（Android に依存しない。行の各版の文字と確信度から1つ選ぶ）
 └ まとめ方 BlockMerger（位置で突き合わせ、LineChoice に選ばせ、束ねる）
```

- `Recognizers` は言語ごとの「使う読み手（Source）の集合」にする。韓国語を指定したら、ML Kit 韓国語と、Paddle の検出＋韓国語の認識。
- `BlockMerger.merge` は `Map<Source, List<Candidate>>` を受ける。`Candidate` に確信度（ML Kit は null）を持たせる。
- 読み手は「1行ずつの読み取り結果」と「自分が読める文字種」を返す共通の形にそろえ、認識器の知識（読める文字種・採る確信度）は読み手の側に置く。
- 採る規則は、文字種ごとの優先順の表にする（例：ハングルの行は「PP-OCR 韓国語 → ML Kit 韓国語」）。構造の直しのコミットでは今の規則を表に移すだけで、結果は変えない（単体テストで前後が同じことを確かめる）。
- 認識器を登録するプラグインのような汎用の仕組みは作らない（先回りして作らない）。
- `MangaOcr` は消し、`PaddleReader` の組み合わせで表す（漫画用＝検出＋漫画用の認識）。
- 韓国語の版の選び方：韓国語の認識器の確信度が0.8以上なら採る。ただし、空白を除くと ML Kit の読みと同じなら、空白を保つ ML Kit を採る。確信度が0.8未満なら ML Kit。韓国語の認識器だけが読めた行（업적）は、確信度0.8以上なら足す。

## 範囲

- 使うのは、原文の言語を「韓国語」にしたときだけ（トリッカルでの作者の使い方）。「自動」に入れると中国語・日本語の行の選び方に効くが、手元に中国語・日本語の評価用の画像が無く前後を比べられないので、評価の画像がそろってから広げる（バックログに置く）。
- カメラ翻訳は今のまま（漫画用OCRも使っていない）。
- 動く画面のモードの白縁の読み比べ（最小値の画像）には、漫画用と同じく Paddle を使わない（速さのため）。

## 移す順番（コミットごと）

1. **構造の直し**（振る舞いは変えない）：Paddle の検出と認識を分ける、読み手と Source の集合、`merge` の入力の形、`LineChoice` を取り出して単体テストを書く。今の選び方を試験で固定してから移す。
2. **機能**：韓国語の認識器、モデルの取得（初回にそろえる組に足す。0.7.0から上げた端末では、起動時に13.5MBを取る）、韓国語の版の選び方とその試験、`tools/ocr-spike.py` に韓国語の認識器を足す。
3. **確かめる**：PC の試験の再現、端末でトリッカルの画像を読ませる（`BenchActivity` に画像を送る。速さもここで測る）、`design-reviewer`。
4. **文書**：設計書（画面翻訳「文字認識」・アーキテクチャの採用技術）、判断の記録、現在地の固定した版。

## 決めてほしいこと

- この構造と順番で進めてよいか。
- 韓国語の認識器を初回にそろえる組に入れてよいか（13.5MB。0.7.0から上げた端末は起動時に取る）。代わりは、原文の言語を韓国語にしたときに取る形（取る仕組みは読み上げのモデルと同じ）。
