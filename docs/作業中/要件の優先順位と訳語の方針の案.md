# 要件の優先順位と訳語の方針の案

`docs/要件.md` に足す案。要件の変更なので、作者の確認を取ってから要件へ移し、この文書を消す（`CLAUDE.md`「確認を取ること」）。

## 足す節：機能ごとの優先順位（`## 共通の前提` の後に置く）

0.11.0（会話翻訳の音声認識モデルの選択と話し手の判定の作り直し）を土台に整理した。会話翻訳の並びは、0.11.0で作者が決めたこと（取り違えないために確定を待つ）から導いた。

要件どうしがぶつかったときの優先順位を、機能ごとに決める。機能によって、使う場面と、いちばん困る失敗が違うためである。下の項目のために上の項目を損なう変更は、作者の判断なしに入れない。

どの機能でも最上位は「外へ出さない」（訳す文字・画像・声を端末の外へ送らず、正式版のログに原文・訳・話した言葉を書かない）。端末の中だけで動くことがこのアプリの前提で、どの機能も他人の声・他人とのやり取り・その場の映像を扱うためである。以下は、その次からの並び。

### 会話翻訳

- 場面：旅先などで、言葉の通じない相手と、端末を2人の間に置いて話す（対面の表示）。手は空かず、画面は話の合間に見る。0.11.0から、設定で選ぶ音声認識モデルによって21言語の相手とも話せる（重いモデルは認識に0.6〜1.5秒かかる）。
- 解決したいこと：相手の話を、話の流れを止めずに分かり、こちらの話を伝える。
- いちばん困る失敗：話し手か言語を取り違え、相手の発言を自分の発言として、または逆向きに訳すこと。会話そのものが食い違い、利用者は気づきにくい。次に、訳が出ずに会話が途切れること。次に、カードが細切れで読めないこと。
- 根拠（0.11.0の作者の判断）：相手の言語が分かるまでは自分の発話を原文だけで出し、決まってからさかのぼって訳す。短い返事や割り込みの交代は取りにいかず、交代の確定は1〜2秒遅れてよい（`docs/判断/2026-11-15_会話の話し手は区間の時系列から決め取りにいく交代と諦める交代を分ける.md`・`docs/判断/2026-11-15_相手不明の間は相手の言語が確かなときだけ名指しする.md`）。自動で決まった相手の言語は画面に出し、誤りは利用者が選び直す。
- 優先順位：
  1. **話し手と言語を取り違えない**：確かでないときは決めずに待ち、決めた相手の言語を画面に出して、利用者が直せるようにする。
  2. **会話を途切れさせない**：話している最中から途中の文字と途中訳を出し続ける。
  3. **読める区切り**：1枚のカードは話した人の1〜2文で、文の途中で切らず、断片を作らない。
  4. **確定訳の速さ**：交代や話し終わりの確定は1〜2秒遅れてよい。
- 拡張版との違い：誤訳の中身が「話し手と訳す向きの取り違え」で、これが速さより上に来る。会話は二人のやり取りで、向きを誤ると会話が食い違うため。速さは途中訳で保ち、確定の遅れは受け入れる二段の作りにしている。

### 画面翻訳

- 場面：自分の端末で、ほかのアプリ（漫画・Discord などのSNS・ゲーム）を使いながら、その上に訳を重ねて読む。読みながらスクロール・タップ・台詞送りを続ける。
- 解決したいこと：外国語のコンテンツを、アプリの使い方を変えずに読み進める。
- いちばん困る失敗：訳の表示が下のアプリの操作を妨げること（`docs/判断/2026-11-12_訳の枠は触れた操作を奥のアプリへ通す.md`）。次に、画面が変わった後に古い訳や別の場所の訳が残り、今の原文の訳に見えること。誤訳の実害は小さい（娯楽とやり取りが中心）が、他人のメッセージを読み違えると返事を誤る。
- 優先順位：
  1. **下のアプリの操作を妨げない**：訳の枠は触れた操作を下へ通し、触れたら途中の処理を取り消す。
  2. **古い訳・別の場所の訳を出さない**：画面が変わったら訳を消す。別の吹き出し・メッセージの訳を付けない。
  3. **原文の位置と範囲に収める**：訳は原文の位置・向き・吹き出しやメッセージの範囲に描き、縦書きは縦書きで描く。
  4. **読みやすい訳語**：下の「訳語の方針」。
  5. **速さ**：「性能の目標」の値。見ている部分から先に訳す。
- 拡張版との違い：「操作を妨げない」が最上位の次に来る。ほかのアプリの上に重ねて表示するので、表示がアプリそのものを使えなくするおそれがあるため。

### カメラ翻訳

- 場面：旅先で、看板・メニュー・商品のラベルにカメラを向け、その場で読む。手は端末を持ち、端末は揺れる。
- 解決したいこと：その場で意味を知り、何を注文するか、どちらへ行くか、何を買うかを決める。
- いちばん困る失敗：読み違えた原文の訳を正しい訳として見せること（メニューの食材、薬や食品のラベルでは実害につながる）。次に、訳がちらついて読めないこと。
- 優先順位（今の設計は安定性・精度・速さ・電池の順：`docs/設計/カメラ翻訳.md` の冒頭）：
  1. **読み違えた原文を訳さない**：読み取りがそろった行だけを訳す。
  2. **表示の安定**：枠と段落の区切りがちらつかず、同じ文の訳が出たり消えたりしない。
  3. **速さ**：見ている文から待たされずに訳がそろう。
  4. **電池**。
- 拡張版との違い：レイアウトより「読み取りの正確さ」と「ちらつかない」が重い。原文が映像の文字で、読み取りの誤りがそのまま誤訳になるため。

### テキスト翻訳

- 場面：文を入力するか貼り付けて、内容を確かめながら訳す。急いでいない。
- 解決したいこと：文の意味を正しく知る。
- いちばん困る失敗：誤訳。
- 優先順位：1. 誤訳しない、2. 読みやすい訳語、3. 速さ。レイアウトの項目は無い。
- 拡張版との違い：ほぼ同じ。ページの構造を保つ項目が無い。

### 作者に決めてもらうこと

- **会話翻訳で、話せる言語の広さと速さのどちらを既定にするか**：取り違えを避けて確定を待つことは、0.11.0で作者が決めた（上の根拠）。残るのは音声認識モデルの既定である。
  - 案A（今の作り）：既定は軽いモデル（SenseVoice。日・韓・英・中・広東語）。認識は0.2秒以内で、途中の文字と途中訳がすぐ出る。ほかの言語の相手と話すときは、利用者が設定で重いモデルに替える。
  - 案B：既定を重いモデル（Qwen3-ASR。21言語）にする。どの相手とも設定を替えずに話せるが、認識に0.6〜1.5秒かかり、途中の文字と途中訳が遅れ、メモリも約1.1GB増える。
- **カメラ翻訳で、表示の安定と読み取りの正確さの順**：今の設計は安定を先に書いている。実害の大きさからは正確さを先にする案を上に書いた。どちらも、そろった行だけを訳す今の作りで両立しているので、ぶつかるのは「そろうのを待つ時間を延ばすか」を決めるときだけ。
- **画面翻訳の速さの目標**：一般の画面で2秒以内の目標に対し、キャッシュが無い画面は今も数秒かかる（`docs/設計/画面翻訳.md`「性能の目安」）。目標を場面ごとの体験（台詞送りに追いつく、など）で決め直すか、今の目標のままにするか。

## 足す節：訳語の方針（`## 機能ごとの優先順位` の後に置く）

- 文章・吹き出し・会話は、文脈に合った自然な日本語にする。会話翻訳は話し言葉で訳す。
- 製品名・ボタン名・モデル名のような短い英字の項目は、モデルが原文のまま返したものを受け入れる（`docs/設計/翻訳コア.md`「生成の点検」）。
- 画面の文言・README・プライバシーポリシーは、技術者でない利用者に通じる一般的な名称で書く（`docs/設計/アーキテクチャ.md`「書き方の決まり」）。

## 直す古い項目（今の作りと食い違う）

- 画面翻訳「フローティングボタンを押したときだけ画面を1枚撮って翻訳する。常時キャプチャはしない」：今は、画面が止まったら自動で訳す（約200msごとに縮めた画面を監視する）モードと、動く画面のモードがある。案：「フローティングボタンを押したとき、または自動で訳す設定では画面が落ち着いたときに撮って訳す」。
- 画面翻訳「タップで原文と切り替えられる」：今は、訳の枠に触れた操作を下のアプリへ通すので、タップでは切り替えない。案：この文を消し、「訳の消え方（次の操作で消す・触れるまで残す）を場面で選べる」にする。
- 日付・作者の要望の引用・判断の理由（「2026-11-05作者決定」など）：要件から外し、判断の記録を示す（`docs/README.md`「今の姿を書く文書の書き方」と同じ扱い）。
