# 文書の方針

`docs/` は、会話の経緯を知らない次の担当者（作者と、別のPCで作業を続けるAI）が、アプリの今の姿をつかみ、同じ失敗を繰り返さずに作業を続けるための文書である。文書の価値は量ではなく、読んだ人の判断と作業を正しく支えるかで決まる。そのために、文書を役割で分けて置き場と更新のしかたを固定し、出来事は一般化してから文書に反映し、区切りごとに検査する。

## 置き場と役割

文書の役割は置き場で決まる。役割ごとに、書き換えるか、足すか、畳んで消すかが決まっている。

| 置き場 | 役割 | 更新のしかた |
| --- | --- | --- |
| `README.md`（この文書） | 文書の方針と索引 | 方針を変えたときに書き換える |
| `現在地.md` | 今どこまで動き、次に何をするか。100行以内 | 区切りごとに全体を書き換える |
| `バックログ.md` | 次にやり得ること、決まっていないこと | 済んだ項目を消す |
| `要件.md` | 何を作るか | 作者の確認を取って書き換える |
| `設計/` | 今の姿：全体の組み立てと、各機能がどう動き、なぜその形か | 書き換える |
| `手順/` | ビルド・端末・リリースの手順 | 書き換える |
| `資料/` | 確かめた事実（端末とOSの振る舞い）と外部の資料 | 確かめ直したら書き換える |
| `判断/` | なぜ今の形になったか。1件1ファイル | 足すだけ |
| `作業中/` | 計画・調査など、作業の単位の文書 | 作業が終わったら畳んで消す |

作業の規則はリポジトリ直下の `CLAUDE.md` に置く。完了した作業の一覧はGitの履歴とGitHubのリリースのノートを正本とし、`docs/` には置かない。開発日誌はリポジトリの外に置く（置き場は各自の環境の指示に従う）。

読む順番：`現在地.md` → `要件.md` → `設計/アーキテクチャ.md` → 触る機能の `設計/` → 必要に応じて `資料/`・`判断/`。

| 文書 | 答える問い |
| --- | --- |
| `設計/アーキテクチャ.md` | 設計の幹、層とモジュールと依存の向き、採用している技術、データの置き場 |
| `設計/翻訳コア.md` | 翻訳の契約 `TranslationStream` とエンジン（llama.cpp、プロンプト、モデル、性能） |
| `設計/会話翻訳.md`・`設計/画面翻訳.md`・`設計/カメラ翻訳.md` | その機能が今どう動き、なぜその形か |
| `手順/開発環境.md` | PCと端末の準備、ビルド、モデルの配置、リリース、片付け |
| `資料/端末の能力.md` | 端末とOSで何が届き、何が撮れるか（`featurelab` で確かめた事実） |
| `資料/参考資料.md` | 外部の資料の場所 |

## 出来事を文書に反映する流れ

不具合や作者の指摘を受けたら、出来事をそのまま書かず、次の順で反映する。

1. **構造**：何が起きたかではなく、どの構造から起きたかを特定する（例：戻る操作が止まらなかった → 端末に届く合図を確かめずに画素の推測で設計した／制御が十数個の変数に散っていた）。
2. **一般化**：同じ構造から起きる別の失敗も防ぐ形にする。作業の進め方なら `CLAUDE.md` の規則に、作りなら `設計/` の原則か差し込み口に、振る舞いなら試験に置く（例：「端末の能力は先に確かめる」「制御は状態遷移の1か所に集める」）。
3. **現在の姿**：直した結果の構造を `設計/` に書く。出来事の経緯は書かない。
4. **判断の記録**：上の3つを `判断/` に1件だけ残す。

出来事の話が設計書に入ったら、2の一般化が済んでいない合図である。

## 1つの事実は1か所

1つの事実は1か所にだけ書く。ほかの文書からは場所を示し、書き写さない。

- 機能をまたぐもの（設計の幹、層と依存の向き、翻訳の契約）は `設計/アーキテクチャ.md` と `設計/翻訳コア.md` に置く。機能に固有のものは、その機能の文書に置く。
- 定数の値の一覧やクラスのメンバーは、コードを正本にする。文書には、その意味と判断に効く値だけを、コードの場所と一緒に書く。
- 値を決めた計測（候補の比較、しきい値の根拠）は `判断/` に置く。今の性能の目安（速さ、メモリ）は、その機能の文書の「性能の目安」の節の1か所に、測った条件（端末・モデル・測った日）と一緒に置く。
- 未確認のことは `バックログ.md` に項目として置く。設計書には「未確認」と書き、その項目を示す。

## 今の姿を書く文書の書き方

`設計/`・`手順/`・`資料/` と `現在地.md` は、現在形で今の姿を書く。

- 経緯（「以前は」「〜に変えた」、日付、作者の指示の引用、試したことの列挙）を書かない。今の形が成り立つ理由は1〜2文で書き、詳しい経緯は判断の記録を示す。
- 段落ごとに次の3つを確かめ、どれかが「いいえ」なら書かない。
  1. この文書の問いに答えるか
  2. 読者はまだ知らないか（読者はAndroid・Kotlin・llama.cppを知る開発者。基本は説明しない）
  3. 消すと、読者の判断や作業が変わるか
- 段落の先頭に要点を置く。並ぶものは箇条書き、比べるものは表、手順は番号付き、部品の関係や流れはMermaidにする。

## 判断の記録の書き方

判断の記録は `判断/YYYY-MM-DD_題.md` に1件1ファイルで置く。題は決めたことを短く書く。記録するのは、今の形を縛る判断と、同じ案を試し直す無駄を防ぐ判断だけである。

```markdown
# 決めたこと（題と同じ）

- 状態：有効
- 問題：決める必要があった事情。不具合や指摘から来た判断なら、どの構造から起きたか
- 決めたこと：
- 理由：根拠になった計測の数値や確かめた事実
- 捨てた案：（あれば、捨てた理由と一緒に）
- 再発を防ぐもの：一般化した規則・設計・試験と、その置き場。方式の選択のように防ぐ失敗が無い判断は「なし（選択）」
```

- 1件は30行以内を目安にする。計測の表が要るときだけ、ファイルの中に置く。
- 同じ判断を2つのファイルに書かない。同じ問題への判断が後から増えたら、新しいファイルを足し、古いファイルを「置き換え」にする。
- 本文は後から直さない。後の判断で覆ったら、古いファイルの「状態」を「置き換え（→ 新しいファイルへのリンク）」に変える。
- 設計書から引くときは、ファイルへのリンクで示す。

## 区切りでの更新と検査

作業の区切りごとに、次の順で直す。

1. 出来事や設計の変更があれば、「出来事を文書に反映する流れ」で `設計/` と `判断/` を直す。
2. `作業中/` の文書のうち作業が終わったものを、`設計/`・`判断/`・`バックログ.md` へ畳んで消す。
3. `現在地.md` を書き換え、`バックログ.md` の済んだ項目を消す。
4. 版を固定したライブラリを変えたら、`現在地.md`「固定した版」と `設計/アーキテクチャ.md`「採用している技術」を直す。
5. `tools/check-docs.ps1` を回し、出たものを直す。参照先の文書や節が無い、現在地が長すぎる、今の姿の文書に日付がある、`作業中/` に残りがある、判断の記録の書式が欠けている、を見つける。
6. 構成を大きく変えた文書は、経緯を知らない別の担当（別のAI）に読ませ、止まった箇所を直す。

## この方針が防ぐもの

各規則は、次の失敗の構造を防ぐためにある。規則を変えるときは、この対応が崩れないかを確かめる。

| 失敗の構造 | 防ぐ規則 |
| --- | --- |
| 作業の単位で作った文書（計画・候補・試験の記録）が、作業の後も主題の文書と並んで残り、同じ主題が2か所に分かれる | `作業中/` に置き、終わったら畳んで消す |
| 更新の操作が「書き足す」しかなく、今の事実が経緯に埋もれる | 置き場ごとに更新のしかたを決め、時系列は `判断/` の1件1ファイルだけにする |
| 書き手が自分の作業の経過を書き、次の読者が要るものが見えない | 今の姿は現在形で書き、出来事は一般化してから反映する |
| 同じ事実を複数の文書に書き、片方だけ直されて食い違う | 1つの事実は1か所 |
| 古い参照や実在しない名前が残っても気づかない | 区切りごとの機械の検査と、別の担当の通読 |
