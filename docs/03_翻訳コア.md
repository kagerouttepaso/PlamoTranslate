# 翻訳コア

更新日：2026-11-06

## 方針

llama.cppをgit submoduleで取り込み、Gradleの `externalNativeBuild`（CMake）で一緒にビルドする。JNIで薄いラッパーを作り、プロンプトはチャットテンプレートを使わずPFML3形式で直接組み立てる。モデル公式の説明でも、アプリへの組み込みではPFML3を直接組み立てて渡す方法が推奨されている。

llama.cppのリポジトリにある `examples/llama.android` が、JNIとGradleの構成の参考になる。llama.cppは自前でビルドし、plamo3に対応した版を固定して使う。既存のKotlinラッパーライブラリは同梱するllama.cppが古いとplamo3を読めないためである。

## ビルド設定

| 項目 | 値 |
| --- | --- |
| ABI | `arm64-v8a` のみ |
| 最初の構成 | CPUバックエンド、`GGML_CPU_KLEIDIAI=ON`（Arm向けの最適化カーネル） |
| 現在の構成（2026-11-05〜） | `GGML_OPENCL=ON` で全層をAdreno GPUに載せる（`n_gpu_layers=99`）。OpenCL-Headersと、リンク用のOpenCL-ICD-Loaderをsubmoduleで用意し、実行時は端末の `libOpenCL.so` を `uses-native-library` で使う。REDMAGICはCPUクロックが端末側で抑えられるため、GPUのほうが安定して速い |
| 配布用の構成（2026-11-06〜） | 共有ライブラリにし、計算部分を実行時に読み込む（`BUILD_SHARED_LIBS=ON`、`GGML_BACKEND_DL=ON`、`GGML_CPU_ALL_VARIANTS=ON`、`c++_shared`）。Qualcommの端末はGPU（全層）、それ以外の端末とGPUで読み込めなかったときはCPUだけ（`n_gpu_layers=0`、GPUのデバイスを使わない）。CPUのスレッド数は「コア数−2」（2〜6）。詳しくは `docs/02_アーキテクチャ.md`「GPUとCPUの切り替え」 |
| 後回し | Hexagon NPUバックエンド。Hexagon SDKが必要で準備が重いため、GPUで目標に届かない場合だけ検討する |
| 量子化 | Q4_K_M。Q4_0とGPU・CPUで比べたが、GPUでは同程度だったため変えない（2026-11-05） |

## JNIの関数

```kotlin
internal object LlamaNative {
    // 計算部分のライブラリを nativeLibraryDir から読み込む。最初の1回だけ有効。GPUが使えるかを返す
    // cpuVariant が空でなければ、そのファイル名のCPUの版だけを候補にする
    external fun nativeInit(nativeLibDir: String, loadGpu: Boolean, cpuVariant: String): Boolean
    external fun nativeCpuBackend(): String  // 読み込んだCPUの版のファイル名
    // poll・useThreadPool・useMmap・boost は「パフォーマンスの設定」の値。失敗なら0
    external fun nativeLoad(path: String, nCtx: Int, nThreads: Int, nGpuLayers: Int,
                            poll: Int, useThreadPool: Boolean, useMmap: Boolean, boost: Boolean): Long
    external fun nativeFree(handle: Long)
    // callback は1トークン分のUTF-8ごとに呼ばれ、false を返すと生成を止める。
    // 戻り値は生成トークン数、または負のエラーコード（-1 トークン化失敗、-2 長すぎる、-3 推論失敗）
    external fun nativeTranslate(handle: Long, prompt: String, maxTokens: Int, callback: TokenCallback): Int
    external fun nativeConfigure(handle: Long, boost: Boolean, nThreads: Int)  // 計測用
}
```

呼び出しは `TranslationEngine` が1本の専用スレッド（`PlamoInference`）に寄せる。llama.cppのコンテキストは同時に使えないためと、性能ヒントの対象スレッドを固定するためである。設定はコンテキスト4096（2026-11-12に2048から上げた。「複数の文を同時に訳す」）、流れ（シーケンス）8本、スレッドは大きいコアの数か「コア数−2」（2〜6。REDMAGICは6、15T Proは4。「パフォーマンスの設定」）、GPU層は、GPUを使う端末では99（全層）、使わない端末では0。`TranslationEngine.load` は、GPUで読み込めなければCPUでやり直し、どちらで動いているかを `usesGpu` で返す。GPUで読み込む途中でプロセスごと終わったときは、次の起動でCPUに切り替える（「GPUで落ちたときの切り替え」）。

実装上の要点は次のとおり。

- **トークン化**：`llama_tokenize` を `add_special = true`、`parse_special = true` で呼ぶ。`parse_special` を有効にしないと、`<|plamo:tag|>` などの区切りが特殊トークンとして扱われない。先頭のBOSはllama.cppが自動で付けるので、プロンプトに書かない。
- **サンプリング**：貪欲法（温度0）。
- **停止**：`<|plamo:tag|>` または `<|plamo:bos|>` が出たら止める。どちらも出力に含めない。
- **取り消し**：トークンごとに、収集側のコルーチンが生きているかを確認し、取り消されていたら生成を止める。
- **コンテキスト長**：4096トークン（2026-11-12まで2048）。KVキャッシュは全部の流れで1つを分け合う（`kv_unified = true`）ので、1文だけを訳すときは全部を1文に使える。プロンプトは1回のdecodeで処理する（`n_batch = n_ctx`）。KVキャッシュのメモリは2048のときの約2倍になる。
- **初回の準備**：GPUは初回の推論でカーネルを準備するため約4秒かかる。モデルを読んだ直後に短い文を1回訳しておく（`EngineHolder.warmUp`）。カーネルのコンパイル結果はアプリのキャッシュ `cl-cache/` に残す。
- **KVキャッシュの再利用**：会話の途中訳は先頭（`dataset` と `context`）が毎回同じなので、途中訳が遅いと感じたら `llama_memory_seq_rm` を使った先頭部分の再利用を試す。

## GPUで落ちたときの切り替え

GPU（OpenCL）での読み込み中にアプリが終わったら、次の起動からその端末ではCPUで動かす（`GpuGuard`、2026-11-09）。

- **起きたこと**：同僚のROG Phone（Snapdragon 8 Gen 3、Adreno 750）で、翻訳モデルの読み込みのたびにアプリが再起動を繰り返した。llama.cppのOpenCLの部分は、カーネルの組み立てに失敗すると `exit(1)` でプロセスごと終わる（`ggml-opencl.cpp` の `build_program_from_source_ex` など）。失敗が戻り値で返らないので、`TranslationEngine.load` のCPUでのやり直しが働かない。Androidがアプリを開き直すたびに、同じ所で終わる。Adreno 750はllama.cppでは手元のAdreno 840（A8X）と別の世代（A7X）として扱われ、通るカーネルの組み合わせも違う。報告の端末のログはまだ見ていないので、`exit(1)` が原因というのは推定である。
- **仕組み**：GPUで読み込む直前に「読み込み中」の印（プロセスID）を `TranslationPreferences` へすぐに書き（`commit`）、読み込みと初回の推論（`warmUp`）が済んだら消す。次の起動で印が残っていれば、前回はGPUの読み込み中に終わっている。Androidが記録した前回の終わり方（`ApplicationExitInfo`）が異常終了（クラッシュ、応答なし、`exit` の終了コードが0以外、SIGKILL以外のシグナル）ならすぐCPUに切り替える。強制停止やメモリ不足など、異常終了とは言えない終わり方でも、2回続けば切り替える。1回の強制停止だけでGPUを外さないためである。
- **戻し方**：アプリの版か端末のビルド（`Build.FINGERPRINT`。GPUのドライバーの更新を含む）が変わったら、もう一度GPUを試す。設定の「パフォーマンス」に切り替えた理由と日時を出し、「GPUをもう一度試す」で戻せる。計算部分のライブラリは起動ごとに1回だけ読み込むので、押すとアプリを起動し直す。自分で起動し直すとき（`restartApp`）は印を消し、GPUで落ちたとはみなさない。
- **確かめたこと**：REDMAGIC 11 Proで、読み込み中の強制停止を2回続けると、3回目の起動でOpenCLを読み込まずCPUで読み込むこと、設定の画面に理由が出て、「GPUをもう一度試す」でGPUに戻ることを確かめた。`exit(1)` を異常終了と判定することは単体テスト（`GpuGuardTest`）で確かめた。手元の端末では `exit(1)` を起こせない。
- **範囲**：印を置くのは、読み込みから初回の推論までの間である。読み込みが済んだ後の翻訳の途中でGPUが落ちたときは、この仕組みでは切り替わらない。起きたら、印を置く範囲を翻訳まで広げるか、落ちた回数で切り替える。

## PFML3プロンプト

`Pfml3PromptBuilder` は次の順で要素を並べる。改行は入れない。

1. `<|plamo:tag|>dataset<|plamo:msg|>translation`（必須、常に `translation`）
2. `context`（任意）：周辺の文章や状況の説明
3. 履歴の `input` / `output` の組（任意、古い順）
4. `glossary`（任意）：用語の対訳
5. 今回の `input`
6. 空の本文で終わる `output`（訳先の言語を指定する）

```text
<|plamo:tag|>dataset<|plamo:msg|>translation
<|plamo:tag|>context<|plamo:msg|>韓国の取引先との打ち合わせ。
<|plamo:tag|>input<|plamo:key|>lang<|plamo:val|>ko<|plamo:msg|>내일 몇 시에 만날까요?
<|plamo:tag|>output<|plamo:key|>lang<|plamo:val|>ja<|plamo:msg|>
```

上の例は読みやすさのために改行しているが、実際のプロンプトは1行につなげる。

| 属性 | 書く場所 | 値 |
| --- | --- | --- |
| `lang` | `output`（必須）、`input`（任意） | 言語コード。日本語 `ja`、英語 `en`、韓国語 `ko`、簡体字 `zh-hans`、繁体字 `zh-hant` など53言語（モデルカード「Supported Languages」）。アプリは `Language` に53言語すべてを持ち、テキスト翻訳ではすべて選べる。会話・カメラ翻訳で選べるのは、前段の音声認識・文字認識が扱える言語だけ（2026-11-08） |
| `form` | `output` | 日本語へ訳すときだけ `plain`（だ・である）か `polite`（です・ます）。会話は `polite` を既定にする |
| 用語集 | `glossary` | `<|plamo:index|>原語<|plamo:item|>訳語` を繰り返す |

原文の言語が分からない場合（画面翻訳）は `input` に `lang` を書かない。モデルが原文から言語を判定する。

原文に `<|plamo:` で始まる文字列が含まれていると、プロンプトの区切りと誤認される。組み立て前に原文からこの文字列を取り除く。

## 履歴と文脈の使い分け

PFML3の履歴（`input` / `output` の組）は、同じ方向の訳を続けるときに用語と文体をそろえる。会話は発話ごとに方向が入れ替わるため、次のように使い分ける。

- **同じ方向の履歴**：方向ごとに直近3組まで保持し、同じ方向の確定訳に付ける。
- **文脈**：方向に関係なく、直近の会話（原文と訳文）を数行の文章にまとめて `context` に入れる。
- **異なる方向の履歴を混ぜる方式**：各 `input` / `output` に `lang` を書けば形式上は書けるが、公式の例は同じ方向だけを示している。会話翻訳の訳に不満が出たら品質を比べ、良ければ採用する。

## 翻訳の依頼

今の実装は、原文・原文の言語・訳先・文体と、任意の背景（`context`）を渡す。背景はカメラ翻訳の表・メニューのモードで「機器のボタン・表示画面、メニュー、看板、表などに書かれた短い表記」を渡している（2026-11-06。効果は限られ、「송풍」が宋風→送風になった程度。`docs/10_カメラ翻訳.md`）。履歴・用語集は、必要になったら足す。

```kotlin
data class TranslationRequest(
    val text: String,
    val source: Language?,                       // null なら原文の言語をモデルが判定する
    val target: Language,
    val form: JapaneseForm = JapaneseForm.POLITE, // 日本語へ訳すときだけ使う
    val context: String? = null,                  // 原文の背景。null なら context を書かない
)
```

`TranslationEngine.translate` は訳文をトークンごとに `Flow<TranslationEvent>`（`Delta` で続き、`Done` で完了）として流し、画面がそのまま逐次表示できるようにする。エンジン自体に優先度は持たせていない。会話翻訳の「確定訳を優先し、古い途中訳を捨てる」は、呼び出し側の `ConversationViewModel` が、途中訳の依頼を最新の1件だけに絞り、確定時に途中訳のジョブを取り消すことで実現した（`docs/04_会話翻訳.md`「途中結果と途中訳」）。ジョブを取り消すと、生成も次のトークンで止まる。

## 翻訳モデルの大きさ（0.8Bと2B）

翻訳モデルは0.8B（既定）と2Bを選べる（2026-11-06、作者の要望「2Bも選べるようにして、翻訳品質と速度の違いをチェックしたい」）。どちらもQ4_K_Mで、大きさの違いだけを比べられるようにした。作者は2Bを選んで使っている。既定をどちらにするかは、会話翻訳で2Bの途中訳が追いつくかを作者が確かめてから決める（`docs/00_現在地.md`「次の作業」）。

- **選び方**：設定の画面（トップ画面右上の「2B・GPU ⚙」から開く）の「翻訳モデル」で選ぶ。会話・カメラ・テキストの画面にも同じ切り替えボタン（`ModelSwitch`）があり、今のモデル・GPU/CPU・読み込み中かを出し、押すとその場で切り替えられる（2026-11-06、作者の要望。端末にないモデルは選べない）。モデルを切り替えるとエンジンが変わるので、カメラ翻訳・画面翻訳のまとめ訳し（`BatchTranslator`）はエンジンが同じかを見て作り直す（作り直さないと閉じたエンジンで訳し続けて失敗した）。選んだものは次に起動したときも使う（SharedPreferencesの `translation`）。2Bが端末に無ければ、その欄から約1.8GBをダウンロードする（`ModelCatalog` の `TranslationModel`、`ModelDownloads.start` に `ModelBundle.LARGE_TRANSLATION` を渡す）。初回の「モデルの準備」で取るのは0.8Bだけ。
- **切り替え**：`EngineHolder.select` が今のエンジンを閉じてから、選んだモデルを読み込む。閉じるのは推論のスレッドで順番に行うので、走っている翻訳が終わってから閉じる。閉じた後に届いた翻訳の依頼は失敗させる（解放したモデルを触らない）。

比べた結果（2026-11-06、REDMAGIC 11 Pro、GPU。`tools/translate-bench.tsv` の13文。韓・英・中→日、日→韓・英）：

| | 0.8B | 2B |
| --- | --- | --- |
| ファイル | 573MB | 1.8GB |
| 読み込み（ウォームアップ前） | 2.9秒 | 8.5秒 |
| 13文の翻訳の合計 | 3.9秒（51トークン/秒） | 10.0秒（19トークン/秒） |
| 1文あたり | 0.16〜0.55秒 | 0.46〜1.3秒 |

訳の違い：大半は同じ意味で、2Bのほうが少し自然。差が出たのは次のような文だった。

| 原文 | 0.8B | 2B |
| --- | --- | --- |
| 这件事你别管了，我自己会处理的。 | この件はあなたに構わなくていいです、自分で対処します。 | この件は放っておいてください。自分で対処します。 |
| 이거 진짜 맛있다! 다음에 또 오자. | これマジで美味しい！また来よう。 | これめっちゃ美味しいです！また来ましょう。 |
| （ファームウェアの文の「bug」） | バグ | 不具合 |

2Bは約2.5倍遅い（13文の合計で2.56倍）。会話翻訳の途中訳（0.5秒ごと）では、長い文で途中訳が追いつかなくなる見込み。実際の使い心地は作者が2Bで話して確かめる。

品質評価の文で比べた結果（2026-11-06）：作者の品質評価の7本 `tools/translate-quality.tsv` と、口語の難しい文54文 `tools/translate-tricky.tsv`（二重否定・反語・皮肉・婉曲な断り・慣用句。4列目が正しい意味）を両モデルに通した。訳の全文は `tools/bench-results/2026-11-06/`、下の表は作者の採点と考察の要約。

| | 0.8B | 2B |
| --- | --- | --- |
| 7本（長文5件＋旅行の短文28件）の合計 | 30.9秒 | 74.6秒 |
| 韓国語の長文（約500字） | 5.1秒 | 11.8秒 |
| 口語の難しい文54文：正しく自然／ニュアンスの欠け／取り違え | 36 / 11 / 7 | 42 / 8 / 4 |

2Bは、0.8Bが取り違えた「제가 살게요（おごります）→住みます」「좀 빼 드릴게요（値引きします）→お釣り」「4호선 타시면 돼요→ターシ面」「items on hold→貸出中」「いくらかかりますか→어느 정도 걸리나요（時間）」などを正しく訳した。両方とも外したのは「바쁘긴요（忙しくなんか）」「초당순두부」「몇 분이세요?（何名様）」「누가 아니래」「배가 불렀구나」「Oh, you shouldn't have!」など、韓国語の慣用句・皮肉と個別知識。二重否定・反語・付加疑問と、日→韓・日→英の方向は両モデルとも崩れなかった。

### モデルの比べ方

デバッグ版の `TranslateBenchActivity` で、同じ文の組を選んだモデルで訳し、時間と訳文を logcat と `files/translate-bench-<model>.tsv` に書く。アプリのエンジンとは別に読み込み、ウォームアップを1回してから測る。

```powershell
adb push tools/translate-bench.tsv /sdcard/Android/data/app.plamotranslate/files/
adb shell am force-stop app.plamotranslate
adb shell am start -n app.plamotranslate/.TranslateBenchActivity --es model LARGE   # SMALL で0.8B
adb logcat -s PlamoTranslate:I   # 「訳比較: …」
```

別の文の組は、`tools/` の `<名前>.tsv` を同じ場所へ送り、`--es set <名前>`（例：`translate-quality`、`translate-tricky`、`translate-labels`、`translate-labels-batch`）を付ける。結果は `files/<名前>-<model>.tsv`。段落のある長文は、TSVの1行に `\n` と書いて改行を表す。`--es context <文>` を付けると、すべての文にその背景（PFML3の `context`）を渡して訳し、結果は `files/<名前>-<model>-ctx.tsv` に書く。

| 文の組 | 中身 | 使ったところ |
| --- | --- | --- |
| `translate-bench.tsv` | 韓・英・中→日、日→韓・英の13文 | 0.8Bと2Bの速さと訳の比べ（上の表） |
| `translate-quality.tsv` | 作者の品質評価の7本（長文5件＋旅行の短文28件） | 品質評価の文での比べ（上の表） |
| `translate-tricky.tsv` | 口語の難しい文54文。4列目が正しい意味 | 同上 |
| `translate-labels.tsv`・`translate-labels-batch.tsv` | エアコンのリモコンなどの短い語。`-batch` は改行でつないだまとめ訳し | カメラ翻訳の表・メニューのモードで背景を渡す効果（`docs/10_カメラ翻訳.md`「残る問題」） |

測り終えたら、端末の `files/` に送ったTSVと結果のTSVを消す。

## パフォーマンスの設定

設定の画面の「パフォーマンス」で、CPUで動かすときの細かい設定を切り替え、「速さを測る」（決まった日本語の文を英語へ訳す）で比べられる（2026-11-08）。値は `TranslationPreferences` が保存し、`EngineHolder` が読み込むときに `TranslationEngine.load` へ `CpuOptions` として渡す。変えるとモデルを読み直す。既定は今までの動きなので、触らなければ何も変わらない。

| 設定 | 既定 | 中身 |
| --- | --- | --- |
| スレッド数 | 自動 | llama.cppの `n_threads`。自動は、最高周波数が一番低いまとまり（小さいコア）がコアの半分以下なら大きいコアの数、そうでなければコア数−2（どちらも2〜6）。15T Proは4、REDMAGICは6（`TranslationEngine.threadsFor`） |
| 性能ヒント | 有 | ADPFのセッションを作り、推論のスレッドの周波数・配置を上げてもらう |
| 回して待つ | 有 | スレッドプールの `poll`（有は50、無は0で眠って待つ） |
| スレッドを常駐させる | 有 | 自前のスレッドプールを作る。無なら、llama.cppが推論のたびにスレッドを用意する |
| ファイルの写像で読む | 有 | 無なら `load_mode` を `LLAMA_LOAD_MODE_NONE` にし、モデルをメモリへ全部読む |
| CPUだけで動かす | 無 | Snapdragonの端末でもGPUを使わない（起動し直すと効く） |
| CPUの計算部分の版 | 自動 | `libggml-cpu-*.so` のうち使う版を固定する（起動し直すと効く。計算部分は起動ごとに1回だけ読み込むため） |
| 同時に訳す数 | 4 | 画面翻訳・カメラ翻訳のまとめ訳しが、いくつのまとまりを一緒に訳すか（1・2・3・4・6・8）。読み直さずに効く。「自動で調整」で端末に合う数を探す（「複数の文を同時に訳す」） |

作った理由：15T Pro（Xiaomi、MediaTek Dimensity 9400+、`armv9.0_1` の版が選ばれる）で、アプリ内の生成が0.3〜0.8トークン/秒しか出なかった。同じ端末で同じモデルを `llama-bench` で動かすと、生成は52〜65トークン/秒（1〜6スレッド）出たので、端末の性能ではなくアプリ内の動かし方が原因である。音声認識を動かさないテキスト翻訳でも同じだったので、音声認識とのCPUの取り合いでもない。どの要素が効くかを作者が実機で試すため、候補を切り替えられるようにした。Snapdragon以外の端末の調整にも使えるので、正式な設定として残す（作者の判断）。作者の試験で、原因はスレッド数だった。6スレッドだと小さいコア（2.4GHz）にも仕事が回り、ほかのスレッドが待たされる。4スレッド（大きいコアの数）にすると生成は56〜62トークン/秒になったので、自動の決め方を上のように直した（0.3.4）。

## 速さの確かめ方

- 端末上のCLIで測るときは `tools/device-translate.ps1`（`-Bench` で `llama-bench`）を使う。`build-android/` にビルドしたCLIとモデルを `/data/local/tmp/plamo/` へ送る。
- アプリ内の速さは、logcatの `翻訳: プロンプト N トークン …ms、生成 …` の行で見る。
- 訳文の品質を比べたくなったら、各言語の短文・長文を数件ずつ `tools/testdata/` に置いて同じ文で比べる。
- 判断に効く結果は `docs/00_現在地.md`「押さえておく事実」に要約し、詳細はこの文書に書く。

## 複数の文を同時に訳す

2026-11-12に、作者の要望で、画面翻訳・カメラ翻訳のまとめ訳し（`BatchTranslator`）が、複数のまとまりを同時に訳すようにした。それまでは流れ（シーケンス）が1本だけで、最大8行・400字のまとまりを1つずつ順に訳していた。生成は1トークンずつしか進まないが、複数の流れを1回の `llama_decode` で一緒に進めると、1回あたりの時間はあまり増えない（小さいモデルの生成は、重みをメモリから読む時間で決まるため）。

### 作り

- **JNI**：`nativeTranslateJobs` が、呼ぶ側（`JobCallback`）から依頼を1件ずつ受け取り、最大 N 本の流れ（`seq_id`）で同時に訳す。1回の `llama_decode` に、生成中の流れの次の1トークンと、空いた流れに入れた新しい依頼のプロンプトをまとめて入れる。訳し終わった流れは `llama_memory_seq_rm` で空け、ほかの流れの終わりを待たずに次の依頼を入れる。流れごとに `onToken(id, bytes)` を呼び、戻り値で「続ける・その依頼だけ止める・全部止める」を返す。依頼が終わると `onFinished(id)` を呼び、呼ぶ側はここで訳し直しの依頼を足せる。サンプリングは貪欲法で状態を持たないので、サンプラーは全部の流れで1つを使う。読み込むときに `n_seq_max = 8`、`kv_unified = true` にする。
- **はじめの作りと直した理由**：最初は、N 件を同時に入れたら全部が終わるまで次を入れなかった（`nativeTranslateBatch`）。作者の指摘「Discordでボットの長文の訳が終わるまで、次の短文の訳が始まらない」で、空いた流れへすぐ次を入れる今の作りにした（同じ2026-11-12）。N 件ずつ区切るのはアプリ側の作りの都合で、llama.cpp の制約ではない。
- **入らないとき**：流れ1本が使えるのはコンテキストの N 分の1。依頼のプロンプトと同じ長さの訳がそこに入らなければ、その依頼は訳さずに `onTooLong(id)` で返す。`BatchTranslator` は、全部を訳し終えた後に、それらを流れ1本（コンテキストを全部使う）で訳し直す。それでも入らなければ空の訳にする。
- **1片ずつ訳す**：同時に訳すとき（N が2以上）は、片をつながずに1片を1つの依頼にする。行をつなぐと、モデルが行数をずらしたり一部の行を原文のまま写したりして、訳し直しが毎回1〜4件出た（作者のDiscordでの試験、0.8B）。訳し直しの行は、まとまり1回分＋1行分遅れて出る。また、まとまりの中の行は上から順に訳されるので、長い片の後ろの短い片が長い片の訳し終わりを待った。1片ずつなら訳し直しは起きない。長い片が1本の流れを使っている間も、ほかの流れで短い片が進む。行ごとの原文の前置き（PFML3の見出し、約20〜25トークン）は増えるが、同時に訳す計算の中でまとめて処理する。前後の行が同じ依頼に入らないので文脈の手がかりは減るが、漫画の吹き出しやDiscordの投稿はもともと1つずつ独立している（作者の判断「並列でできるなら、並列の場合は訳し直しのロジックはなしでいい」、2026-11-12）。
- **1片ずつにした後の試験**（2026-11-12、作者が漫画とDiscordで試したログ、同時4本）：訳し直しはどの画面も0件。控えに無い文を訳した画面の翻訳時間は、2Bで9件3.2秒、0.8Bで21件2.2秒、11件5.2秒、14件8.6秒、8件7.8秒。遅い画面は、生成の合計の速さが1本で訳すときと同じくらい（8件で生成358トークンに7.8秒、約46トークン/秒）まで落ちていた。短い片が先に終わり、長い片（Discordのボットの長文など）が最後に1本だけで残ったとみている。長い片を文の切れ目で分けて同時に訳せば縮められる。
- **長いブロックを文ごとに分ける**：同時に訳すときは、ブロックを文の切れ目でおよそ150字ずつの片に分け（`TranslationChecks.PARALLEL_SPLIT`）、分けた片をほかの流れでも訳して、訳をつないで1つのブロックへ戻す（作者の採用、2026-11-12）。文の途中では分けないので、150字を超える1文はそのまま1片になる。1件ずつ訳すときは、今までどおり1200字を超える段落だけ分ける（`LONG_TEXT`）。片ごとに訳すので、前後の文を手がかりにできず、文のつながりが悪くなることがある。訳の控えは片ごとに残すので、同時に訳す数を1と2以上で切り替えると、長いブロックは控えに当たらなくなる。
- **N が1のとき**：今までどおり8行・400字までを改行でつないで1回で訳す。1件ずつ順に訳すので、前置きの処理を減らすためである。行数が合わない・訳されていない片は、そのまとまりが終わった時点で1片ずつの依頼にして列の先頭へ足して訳し直す。JNIは、一度「次の依頼は無い」と返されても、空いた流れがあれば毎回聞き直す。最初の版は一度無いと返された後は聞かず、後から足した訳し直しを取りこぼして、その行の訳が空のまま残った（2026-11-12、作者がDiscordで試したログで、「11片を訳した・訳し直し3」の回にJNIが2件しか訳していなかった）。
- **スレッド**：依頼の列と、依頼ごとの訳文の途中・打ち切りの判定は、推論のスレッドだけが触る。訳の書き換え・控えの更新は、チャンネルで呼んだ側のコルーチンへ渡して行う。
- **使うところ**：画面翻訳とカメラ翻訳（どちらも `BatchTranslator`）。テキスト翻訳と会話翻訳は1つの文を流して訳すので使わない。
- **設定**：設定の画面の「パフォーマンス」→「同時に訳す数」（1・2・3・4・6・8、既定4）。`TranslationPreferences.parallel` に保存し、`TranslationEngine.parallel` に入れる。読み直さずに効く。

### 自動で調整

端末によって速い数が違うので、設定の画面の「自動で調整」で端末に合う数を探す（作者の要望「順に全部試すのではなく、少ない手数で最適な設定に入る形に」）。候補1・2・4・8本のうち3回だけ測る（`ParallelTuner`）。

1. 4本を測る（REDMAGICの最適値に近い真ん中）。
2. 1本を測る（比べる基準）。
3. 4本が1本の1.1倍以上速ければ8本を、そうでなければ2本を測る。

測るたびに、そこまでで一番合う数を設定に入れる。一番速い数を選ぶが、それより少ない数で一番速い値の9割以上出ていれば少ない方を選ぶ（同時に訳す数が多いほど1つのまとまりが短くなり、前後の行が訳の手がかりにならない）。測るのは、長さのそろった日本語の文 N 件を英語へ40トークンまで同時に訳す時間で、プロンプトの処理も含めた全部のトークン/秒（`EngineBenchmark.runParallel`）。測る前に同じ件数で短く1回訳し、初回だけ遅くなる分を除く。

「速さを測る」は、1文の速さ（最初の文字までの時間と生成のトークン/秒。テキスト翻訳・会話翻訳の目安）に加えて、今の「同時に訳す数」での合計の速さ（「自動で調整」と同じ測り方）も出す。数を選んで押せば、手でも比べられる（2026-11-12、作者の指摘「同時に訳す数を変えても、速さを測るの生成の値が24トークン/秒のまま変わらない」。それまでは1文しか測っておらず、同時に訳す数を変えても値が変わらなかった）。合計の値は原文の読み込みを含むので、1文の生成の速さより小さく出る（2Bで1文の生成24、同時に1件の合計22）。

アプリでの結果（2026-11-12、REDMAGIC、2B・GPU）：1本 25、4本 36、8本 39トークン/秒（生成だけ。ログの「翻訳（同時N本）」）。プロンプトの処理を含めると4本が8本の9割以上なので、4本を選んだ。CLIより伸びが小さいのは、早く訳し終わる文があって同時に進む数が途中で減るためとみている（この計測は、空いた流れに次を入れる作りにする前のもの。計測の文は依頼の数と流れの数が同じなので、作りを変えても同じ条件になる）。ログの「翻訳（同時N本）」には、依頼の数・プロンプトと生成のトークン数・全体の時間・最大で何本が同時に動いたかを出す。

### CLIでの計測

作者の質問「複数を同時に回した方が速くなるか」に答えるため、実装の前にREDMAGIC 11 Proで llama.cpp の `llama-batched-bench` を動かし、同時に訳す本数ごとの生成の速さを測った。

条件：プロンプト64トークン、生成64トークン、`-c 4096 -b 2048 -ub 2048 -npl 1,2,4,8`。GPUは `-ngl 99`（OpenCL）、CPUは `-ngl 0 -t 6`。モデルは端末のアプリの `files/models/llm/` のQ4_K_M。数字は全部の流れを合わせた生成のトークン/秒。

| 同時の本数 | 0.8B GPU（2回） | 0.8B CPU | 2B GPU | 2B CPU |
| --- | --- | --- | --- | --- |
| 1 | 58・56 | 77 | 26 | 23 |
| 2 | 53・50 | 108 | 24 | 29 |
| 4 | 99・93 | 201 | 44 | 55 |
| 8 | 115・107 | 225 | 44 | 61 |

分かったこと：

- GPUは、2本では速くならず、4本で約1.7倍になる。8本は0.8Bで約2倍、2Bは4本と同じ。
- CPUは、4本で約2.4〜2.6倍、8本で約2.7〜2.9倍になる。ただしCLI単体の値で、アプリ内では画面描画とのCPUの取り合いと、REDMAGICのCPUクロック上限の影響を受ける（「ビルド設定」）。アプリ内の値は測っていない。
- プロンプト処理は本数を増やしても遅くならない（GPUの0.8Bで830〜1320トークン/秒）。1文ごとにプロンプトを分けても、固定費は小さい。

見込み：4本を同時に訳すと、GPUでは1画面の翻訳時間がおよそ6割になる（一般の画面16件の5.5秒が3.5秒前後）。実際の画面での時間はまだ測っていない。

計測のビルドは、「イテレーション0」（`docs/06_開発環境.md`）のCLIの設定に `-DGGML_OPENCL=ON` と、`third_party/OpenCL-ICD-Loader` から作ったリンク用の `libOpenCL.so`（`-DOpenCL_LIBRARY`、`-DOpenCL_INCLUDE_DIR=third_party/OpenCL-Headers`）を足し、`--target llama-batched-bench` で作った。端末では `LD_LIBRARY_PATH=/vendor/lib64` を付けて動かす。動かすと `/data/local/tmp/llama.cpp/cl-cache/` ができるので、CLIと一緒に消す。
