# 開発環境

WindowsのPCでコマンドからビルドし、adbで端末に入れて試す。新しいPCでは、JDK 21・Android SDK・Python 3を入れ、リポジトリをサブモジュールごと取り、sherpa-onnxのAARを取ってからビルドする。モデルはアプリが初回起動時に取るので、PCから送るのは開発中に同じ版を置き直すときだけである。正式版は配布用の鍵で署名してGitHubのリリースに置き、アプリはそこから自分を更新する。端末に送った試作の残りは、作業の区切りで消す。

## PCに入れるもの

| ソフト | 版 | 用途 |
| --- | --- | --- |
| JDK | 21 | Gradleの実行。Kotlin/JVMのモジュール（`core-pipeline`・`core-log`）が `jvmToolchain(21)` を指定し、toolchainを自動で取る設定は無いので、手元に要る。出力は全モジュールJava 17相当。Android Studio同梱のJBR 25ではGradle 8.14.3が動かない |
| Android SDK Platform | API 36 | `compileSdk`・`targetSdk` |
| NDK | `29.0.14206865` | llama.cppとJNI。`core-llm/build.gradle.kts` の `ndkVersion` で固定している |
| CMake | `3.31.6`（Ninja同梱） | ネイティブビルド。`core-llm/build.gradle.kts` で固定している |
| Git | 最新 | サブモジュール（llama.cpp、OpenCL-Headers、OpenCL-ICD-Loader） |
| PowerShell | 7 以上（`pwsh`） | `tools/` のスクリプト、文書の検査と設計の点検（コミットの前と Claude Code のフックが呼ぶ） |
| Python 3 | 3系 | 必須。llama.cppのOpenCLカーネルを埋め込むスクリプトがビルド中に動く。評価の採点（`tools/eval-screen.py`・`tools/score-speaker.py`）、ライセンス文の収集（`tools/collect-licenses.py`）、モデルの取得（`huggingface_hub` の `hf`）にも使う |
| GitHub CLI（`gh`） | 任意 | リリースの作成とAPKの添付（「リリースを作る」）。無ければ、APKの添付と公開は作者が行う |

1. SDKの部品を入れる。Android Studioがあれば SDK Manager で入れる。無ければ Android SDK コマンドラインツールを `%LOCALAPPDATA%\Android\Sdk\cmdline-tools\latest` へ展開し、`sdkmanager` で `platform-tools`・`platforms;android-36`・`build-tools`・`ndk;29.0.14206865`・`cmake;3.31.6` を入れる。PowerShellから `sdkmanager.bat` を呼ぶときは、`'"ndk;29.0.14206865"'` のように引用符ごと渡す（cmdが `;` で引数を割り、「Package ndk not found」になる）。
2. SDKは `%LOCALAPPDATA%\Android\Sdk` に置く。`tools/` のスクリプトはadbをこの場所から呼ぶ。
3. ユーザー環境変数に `JAVA_HOME`（JDK 21の場所）、`ANDROID_HOME`（1のSDKの場所）、`PYTHONUTF8=1` を設定し、`platform-tools` を `PATH` に足す。GradleはSDKを `ANDROID_HOME` から見つけるので、`local.properties` に `sdk.dir` を書かなくてよい（Android Studioで開くと書き足されるが、どちらでも動く）。`PYTHONUTF8` が無いと、OpenCLカーネルを埋め込むスクリプトが日本語環境の既定（cp932）でソースを読めずに失敗する。
4. TLS検査のあるネットワークで `PKIX path building failed` になるときは、JavaにWindowsの証明書ストアを使わせる。`sdkmanager` は `$env:SDKMANAGER_OPTS="-Djavax.net.ssl.trustStoreType=Windows-ROOT"` を付けて動かし、Gradleは `%USERPROFILE%\.gradle\gradle.properties` に `systemProp.javax.net.ssl.trustStoreType=Windows-ROOT` を書く。プロキシを通るときは、同じファイルに `systemProp.https.proxyHost`・`systemProp.https.proxyPort` を書き、`hf` には環境変数 `HTTPS_PROXY` を設定する。

## 端末の準備

開発者向けオプションで「USBデバッグ」を有効にし、USBでつなぐ。無線なら「ワイヤレスデバッグ」の「ペア設定コードによるデバイスのペア設定」の値で `adb pair <IP>:<ペア設定用ポート>`、`adb connect <IP>:<接続用ポート>` を実行する。Wi-Fiが端末どうしの通信を遮るなら、USBを使う。

## リポジトリ

リポジトリは GitHub の [kagerouttepaso/PlamoTranslate](https://github.com/kagerouttepaso/PlamoTranslate)（ブランチ `main`）にある。公開リポジトリなので、コミットの作者はGitHubのnoreplyのアドレスにする。

1. サブモジュールごとクローンする。

   ```powershell
   git clone --recurse-submodules https://github.com/kagerouttepaso/PlamoTranslate.git
   cd PlamoTranslate
   ```

2. コミットの作者をクローンごとに設定する。Gitはリポジトリの中のファイルから設定を読まないので、クローンするたびに行う。クローンごとの設定（`.git/config`）はPCのグローバル設定より優先される。

   ```powershell
   git config user.name kagerouttepaso
   git config user.email 4670521+kagerouttepaso@users.noreply.github.com
   git config --show-origin user.email   # file:.git/config と出ればよい
   ```

3. コミットの前の検査を有効にする。`.githooks/pre-commit` が文書の検査と設計の点検を回し、誤りがあればコミットを止める（`CLAUDE.md`「規則を支える仕組み」）。これもクローンごとの設定である。

   ```powershell
   git config core.hooksPath .githooks
   ```

4. Gitに入れていないsherpa-onnxのAARを取る（無いとビルドが失敗する）。音声認識のモデルもPCに取るなら `-Models` を付ける。

   ```powershell
   ./tools/get-sherpa-onnx.ps1
   ```

5. 作業を始めるたびに `git pull` し、サブモジュールの固定したコミットが変わっていれば `git submodule update --init` で合わせる。

## ビルドと実行

テストを流してから開発版を入れる。

```powershell
.\gradlew.bat :core-pipeline:test :core-log:test :core-llm-jvm:test :core-ocr:testDebugUnitTest :core-asr:testDebugUnitTest :core-tts:testDebugUnitTest :app:testDebugUnitTest
.\gradlew.bat :app:installDebug
.\gradlew.bat :featurelab:installDebug   # 機能テストをするときだけ（docs/資料/端末の能力.md）
```

- `core-pipeline` と `core-log` はKotlin/JVMのモジュールなので、テストのタスクは `test` である。状態遷移・判定器・翻訳の契約の単体テストは `core-pipeline` にある。ほかのモジュールはAndroidのモジュールなので `testDebugUnitTest` になる。
- 初回はGradle・ライブラリの取得と、llama.cppのコンパイルで数分かかる。llama.cppの構成時にKleidiAIを取るので、ネットにつながっている必要がある。デバッグビルドでも、llama.cppは `-DCMAKE_BUILD_TYPE=Release` で作る（Debugだと推論が桁違いに遅い）。
- 入れた直後は、アプリが「モデルの準備」の画面を出す（「モデルの取得と置き場」）。
- 開発版はPCごとのデバッグ用の鍵（`%USERPROFILE%\.android\debug.keystore`）で署名される。正式版の入った端末にも上書きできないので、入れ替えるときはアンインストールが要る（作者に確認する）。モデル（`files/models/`）は端末の中で `/sdcard/` の下へ `mv` で退避し、入れ替えた後にアプリを一度開いて `files/` を作らせてから戻すと、取り直さずに済む（シェルで `files/` を作ると、アプリが読めない持ち主になる）。設定は消える。別のPCで入れた開発版には上書きできない（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）。複数のPCから入れるなら、同じ `debug.keystore` を各PCの同じ場所へ写す（Gitには入れない）。写さずに入れ直すとアプリのデータ（設定・モデル）が消えるので、`adb uninstall` の前に作者に確認する。

### ログを見る

1. `adb shell setprop log.tag.PlamoTranslate V` でアプリのタグを開ける。REDMAGICは既定でログを黙らせているので、端末を再起動するたびに打ち直す（`docs/資料/端末の能力.md`「設計に効く、思わぬ事実」）。
2. `adb logcat -s PlamoTranslate` で見る。どのモジュールもネイティブ（`plamo_llm.cpp`）も、ロガー `Logs` を通してタグ `PlamoTranslate` で出す（JVMにつながっていないllama.cppのスレッドからの行だけは、logcatにだけ出る。`docs/設計/アーキテクチャ.md`「ログ」）。原文・訳・読み取った文字・話した言葉を含む行は、「詳しい記録を残す」がオンのときだけ出る。デバッグ版の既定はオンで、正式版では設定の「詳細設定」（設定の画面の下の「詳細設定を表示」で出る）で選ぶ。翻訳エンジンは1回の実行ごとに `翻訳（同時N本）: N件、プロンプト … トークン、生成 … トークン、…ms` の行を出す（読み方は `docs/設計/翻訳コア.md`「速さの確かめ方」）。

ログを開けていなくても、アプリはプロセスごとのファイルにもログを書いている。落ちた後なら、設定の「不具合の記録」で書き出した zip に、落ちたプロセスのログが入る。

### GPUとCPU、デバッグ版の入口

- 翻訳はQualcommの端末ではGPU、それ以外ではCPUで動く。GPUの端末でCPUの速さを見るときは、設定の画面の「性能」で「CPUだけで動かす」を選び、アプリを起動し直す。どちらで動いているかは、トップ画面右上（「2B・GPU」と歯車など）と設定の画面に出る。
- デバッグ版だけ、画面翻訳を開始した状態で、PCからブロードキャストで操作できる（計測用）。

  ```text
  adb shell am broadcast -a app.plamotranslate.DEBUG_TRANSLATE                                # 画面翻訳を1回動かす
  adb shell am broadcast -a app.plamotranslate.DEBUG_CONFIG --ez boost false --ei threads 6   # 性能ヒントとスレッド数を変える
  ```

- 評価の `BenchActivity` は `docs/設計/画面翻訳.md`「評価」、翻訳モデルの比べの `TranslateBenchActivity` は `docs/設計/翻訳コア.md`「モデルの比べ方」、音声認識モデルの比べの `AsrBenchActivity` と会話翻訳に音声ファイルを流す入口は `docs/設計/会話翻訳.md`「動作確認」を見る。

## Windows版のビルドと実行

Windows 11 x64 で CPU と Vulkan の DLL をまとめてビルドする。Gradle の起動には「PCに入れるもの」の環境を使う。これに加えて次を用意する。

- Visual Studio Community 2026 の「C++ によるデスクトップ開発」。MSVC の x64 ビルドツールと Windows 11 SDK を入れる。CMake と Ninja は Android SDK 同梱のものを使ってよい。両方に `PATH` を通す。
- x64 の JDK 21。`JAVA_HOME` に JDK のルートを設定する。CMake はここから JNI のヘッダーを見つけ、Gradle は JDK 21 で PC 版を起動する。
- Vulkan SDK 1.4.363.0。`winget install --id KhronosGroup.VulkanSDK --exact --version 1.4.363.0 --source winget` で入れる。インストール後に開いた端末で `VULKAN_SDK` が SDK のルートを指していることを確かめる。CMake は SDK の `glslc` と SPIRV-Headers を使う。

Visual Studio 2026 の **x64 Native Tools Command Prompt** を開き、`pwsh` に入る。サブモジュールを取得したリポジトリのルートで次を実行する。

```powershell
./tools/get-pdfium.ps1
./tools/get-harfbuzz.ps1
cmake -S desktop-native -B desktop-native/build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build desktop-native/build --parallel 4
.\gradlew.bat :desktop:run
```

DLL は `desktop-native/build/bin` にまとまる。`get-pdfium.ps1` と `get-harfbuzz.ps1` はアーカイブを SHA-256 で照合し、`third_party/pdfium/` と `third_party/harfbuzz/` に展開する。HarfBuzz のサブセット処理は `mockingword-pdf.dll` に静的リンクし、PDFBox は Gradle が取得する。PDF 翻訳用の Noto Sans JP はアプリが初回に取得し、`%LOCALAPPDATA%\Mockingword\fonts` に保存する。

GGUF の音声認識を Windows の JNI で試験するには、`MOCKINGWORD_ASR_NATIVE` にこの DLL ディレクトリの絶対パス、`MOCKINGWORD_ASR_FIXTURES` に `Qwen3-ASR-0.6B-Q8_0.gguf`、`mmproj-Qwen3-ASR-0.6B-Q8_0.gguf` と日英韓の `ja00.pcm`・`en00.pcm`・`ko00.pcm`（16 kHz、モノラル、リトルエンディアンの float32）を置いたディレクトリを指定する。Vulkan でも中断を試すときは `MOCKINGWORD_ASR_VULKAN=1` を設定する。`:core-llm-jvm:test` で実行し、終了した要求の本文と言語を中断前の結果と照合する。これらのファイルはリポジトリには含めない。モデルなしでの出力解析試験は `:core-pipeline:test` にある。

PDF の試験は `./gradlew.bat :desktop:test` で実行する。起動中の PC 版と並行して PDF 用 DLL を作る場合は、CMake の `-B` で別のビルド先を指定し、`cmake --build <ビルド先> --parallel 4 --target mockingword-pdf` で PDF 用 DLL を作る。同じ出力先からアプリも起動する場合は、そこにすべての DLL をビルドする。別の DLL を使う試験・起動では Gradle に `-PdesktopNativeDir=<DLLのフォルダー>` を渡す。`:desktop:run` は標準出力と標準エラーを UTF-8 で Gradle に渡す。

起動だけを繰り返す場合は、Windows のショートカットのリンク先に `<クローンした場所>\gradlew.bat :desktop:run`、作業フォルダーにクローンした場所を指定する。標準のビルド先の DLL を更新するときは PC 版を閉じる。

配って使う形のリリース版は、上の DLL と sherpa-onnx の DLL（「Windows で音声翻訳を使う」の手順1）をそろえてから `.\gradlew.bat :desktop:createReleaseDistributable` で作る。`desktop/build/compose/binaries/main-release/app/Mockingword/` に `Mockingword.exe`、Java の実行環境、DLL（`app/resources`）がまとまる。このフォルダーをそのまま渡せば、Gradle や JDK の無い PC でも起動できる。開発起動と配布版は Compose が準備した同じ DLL 一式を使う。開発時は準備先の絶対パスを JVM に渡し、配布時はランチャーが実行ファイルからの相対位置を解決する。アプリは起動時に、JNI の DLL が依存する DLL（`llama.dll`・`pdfium.dll` など）を完全なパスで先に読み込む。ProGuard による縮小は、JNI と PDFBox がリフレクションから呼ばれるのでかけない。

起動時に使う翻訳モデルがないと、「モデルの準備」が開く。翻訳モデルと音声認識モデルを選んで「ダウンロード」を押す。既定は 0.8B と SenseVoice Small。必要なファイルを取得して SHA-256 の照合が終わると、「テキスト翻訳」が開く。選んだモデルは後から「設定」で変更できる。「取り消す」で止めたダウンロードは、同じモデルを選ぶと途中から再開できる。

翻訳モデルは `%LOCALAPPDATA%\Mockingword\models`、音声認識モデルはその下の `asr` に置く。手動で配置したモデルも使える。一覧にない GGUF は初回の「GGUF ファイルを選ぶ」か、「設定」→「モデルの詳細」から指定する。モデルが使える状態になったら「テキスト翻訳」で言語を選び、原文を入力して「翻訳する」を押す。

「設定」の「性能」で Vulkan と CPU を切り替える。Vulkan を利用できない場合や GPU での準備に失敗した場合は CPU で動く。使用中の実行先は「設定」に出る。「設定」→「詳しい記録を残す」は既定でオフ。オンにすると原文と訳文を記録するため、試すときは機密情報を使わない。保存先は `%LOCALAPPDATA%\Mockingword\logs`。

### Windows で音声翻訳を使う

1. リポジトリのルートで `./tools/get-sherpa-onnx.ps1 -Windows` を実行する。Gradle は AAR から Kotlin API を取り出す。起動時は同じ版の Windows x64 JNI と依存 DLL を `third_party/sherpa-onnx/sherpa-onnx-v2.0.1-win-x64-jni/lib` から読み込む。別の場所に展開した場合は `:desktop:run -PdesktopSherpaDir=<libの場所>` で指定する。音声の取り込みに使う `mockingword-audio.dll` は上の CMake ビルドで作る。
2. `./gradlew.bat :desktop:run` またはリリース版の `Mockingword.exe` で起動する。「音声翻訳」でモデルの準備を求められたら音声認識モデルを選んでダウンロードする。「設定」→「音声認識」からも取得できる。どちらも Silero VAD を含み、Qwen3-ASR には Whisper tiny も含む。旧 ONNX から移る際は「Qwen3-ASR のモデル更新が必要」の表示で取得量を確認して選ぶ。手動配置なら `models/asr/qwen3-asr-gguf/` に本体と mmproj の Q8_0 を両方置く。サイズと SHA-256 が一致するまで使えない。照合後に「旧 Qwen3-ASR のファイルを確認…」で対象と容量を確認して削除できる。手動で置く場合は `SharedModelCatalog.kt` の相対パスを使い、起動中に追加した場合はアプリを開き直す。
3. 「音声翻訳」→「マイク」で、自分を日本語、相手と話す人を「自動」にする。「開始」を押して日本語と英語を交互に話し、相手の言語と訳の向きを確かめる。手動で試す場合は相手の言語を固定し、「停止」してから話す人を切り替える。マイクを開けない場合は、Windows の「プライバシーとセキュリティ」→「マイク」のデスクトップ アプリのアクセスを確認する。
4. 「PC の再生音」では原文と訳す先を選び、「開始」を押して別のアプリで音声を再生する。原文と訳はメインウィンドウと字幕ウィンドウに出る。字幕はタイトル部分をドラッグして移動し、枠をドラッグして大きさを変える。「停止」を押すと最後の発話を確定する。

## モデルの取得と置き場

Android アプリは初回起動時に、全画面の「モデルの準備」で要るモデルをダウンロードする。モデルごとの版と取得元の参照先は `docs/現在地.md`「固定した版」にある。配った端末ではこれだけでよい。

開発中に PC から送るときは、カタログの URL と同じコミットの版を送る。Android アプリはファイルサイズがカタログの値と一致するものをダウンロード済みとみなす。Hugging Face から取る `hf` は `pip install -U huggingface_hub` で入る。

| モデル | PCへの取り方 | 端末の置き場（`/sdcard/Android/data/app.plamotranslate/files/models/` の下） |
| --- | --- | --- |
| 翻訳 0.8B（既定） | `hf download pfnet/plamo-3-translate-0.8b-GGUF plamo-3-translate-0.8b-Q4_K_M.gguf --revision <コミット> --local-dir models` | `llm/plamo-3-translate-0.8b-Q4_K_M.gguf` |
| 翻訳 2B（選んだときだけ） | 同じく `pfnet/plamo-3-translate-2b-GGUF` の `plamo-3-translate-2b-Q4_K_M.gguf`。ふだんは「モデルの準備」の画面で選ぶか、設定の「翻訳モデル」の「2Bをダウンロード」で取る | `llm/plamo-3-translate-2b-Q4_K_M.gguf` |
| 音声認識（SenseVoice Small int8、Silero VAD） | `./tools/get-sherpa-onnx.ps1 -Models` で `models/asr/` に取る | `asr/sense-voice/model.int8.onnx`・`asr/sense-voice/tokens.txt`・`asr/silero_vad.onnx` |
| 音声認識（Qwen3-ASR 0.6B int8、言語の識別 Whisper tiny int8。選んだときだけ） | 「モデルの準備」で選ぶか、設定の「音声認識モデル」で取る。録音のリプレイに使う場合は `SharedModelCatalog.kt` の URL から同じ並びに取る | `asr/qwen3-asr/`・`asr/whisper-tiny/` |
| 漫画用OCR（PP-OCRv6 manga） | `hf download Kellenok/PP-OCRv6_manga det/manga_det_v0.2.onnx rec/manga_rec_v0.2.onnx ppocrv6_dict.txt --revision <コミット> --local-dir models/ocr/manga-src` で取り、下の手順2で名前を変えて `models/ocr/manga/` に置く | `ocr/manga/det.onnx`・`rec.onnx`・`dict.txt` |
| 韓国語の文字の認識（PP-OCRv5 korean） | `hf download wycliffeassociates/docscanner-ocr korean/rec_model.onnx korean/charset.json --revision <コミット> --local-dir models/ocr/korean-src` で取り、下の手順2で名前を変えて `models/ocr/korean/` に置く。検出は漫画用OCRの `det.onnx` を使う | `ocr/korean/rec.onnx`・`dict.json` |
| 読み上げ（Supertonic 3） | PCからは送らない。「モデルの準備」の画面か設定の「読み上げ」で選んだときにアプリが取る | `tts/supertonic-3/` |
| ML Kit | APKに同梱 | 不要 |

1. アプリを一度起動する（端末にアプリのフォルダーができる）。
2. 上の表のとおり PC に取る。`<コミット>` はカタログの URL の `resolve/` の後ろの値。漫画用 OCR と韓国語の文字の認識は、アプリが読む名前に変えて置く。

   Copy-Item models/ocr/korean-src/korean/charset.json models/ocr/korean/dict.json

3. adbで送る。

### モデルの版を上げる

アプリはHugging Faceのファイルを、コミットを指定したURLで取り、大きさとSHA-256で照合する（理由は `docs/判断/2026-11-08_モデルのURLをコミットで固定し大きさとハッシュで照合する.md`）。配布元が古いコミットのファイルを消すと、アプリは「ダウンロードに失敗しました（HTTP 403）」などを出すので、次の手順で版を上げる。

1. 配布元のコミットの履歴で、何が変わったかを見る。
2. 重みが変わったなら、品質と速度を測り直す（`docs/設計/翻訳コア.md`）。
3. 新しいコミットの大きさとハッシュを、HEADの応答の `X-Linked-Size`（バイト数）と `X-Linked-ETag`（SHA-256）で取る。`curl.exe -sI <新しいURL>` で見る（転送先へ進まない最初の応答に付く）。
4. 該当するカタログの URL・ファイルサイズ・SHA-256 をまとめて書き換え、`docs/現在地.md`「固定した版」を直し、アプリの版を上げる。

## 端末でCLIを動かして測る

llama.cppのCLIを端末で直接動かすと、アプリの外で端末の素の速さを測れる（アプリ内の速さと比べるときに使う。`docs/設計/翻訳コア.md`「速さの確かめ方」）。

1. SDK同梱のCMake・Ninjaで、CPU版のCLIを `build-android/` に作る。

   ```powershell
   $s="$env:LOCALAPPDATA\Android\Sdk"; $cm="$s\cmake\3.31.6\bin"
   & "$cm\cmake.exe" -S third_party/llama.cpp -B build-android -G Ninja "-DCMAKE_MAKE_PROGRAM=$cm\ninja.exe" `
     "-DCMAKE_TOOLCHAIN_FILE=$s/ndk/29.0.14206865/build/cmake/android.toolchain.cmake" `
     -DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-28 -DCMAKE_BUILD_TYPE=Release `
     -DGGML_NATIVE=OFF -DGGML_OPENMP=OFF -DGGML_LLAMAFILE=OFF -DLLAMA_OPENSSL=OFF `
     -DGGML_CPU_KLEIDIAI=ON -DBUILD_SHARED_LIBS=OFF -DLLAMA_BUILD_TESTS=OFF
   & "$cm\cmake.exe" --build build-android -j 12 --target llama-cli llama-bench llama-completion
   ```

2. 翻訳モデルを `models/plamo-3-translate-0.8b-Q4_K_M.gguf` に置く（「モデルの取得と置き場」）。
3. `./tools/device-translate.ps1 -Text "<原文>" -Source ko -Target ja` で1文を訳し、`./tools/device-translate.ps1 -Bench` で `llama-bench` を動かす。CLIとモデルは端末の `/data/local/tmp/plamo/` へ送られる。
4. GPU（OpenCL）で測るときは、まずリンク用の `libOpenCL.so`（KhronosのICDローダー）を同じツールチェーンで作る。アプリのビルドが `core-llm/src/main/cpp/CMakeLists.txt` で作るものと同じ設定である。実行時は端末の `/vendor/lib64/libOpenCL.so` を使うので、作ったものは端末へ送らない。

   ```powershell
   $s="$env:LOCALAPPDATA\Android\Sdk"; $cm="$s\cmake\3.31.6\bin"
   & "$cm\cmake.exe" -S third_party/OpenCL-ICD-Loader -B build-android/opencl-icd -G Ninja "-DCMAKE_MAKE_PROGRAM=$cm\ninja.exe" `
     "-DCMAKE_TOOLCHAIN_FILE=$s/ndk/29.0.14206865/build/cmake/android.toolchain.cmake" `
     -DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-28 -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF `
     "-DOPENCL_ICD_LOADER_HEADERS_DIR=$PWD/third_party/OpenCL-Headers"
   & "$cm\cmake.exe" --build build-android/opencl-icd --target OpenCL
   ```

   次に、1の構成に `-DGGML_OPENCL=ON`、`"-DOpenCL_INCLUDE_DIR=$PWD/third_party/OpenCL-Headers"`、`"-DOpenCL_LIBRARY=$PWD/build-android/opencl-icd/libOpenCL.so"` を足して作り直す。端末では `LD_LIBRARY_PATH=/vendor/lib64` を付けて動かす。
5. 測り終えたら消す（「端末の片付け」）。

## 画面翻訳の評価

保存したスクリーンショットに、デバッグ版の `BenchActivity` で画面翻訳と同じ処理をかけて採点する。観点と採点の方法は `docs/設計/画面翻訳.md`「評価」。

1. 評価用の画像は著作物を含むのでGitに入れない。手元に無ければ作者にスクリーンショットを頼み、正解（`truth.json`）も作り直す。画像と `truth.json` は `tools/testdata/ocr/<セット>/` に置く。
2. 開発版を入れた端末で `./tools/run-bench.ps1 -Set <セット> -Label <名前>` を流す（原文の言語は `-Lang` に言語コードで渡す。`auto`（既定）・`zh-hans`・`ko`・`en` など）。画像を端末の `files/bench/in` へ送り、結果を `tools/testdata/ocr/<セット>-out/<名前>/` へ取り出し、`truth.json` があれば `tools/eval-screen.py` で採点する。
3. 変更の前と後で同じセットを流して比べる。

- 英語の合成画面と正解は `./tools/make-en-screen.ps1` で作る（既定の出力は `tools/testdata/ocr/en-synthetic/`）。
- 文字認識の候補をPCで試す `tools/ocr-spike.py` は、ONNX Runtime・OpenCV・pyclipperを入れたPythonの仮想環境で動かす。

## 会話の録音をリプレイする

会話翻訳の区切り（話し手の判定・カードの区切り・書き起こし）を、端末で録った会話の録音でPCに再現する（`core-asr` の `ConversationReplayTest`）。VAD・言語の識別・書き起こしは端末と同じモデルを sherpa-onnx と ONNX Runtime で動かし、ジョブの処理時間だけを端末で測った式で模擬するので、同じ録音からは同じ結果になる。区切りを変えたら、変更の前と後で同じ録音を流して比べる。

1. 録音を取る。会話翻訳は、「詳しい記録を残す」がオン（デバッグ版の既定）なら、聞いている間の音声を端末の `Android/data/app.plamotranslate/files/asr-rec/conv_*.wav` に書く。`adb pull` で取り出す。録音は話した声なのでGitに入れない。
2. `silero_vad.onnx`、`qwen3-asr/`、`whisper-tiny/` を1つのフォルダーに置く。Android の `files/models/asr/` と同じ構成で、取得元は `SharedModelCatalog.kt` にある。
   PC 版と比較する場合は `PLAMO_REPLAY_DESKTOP=1` で Windows 版の Whisper を選ぶ。旧 sherpa を測るときは `MOCKINGWORD_ASR_FIXTURES` を設定せず、GGUF 版を測るときは「Windows版のビルドと実行」の JNI 試験と同じ `MOCKINGWORD_ASR_FIXTURES` と `MOCKINGWORD_ASR_NATIVE` を設定する。
3. `./tools/get-sherpa-onnx.ps1 -Windows` で sherpa-onnx の Windows x64 JNI を展開する（「Windows で音声翻訳を使う」）。
4. 環境変数を置いて流す。手で区切った位置は、端末の記録の「区切ると決めた（手で区切り）」の秒を渡す。

   ```powershell
   $env:PLAMO_SHERPA_LIB="<JNIの展開先>\lib"
   $env:PLAMO_REPLAY_WAV="<録音>.wav"
   $env:PLAMO_REPLAY_ASR="<モデルのフォルダー>"
   $env:PLAMO_REPLAY_OUT="<結果のファイル>"
   $env:PLAMO_REPLAY_CUTS="72.1,83.8"     # 任意
   $env:PLAMO_REPLAY_PARTNER="auto"       # 相手の言語。auto か言語のコード
   .\gradlew.bat :core-asr:testDebugUnitTest --tests "*ConversationReplayTest.replay" --rerun
   ```

   結果のファイルには、確定したカードの一覧（人が読むための要約）と区切りの経過が入る。採点の道具は区切りの経過の中の確定の行を読む。7分の録音で20分ほどかかる。
5. 採点する。録音ごとに一度、基準（0.25秒ごとの声の言語。録音の全体を見通した Whisper tiny の判定で、声の有無は Silero VAD）を作り、リプレイの結果を `tools/score-speaker.py` で採点する。言語の違う声の割合、話し手の交代の取りこぼしと遅れ、幻（「system」など）の数が出る。変更の前と後の結果を並べて渡すと、同じ基準で比べられる。

   ```powershell
   $env:PLAMO_REFERENCE_OUT="<基準>.tsv"
   .\gradlew.bat :core-asr:testDebugUnitTest --tests "*ConversationReplayTest.reference" --rerun
   python tools/score-speaker.py <基準>.tsv <変更の前>.txt <変更の後>.txt
   ```

カードの区切り方（文の途中で切っていないか、長すぎ・断片のカード）は、カードを確定した行（「確定（理由）…」）を、正解の区切り（`tools/testdata/conversation/` に置く。書き方は `docs/設計/会話翻訳.md`「動作確認」）に照らして採点する。行は、PC のリプレイの結果のファイル（`ConversationReplayTest.replay`）か、端末で録音を `--es wav` でリプレイしたときの logcat（「詳しい記録を残す」をオン）から読む。2つの採点の道具は、この確定の行を同じ読み方（`tools/conversation_log.py`）で読む。行の形の正本は `tools/conversation_log.py` の `CARD_CLOSED` で、`SpeechSegmenterTest` が実際の行に当てて確かめる。

```powershell
python tools/score-conv.py <正解>.truth.txt <リプレイの結果>.txt
adb logcat -d -s PlamoTranslate:D > <ログ>.txt   # 端末でリプレイしたとき
python tools/score-conv.py <正解>.truth.txt <ログ>.txt
```

端末で確かめるのは、PC のリプレイで改善した版だけにする（直していない版を端末で流しても、録ったときの記録以上のことは分からない）。配った版が入っている端末に、データとモデルを残したままデバッグ版を入れるときは、配布の鍵で署名する（`.\gradlew.bat :app:assembleDebug -Pplamo.debugWithReleaseKey`）。

### 見立ての会話を作る

人の声を録らずに区切りを比べるときは、公開の音声データ FLEURS（CC BY 4.0）の2言語の文をつないで、2人の会話に見立てた試験音声を作る（`tools/make-conv.py`）。音声と一緒に、正解の区切り（`.truth.txt`。1文を1単位とする）と声の言語の基準（`.reference.tsv`）も書くので、`ConversationReplayTest.reference` を回さずにそのまま採点できる。FLEURS の置き場に文が無ければ、dev の先頭の60文を取り出す。

```powershell
# 交代の間が0.3〜1.2秒で、半分の交代で前の人の文の終わりに重ねて話し始める会話（20文）
python tools/make-conv.py <FLEURSの置き場> tools/testdata/conversation/fleurs-jako-quick-1 --seed 21 --overlap 0.5
adb push tools/testdata/conversation/fleurs-jako-quick-1.wav /sdcard/Android/data/app.plamotranslate/files/asr-test/
adb shell am start -S -n app.plamotranslate/.conversation.ConversationActivity --es wav /sdcard/Android/data/app.plamotranslate/files/asr-test/fleurs-jako-quick-1.wav --es partner ko
# 流し終わったら（音声の長さ＋40秒ほど）
adb logcat -d -s PlamoTranslate:V > <ログ>.txt
python tools/score-conv.py tools/testdata/conversation/fleurs-jako-quick-1.truth.txt <ログ>.txt
python tools/score-speaker.py tools/testdata/conversation/fleurs-jako-quick-1.reference.tsv <ログ>.txt
```

- FLEURS の文は前後に無音（前に平均1.5秒、後ろに平均2秒）を含む。道具はこれを落としてから並べる。落とさないと交代の間が3.5秒ほどに延び、素早い交代を試せない。
- 重ねた交代では、前の人は文を言い切っている（正解の文は全文のまま）。前の人の文を途中で切る会話は、正解の文をどこまでにするかを決められないので作らない。
- 端末で実時間で流すので、同じ音声でも結果が揺れる（カード1枚、切れ目1〜2か所ほど）。変更の前後は、同じ音声を同じ端末で流して比べる。
- 端末の画面が消えたりアプリが裏に回ったりすると、流すのが止まる。流す間は `adb shell svc power stayon usb` で画面を点けたままにする。

## 配布用のAPK

正式版は配布用の鍵で署名し、GitHubのリリースにAPKを1つ置いて配る（`docs/判断/2026-11-08_署名したAPKをGitHubのリリースで配る.md`）。正式版には `app/src/debug/` の入口（`BenchActivity`、`TranslateBenchActivity`、`AsrBenchActivity`、会話翻訳に音声ファイルを流す入口）と、デバッグのブロードキャストが入らない。

### 署名鍵を用意する

1. 鍵（`.jks`）と、`storeFile`・`storePassword`・`keyAlias`・`keyPassword` を書いた `keystore.properties` を、リポジトリの外の安全な場所に置く。`storeFile` が相対パスなら、`keystore.properties` のフォルダーから探す。
2. 各PCの `local.properties` に `plamo.keystore=<そのフォルダー>/keystore.properties` を1行書く（区切りは `/`。日本語のパスならUTF-8で保存する）。`app/build.gradle.kts` がこれを読む。無ければ署名せず、`app-release-unsigned.apk` になる（端末に入らない）。
3. 鍵のフォルダーは別の場所にも保存しておく。鍵を失うと、使う人はアプリを消して入れ直すしかなく、モデルも消える。

### リリースを作る

1. 前の版のタグからの差分を、`design-reviewer` エージェントで点検する（`change-flow` スキル「リリースの前」）。直すべき構造の崩れは、この版で直すか `docs/バックログ.md` の「構造の既知の問題」に理由と一緒に置く。
2. 依存やモデルを変えたなら、「ライセンス文を集め直す」を行う。`app/build.gradle.kts` の `versionCode` を1つ上げ、`versionName` を変える。`versionCode` が上がっていないと、配った端末で上書きできない。
3. 正式版を作り、版番号を付けて `dist/`（Gitの対象外）に取っておく。

   ```powershell
   $env:PYTHONUTF8="1"
   .\gradlew.bat :app:assembleRelease
   New-Item -ItemType Directory -Force dist | Out-Null
   Copy-Item app/build/outputs/apk/release/app-release.apk dist/PlamoTranslate-<versionName>.apk
   ```

   公開する前にこの正式版を端末に入れて確かめ、その後に中身を変えたら、2に戻って版を上げてから作り直す。同じ `versionCode` で中身の違う版を公開すると、先に入れた端末はそれを新しい版として受け取れない（`docs/判断/2026-11-12_0.6.0を欠番にしv0.6.1として出す.md`）。
4. `main` と、タグ `v<versionName>` をプッシュする。正式版のタグは数字と `.` だけにする。ベータは `v<版>-beta.<番号>`（`versionName` も同じ）にし、開発のブランチとタグをプッシュする（「ベータを出す」）。

   ```powershell
   git tag v<versionName>
   git push origin main v<versionName>
   ```

5. GitHubのリリースを作り、APKを1つだけ添付して公開する。題名は「Mockingword <versionName>」。本文は利用者向けに「増えたこと」「変わったこと」「入れ方」「注意」の節で書き、前の版のリリースを手本にする。完了した作業の一覧の正本はこの本文なので、利用者に見える変化は漏らさず書く。「注意」にはPLaMo Community Licenseの条文のリンク（https://plamo.preferredai.jp/info/plamo-community-license-ja ）を添える。
   - GitHub CLIがあれば、次で作成・添付・公開まで行える。

     ```powershell
     gh release create v<versionName> dist/PlamoTranslate-<versionName>.apk --title "Mockingword <versionName>" --notes-file <本文のファイル> --verify-tag
     ```

   - GitHub CLIが無い場合は、GitHubの画面または認証済みのREST APIでリリースを作り、APKを添付する。認証情報をファイルやログへ書かない。
6. 公開した後、最新のリリースのタグと、APKの `digest`（`sha256:` の後ろ）が、手元のAPKのSHA-256と一致することを確かめる。

   ```powershell
   $r = gh api repos/kagerouttepaso/PlamoTranslate/releases/latest | ConvertFrom-Json   # gh が無ければ Invoke-RestMethod で同じURLを読む
   $r.tag_name; $r.assets | Select-Object name, digest
   (Get-FileHash dist/PlamoTranslate-<versionName>.apk -Algorithm SHA256).Hash.ToLower()
   ```

7. `docs-update` スキルの手順で、`docs/現在地.md` の状態を公開した後のものに書き換える。

### ベータを出す

開発のブランチの途中の版を、正式版の前に実機で試して測るために配る。手順は「リリースを作る」と同じで、次だけが違う。

- 版は次の正式版の数字に `-beta.<番号>` を付ける（例：`0.11.0-beta.1`）。`versionCode` は正式版と同じく1つずつ上げる。
- タグは開発のブランチのコミットに付け、`main` ではなく開発のブランチとタグをプッシュする。
- `gh release create` に `--prerelease` を付ける。`releases/latest` は pre-release を返さないので、「正式版のみ」の端末には届かない。
- 公開した後の照合は、`releases/latest` ではなく `gh api repos/kagerouttepaso/PlamoTranslate/releases/tags/v<versionName>` を読む。

開発版が入っている端末には、正式版を上書きできない（鍵が違う）。入れるにはアプリを消す必要があり、モデルも消えるので、作者に確認してから行う。

### ライセンス文を集め直す

アプリに同梱するライセンス文は `app/src/main/assets/licenses/` にある（`docs/設計/アーキテクチャ.md`「採用している技術」の「ライセンスの表示」）。依存の版を変えたら、リリースの前に次を行う。

1. `python tools/collect-licenses.py` を流す。正式版に入る Maven の依存の一覧（`maven.txt`）、Google のライブラリが同梱する第三者のライセンス文（`google-third-party.txt`）、ONNX Runtime の第三者の告知（`onnxruntime-third-party-notices.txt`）を作り直す。POM にライセンスの記載が無い依存が増えると止まるので、確かめて道具の `KNOWN` に足す。
2. 手で書く `native.txt` を、変えた版に合わせる。llama.cpp・KleidiAI・ONNX Runtime・sherpa-onnx（静的に組み込まれた第三者のコードの版は、sherpa-onnx の `cmake/*.cmake` で分かる）・libc++・OpenCL-Headers・libyuv の節である。sherpa-onnx を1.x系に戻すと、GPL-3.0 の espeak-ng が入るので戻さない。
3. モデルを足したり変えたりしたら、`AboutApp.kt` の一覧（名前・作者・ライセンス名・配布元）を直す。

### 配った端末に入れる手順

リリースのノートに書く、使う人の手順である。

1. リリースのページからAPKを端末に取って開き、「提供元不明のアプリのインストール」を許可して入れる。
2. アプリを開き、「モデルの準備」の画面で「ダウンロード」を押す（大きさは画面に出る。Wi-Fiで取る）。翻訳モデルはPLaMo Community Licenseのもとで使う（画面の「ライセンスを読む」）。
3. 新しい版は、設定の画面の「このアプリについて」の「更新を確認」で入れる。

### アプリの更新

使う人は、設定の画面の「このアプリについて」で「更新を確認」を押し、新しい版があれば「ダウンロードして更新」を押して、Androidのインストールの確認に答える。アプリはそのときだけGitHubの `releases/latest`（「ベータも受け取る」なら `releases` の一覧）から新しい版を取る（`app/src/main/java/app/plamotranslate/update/AppUpdater.kt`）。上の「リリースを作る」の決まり（タグの形、`versionCode` を上げる、APKを1つだけ添付する）は、この仕組みが入れ替える前に確かめることから来ている。開発版が入っている端末では、鍵が違うので更新は止まる。正式版の鍵で署名した端末（versionCode 14）から0.8.0へ、この仕組みで上げられることを確かめてある。

## 端末の片付け

作業の区切りで、試作の残りを消し、最新のアプリとモデルだけを残す。

| 場所 | 扱い |
| --- | --- |
| `/data/local/tmp/plamo/`、`/data/local/tmp/llama.cpp/cl-cache/` | CLIの計測で送ったCLI・モデルと、GPUのCLIが作るカーネルのキャッシュ。消す |
| `/sdcard/Android/data/app.plamotranslate/files/bench/` | 画面翻訳の評価の画像と結果（`run-bench.ps1` が毎回作り直す）と、音声認識モデルの比べの音声と結果（`bench/asr/`・`bench/asr-result.tsv`）。消す |
| `/sdcard/Android/data/app.plamotranslate/files/*.tsv` | 翻訳モデルの比べに送った文の組と結果。消す |
| `/sdcard/Android/data/app.plamotranslate/files/asr-test/` | 会話翻訳の動作確認の試験音声。消す |
| `/sdcard/Android/data/app.plamotranslate/files/asr-rec/` | 「詳しい記録を残す」で会話翻訳が書いた会話の録音（会話の中身）。PCに取り出したものも含めて消す |
| `/sdcard/Android/data/app.plamotranslate.featurelab/files/lab/` | 機能テストのウィンドウの撮影と画面共有の撮影で保存した画像（作者の画面の中身）。消す |
| `/sdcard/Android/data/app.plamotranslate/files/models/` | 翻訳・音声認識・漫画用OCR・読み上げのモデル。残す |
| アプリの `cache/cl-cache/` | GPUカーネルのコンパイル結果。残す（消すと次の起動が遅くなる） |
| 機能テスト用のアプリ（`app.plamotranslate.featurelab`） | ユーザー補助の「機能テスト（イベントの計測）」をオフにする。アプリを消すかは作者に確認する |
| `log.tag.FeatureLab` | 機能テストのログを出すために開けたもの。`adb shell setprop log.tag.FeatureLab '""'` で戻す（端末の再起動でも戻る） |
| アプリ本体 | `.\gradlew.bat :app:installDebug` で最新を上書きする。`adb uninstall` はモデルを含むデータも消すので、作者に確認する |
