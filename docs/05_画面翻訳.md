# 画面翻訳

更新日：2026-11-12

## 方針

画面共有を開始しておき、浮遊ボタンを押したときだけ1枚撮影する。撮影した画像の文字を読み、吹き出し・段落のまとまりごとに日本語へ訳して、元の位置へ重ねる。一般のアプリ画面と漫画を同じ処理で扱う。縦書きを読める漫画用OCRとML Kitを併用し、行ごとに合う結果を選ぶためである（当初の「一般モード・漫画モード」の切り替えは作らなかった。経緯は「判断の記録」）。

1回の翻訳の流れ（`ScreenTranslateService.translateScreen`）：

1. 浮遊ボタンと前の訳を隠し、50ms待って1枚撮る（`ScreenCapturer`）。撮る前に、撮影用の仮想ディスプレイの大きさを今の画面（向き）に合わせる（「画面の向きと大きさ」）。
2. 文字を読み、まとまりにする（`MultiScriptOcr`。「文字認識」）。
3. 訳す対象を選び、訳の枠の色を撮影画像から読み取る（`selectTargets`。「訳す対象と翻訳」）。ここで撮影画像を捨てる。
4. 空の訳の枠を先に並べ、まとめて訳しながら訳文を流し込む（`BatchTranslator`、`TranslationOverlay`）。

評価用の `BenchActivity` は、文字認識・訳す対象の選別・まとめ訳し（手順2〜4）を実機と同じ関数で行う。評価で測った結果が、実機の画面翻訳の結果と一致するようにするためである。描画だけは画像へ描く別の実装（`BenchActivity.render`）で、枠の広げ方・内側の余白・文字の大きさの範囲は実機と同じ値を使う。評価は画像ごとに訳の控えを作り直すので、控えの効果は測らない。

## 操作

| 操作 | 動き |
| --- | --- |
| 開始 | トップ画面の「画面翻訳」のタイル、アイコンの長押しメニューの「画面翻訳」、クイック設定の「画面翻訳」タイル。どれも `MainActivity` を通して、毎回、画面共有の許可を得る（Android 14以降は許可を使い回せない）。動作中はタイルの色が変わる |
| 浮遊ボタンのタップ | 訳の表示を一括でオン・オフする。タップで訳すときは、訳を出していれば消し、出していなければ画面を撮って訳す。自動で訳すときは、自動の見張りを止める（ボタンが薄くなる）か再開する |
| 浮遊ボタンの長押し | メニュー：原文の言語（自動・中国語・韓国語・英語）、認識モード（通常・動く画面）、翻訳モデル（0.8B・2B）、画面翻訳を終了。言語と認識モードは次に始めたときも引き継ぐ。翻訳モデルはアプリ全体で1つなので、ここで変えると他の画面のモデルも変わる（端末に無いモデルは選べない）。ボタンの字は自動なら「訳」、言語を決めたら「訳／中」のようにする。メニューを開くときは訳を消し、訳している途中なら取り消す（2026-11-12、作者の指摘「訳の枠がメニューの上に来て触れなくなる」。ユーザー補助の重ね表示はメニューより手前に出る。途中を取り消さないと、訳し終わった枠がメニューの上に出る）。自動で訳すときは、メニューを閉じた後に画面が止まっていれば訳し直す |
| 浮遊ボタンのドラッグ | ボタンを動かす |
| 訳の枠に触れる | 何もしない。操作は奥のアプリへ届く（訳の上をスワイプしてスクロールできる） |
| 上部の小さな表示のタップ | 重ね表示を消す |
| 画面のどこかに触れる | タップで訳すときは重ね表示を消す（スクロールで画面が変わるため）。自動で訳すときは消さず、画面が変わったら消す |
| 終了 | 長押しのメニュー、通知の「終了」、トップ画面のタイル、クイック設定のタイル |

## 画面の撮影

| 項目 | 内容 |
| --- | --- |
| サービス | `foregroundServiceType="mediaProjection"`。サービスをフォアグラウンドに上げてから `getMediaProjection` を呼ぶ |
| コールバック | `createVirtualDisplay` の前に `MediaProjection.Callback` を登録する（Android 14以降の必須条件） |
| 取得 | `ImageReader`（RGBA_8888）を常駐させ、ボタンを押したら、隠した後に描かれたフレームを1枚取る |
| 写らない画面 | `FLAG_SECURE` のアプリは黒く写り、訳す文字が見つからない |

## 文字認識

`core-ocr` の `MultiScriptOcr` が複数の認識器を並列に動かし、`BlockMerger` が結果をまとめる。返すのは、まとまりごとの文字・位置・文字種・縦書きか（`OcrBlock`）。カメラ翻訳は同じ `MultiScriptOcr` を、まとまりにせず1行ずつ返す設定（`groupLines = false`）と漫画用OCRなしで使う（`docs/10_カメラ翻訳.md`）。

### 使う認識器

| 認識器 | 読めるもの | 役割 |
| --- | --- | --- |
| 漫画用OCR（PP-OCRv6 manga、`MangaOcr`） | 中国語・日本語。縦書きも読める | 中国語・日本語の行は原則これを採る。確信度0.8未満で、ML Kit韓国語がハングルを読めた範囲だけは韓国語に譲る |
| ML Kit 中国語 | 簡体字・繁体字、ラテン文字 | 横書きの中国語。漫画用OCRが無いときは、1文字ずつの位置から縦書きの列を組み直す（`VerticalColumns`） |
| ML Kit 韓国語 | ハングル、ラテン文字 | 韓国語（漫画用OCRは韓国語を読めない） |
| ML Kit 日本語 | 仮名・漢字、ラテン文字 | 日本語の行を見分け、訳さないために使う |
| ML Kit 英字 | ラテン文字だけ | 英語。手書き風の大文字の写植を、他の認識器より正しく読む |

漫画用OCRのモデルは端末の `files/models/ocr/manga/`（`det.onnx`・`rec.onnx`・`dict.txt`）に置く。無ければML Kitだけで動く。漫画用OCRの前処理と復号はモデルカードに合わせ、検出の後処理（しきい値・画素のまとまり・枠の広げ）はOpenCVを使わずKotlinで書いた（APKを大きくしないため）。縦長の行は90度回して横書きとして読む。

### 原文の言語の指定

言語を決めると要らない認識器を動かさず、翻訳でもPLaMoに原文の言語を伝える（`Recognizers`）。自動ではPLaMoが原文から言語を判定する。

| 指定 | 動かす認識器 | 文字認識の時間（1ページ） |
| --- | --- | --- |
| 自動（既定） | すべて | 漫画0.5〜1.0秒、文字の多い画面1.7〜3.1秒 |
| 中国語 | 漫画用OCR＋ML Kit中国語 | 自動とほぼ同じ（漫画用OCRが時間の大半） |
| 韓国語 | ML Kit韓国語だけ | 0.12〜0.19秒。韓国語の漫画1ページの合計は4.0秒→2.0秒（文字認識の短縮は約0.5秒で、残りは翻訳側の差。原因は確かめていない） |
| 英語 | ML Kit英字だけ | 0.13〜0.24秒 |

中国語を指定すると、PLaMoには簡体字（`zh-hans`）として伝える。繁体字の原文は、自動のままのほうが無難である（繁体字の指定は作っていない）。

言語を足すときは、`OcrLanguage`（`core-ocr`）、`Recognizers`、`ScreenLanguage.kt` の表（メニュー名・ボタンの字・PLaMoへ渡す言語）をそろえる。

### 行の選び方とまとめ方（`BlockMerger`）

段落ごとに認識器を選ぶと、日本語の解説に韓国語の引用が混ざった段落で片方の言語が崩れたため（2026-11-05）、行ごとに選んでから、まとまりを組み直す。

1. **縦書きの行を決める**：漫画用OCRの行を採る。採った範囲に重なるML Kitの行（縦書きを横に読み違えた行）は捨てる。韓国語の範囲は残す（確信度が低く、ML Kit韓国語がハングルを2字以上崩れずに読めた範囲）。
2. **行ごとに1つ選ぶ**：位置が重なる行（IoU 0.4以上）を突き合わせ、各認識器が自分の文字をいくつ読めたかで行の言語を決める。

   | 条件 | 採る結果 |
   | --- | --- |
   | 漢字・仮名・ハングルが無い（英語） | ML Kit英字。無ければ、崩れておらずラテン文字を最も多く読めたもの |
   | 仮名が2字以上で、ハングル以上 | 日本語 |
   | ハングルが漢字より多い | 韓国語 |
   | 漢字がある | 中国語 |
   | どれも崩れている（`TextQuality`） | 後段で訳さない |

3. **まとまりに束ねる**（`LineClusterer`）：横書きの行は上下に詰まった行（行間が行の高さの0.8倍未満）、縦書きの列は左右に詰まった列をつなぐ。範囲が2割以上重なる行は形に関係なくつなぐ（重なったまま別の枠に描くと読めない）。仮名を含む行とそれ以外の行はつながない。
4. **読み順に並べる**：縦書きは右の列から、横書きは上の行から。高さの半分以上重なる行は同じ段とみなして左から並べる。

### 縦書き

- 縦書きの判定：高さが幅の1.5倍以上の行。ただし英字だけの行は縦書きとして扱わない（狭い吹き出しで短い単語が縦長になるため）。
- 縦書きの約物は横書きの形に戻して訳へ渡す（`VerticalColumns.normalize`）。Unicodeの縦書き用表示形（U+FE10〜FE19、U+FE30〜FE4F）はNFKCで戻す（UCD 16.0で確認）。横書き用のOCRは縦の破折号「——」を「|」、縦の省略号「……」を「:」に読むので、1字分の高さがあるものだけ置き換える（中国語の縦書きで両者を字面中央に縦に置く規則は W3C clreq 5.1・5.4.1、GB/T 15834—2011）。

### 英語

漫画の写植は全部大文字のことが多い。大文字だけの文を渡すと、翻訳が固有名詞とみなして英語のまま残した（「FINE.」）。そのため `EnglishText` で次のように整えてから訳す。

- 英字の8割以上が大文字なら、文頭と単独の「I」だけ大文字の文に直す。
- 行末のハイフンで切れた語はつなぐ（「COM-」「PARED」→「COMPARED」）。敬称（「NATORI-CHAN」の「-CHAN」など）のハイフンは残す。

### 動く画面のモード

ゲームの画面では、台詞の枠や文字の奥でキャラクターや演出が動き、1枚で読むと読み違いや余計な文字が出る（2026-11-12、作者の要望「動くキャラクターに負けない文字認識」）。認識モードを「動く画面」にすると、約0.5秒の間に5枚（110msごと）撮り、画素ごとに色の中央値を取った1枚を読む（`ScreenCapturer.captureFrames`、`FrameStack`）。

- 止まっている文字は5枚とも同じ色なので残る。5枚中2枚までにしか写らない動きは消え、半透明の枠の奥で動くものは枠の色にならされる。
- 文字認識は重ねた1枚に1回だけかける。カメラ翻訳のようにコマごとに読んで多数決する方法は、自動の文字認識が1回0.5〜3秒かかるので画面翻訳では遅すぎ、採らなかった。
- 間隔の間に新しい画面が届かなければ（画面が止まっている）撮るのを打ち切る。止まった画面では通常のモードと同じ速さになる。
- 1字ずつ出る台詞や流れる字幕は、出きっていない字が中央値に残る。そうした画面は通常のモードで読む。
- 上部の小さな表示に「5枚重ね」と、撮る時間を含めた合計を出す。REDMAGICで、背景が動き続ける試験の画面（大きな図形と文字が動き、半透明の台詞の枠がある）の撮影と重ね合わせは0.67〜0.76秒、合計1.9〜2.2秒（2026-11-12）。枚数と間隔は、実際のゲームで試して合わなければ変える。

### 白縁の文字

ゲームの文字は白抜き・白縁取りが多い（2026-11-12、作者の要望「それで認識が弱くならないように」）。白縁の文字は字の中身と縁の色の差で読ませるので、明るさの画像では、字の中身が明るい色（黄色など）だと字の形が消える。REDMAGICの試験の画面（縞模様の背景に6種の縁取り）で、黄色い字に白縁の「LEVEL UP! Your attack power increased」を「EEL UR秒OuRateckipoeR」と読み、訳も崩れた。

動く画面のモードでは、元の画像に加えて、画素ごとにRGBの最小値を取った灰色の画像も読む（`OutlinedText`、`MultiScriptOcr.recognizeOutlined`）。白い縁は白（255）のまま、色の付いた字の中身はどの色でも暗くなり、白い紙に黒い字の形になる。暗い背景の上の色の字はかえって薄くなるので、最小値の画像だけにはしない。

- 2つの画像を1行ずつ読み、行ごとに点の高い方を採ってから、まとまりに束ねる（`BlockMerger.group`）。束ねた後で比べると、言語の違う行が一緒に束ねられて比べられなかった。
- 点は、行の文字種の字を1点とし、ほかの文字種の字を3点、崩れた文字列を10点、空白の抜けた16字以上のラテン文字の語を6点引く（`OutlinedText.score`）。元の読み取りを優先し、最小値の画像の方が4点以上高いときだけ置き換える。片方にしかない行は、崩れていなければ足す。
- 結果：「LEVEL UP!」の行は −53点→22点で置き換わり、「レベルアップ！攻撃威力が向上しました」と訳せた。文字認識は0.6秒→1.3秒（漫画モデルは最小値の画像には使わない）。
- 残り：黒い字に白縁の韓国語「오늘의 출석」は、最小値の画像が正しく読んだが、元の読み違い「와늘의출적」と同点で置き換わらなかった。字の形の確かさ（ML Kitの行の確信度）を点に入れれば選べる見込み。

## 自動で訳す

浮遊ボタンの長押しで「翻訳の始め方」を「自動（画面が止まったら訳す）」にすると、タップしなくても訳す（2026-11-12、作者の要望「漫画でページ送りしたら自動で反映、Discordで投稿をスクロールしたら訳が消え、スクロールが止まったら訳し始める」）。ボタンの字は「訳」から「自」に変わる。

- **見張り**（`ScreenTranslateService.watchScreen`）：200msごとに、新しく届いた画面を横48ます目の明るさの格子に縮めて（`ScreenCapturer.latestThumb`、`ScreenChange`）比べる。画像に変えずに受け取った画面から数万点を読むだけなので、文字認識より桁違いに軽い。新しい画面が届いていなければ、画面は変わっていない。
- **変わった**：訳したときの画面（自分の表示を隠して撮った1枚）から、ます目の6%以上が変われば（明るさの差16以上）、訳を消し、訳している途中なら取り消す。自分の訳の枠・上部の表示・浮遊ボタンの下のます目は比べない（自分の表示の変化を画面の変化と取り違えないため）。
- **止まった**：直前の画面からの変化が2%未満の状態が0.6秒続いたら、撮って訳す。点滅するカーソルや小さなアイコンの動きは止まったうちに数える。
- **触れたとき**：訳の枠の真下の変化（ゲームの台詞送り）は、枠の下を比べないので見張りでは見えない。そこで、画面のどこかに触れたら（上部の表示の `FLAG_WATCH_OUTSIDE_TOUCH` で知る）0.35秒待ち、訳の枠を一瞬隠して撮り、訳したときの画面と枠の範囲だけで比べる（`onOutsideTouch`）。ます目の15%以上が変わっていれば訳を消して待ちに戻し、変わっていなければ枠を戻す。動く背景のます目は外さない（半透明の台詞の枠は奥を図形が通ると動く背景とみなされ、外すと台詞の変化に気づけなかった）。誤って変わったとみても、控えがあるので訳し直しは速い。
- **動く画面のモード**（ゲーム）では背景が動き続けるので、1回ごとの格子ではいつまでも「止まった」にならなかった（試験の画面で、しきい値を12%に緩めても20秒間訳さなかった）。そこで、直近5回（約1秒）の格子をます目ごとの中央値で1枚にしてから比べ（`ScreenChange.median`）、その間に明るさが動いたます目も比べる対象から外す（`ScreenChange.active`）。止まったは4%未満、待ちが3秒を超えたら止まるのを待たずに訳す。変わったは、大きなキャラクターが新しい場所へ動くだけで9〜27%になったので、35%以上（場面転換・ページ送り）にした。台詞の変化は「触れたとき」で拾う。
- **訳している途中の操作**：撮影・文字認識・翻訳の途中にほかのアプリの画面に触れたら、すべて取り消して訳を消す（2026-11-12、作者の要望「自動翻訳で訳している途中に画面を操作したら全処理をキャンセル」。タップで訳すときも同じ）。自動なら待ちへ戻り、画面が止まったら訳し直す。触れたことは、左上に置いた見えない1画素の窓（`TouchWatcher`、`FLAG_WATCH_OUTSIDE_TOUCH`）で知る。上部の小さな表示は撮影の間は消えているので、それでは撮影中の操作に気づけない。自分の浮遊ボタン・メニュー・上部の表示に触れたときも知らせが来るので、80ms待って、自分の窓が直前に触れられていれば除く（`OwnTouch`）。実機で、スクロールの0.9秒後（文字認識の途中）のタップで取り消され、約3秒後に訳し直した。浮遊ボタンのタップは取り違えなかった。
- **画面の切り替わり**：戻る・ホームのジェスチャーでは、訳している途中の処理が取り消されなかった（2026-11-12、作者の指摘）。ジェスチャーの帯は重ね表示より手前のシステムの窓で、Androidは「外側に触れた」知らせを触れた窓より手前の窓にしか送らないので、`TouchWatcher` に届かない。また動く画面のモードの見張りは、切り替わりの動きの最初のコマを動く背景として覚えて見逃した。そこで、中央値や動いたます目の除外を通さない1枚で、訳したときの画面からます目の半分以上（動く画面は6割以上）が変わったら、画面が切り替わったとしてすぐ全部取り消す（`switched`）。タップで訳すときも、訳している間だけ同じ見張りをする（`guardSwitch`）。ユーザー補助を有効にしていれば、その知らせでも取り消す（「透けない訳の枠」）。実機で、Discord風の画面を訳している最中のホームのジェスチャーで2回とも取り消し、止まったホーム画面を訳し直した。
- 自動のときは、訳を出し終えた後に触れただけでは訳を消さない（タップで訳すときは触れたら消す）。浮遊ボタンのタップで見張りを止め（ボタンが薄くなり、訳も消す）、もう一度で再開する。メニューを開いている間は訳さない（自動の翻訳がメニューを閉じ、選べなかった）。
- 実機（REDMAGIC、2026-11-12）：Discord風の試験の画面で、スクロールすると訳が消え、スクロール開始から約3.6秒で訳がそろった。止まった画面では訳し直しを繰り返さず、CPU使用率は0%。動く画面のモードで、背景が動き続ける画面で訳が出て、15〜20秒消えずに保たれ、台詞を送ると（枠の下の変化33〜38%）訳し直した。割合と時間は、実際のゲームや漫画で使って合わなければ変える。

## 画面の向きと大きさ

配る端末の画面の大きさ・向きは決め打ちせず、今の画面から求める（2026-11-09、作者の指示「人に配るようになったので、画面サイズなども固定値はやめる」）。

- **撮影**：撮影用の仮想ディスプレイは、画面翻訳を始めたときの画面の大きさで作る。Android 14以降は1つの許可で仮想ディスプレイを1回しか作れないので、画面を回したら作り直さずに大きさだけ変え（`VirtualDisplay.resize`）、受け取り口（`ImageReader`）を新しい大きさのものに差し替える。撮る前に今の画面の大きさ（`maximumWindowMetrics`）と比べて合わせ、合わせた後に届いた1枚を使う。以前は始めたときの大きさのままで、縦持ちで始めて横画面にすると、横長の画面が縦長の枠に約0.45倍に縮めて映り、訳の枠が違う場所に出た（作者の指摘「横画面になっているときレンダリングがバグる」）。
- **訳の枠**：撮った画像の座標をそのまま画面の座標として置く（切り欠きやバーの分を避けない窓の設定）。画面を回したら、前の向きで置いた訳の枠は位置が合わなくなるので消し、訳している途中なら取り消す。
- **浮遊ボタン**：画面を回したら、今の画面の同じ割合の位置へ移す（右端にあれば右端のまま）。ドラッグでは画面の外へ出さない。
- **状態バー**：高さを撮るたびに今の画面から読む（`WindowInsets` の状態バー）。以前はシステムの縦持ちの既定値を固定で使い、全画面のアプリで状態バーが隠れていると、画面の一番上の文字を訳さなかった。

## 訳す対象と翻訳

`selectTargets`（`overlay/TranslationTargets.kt`）が、まとまりから訳す対象を選ぶ。訳す先は呼ぶ側が渡す（画面翻訳は日本語の `SCREEN_TARGET`）。

- 状態バー（時刻・通信速度など）にかかるまとまりは訳さない。状態バーの高さは撮るたびに今の画面から読む（全画面のアプリで状態バーが隠れていれば0）。
- 訳先が日本語なので、仮名を含むまとまり（日本語）、数字・記号だけのまとまり、崩れたまとまりは訳さない。欧文は1文字だけなら飛ばすが、漢字・ハングルは1文字でも訳す（漫画の「咦」「嘟」）。
- 行の折り返しをつなぐ。韓国語・欧文は空白で、日本語・中国語は詰めてつなぐ。英文は上の `EnglishText` で整える。

`BatchTranslator` は、まとまりを読み順に最大8行・400文字ずつ改行でつないで1回で訳し、訳文を改行で分けて各まとまりへ戻す。1まとまりずつ訳すと、毎回プロンプト処理の固定費がかかり1画面で20秒を超えたため（2026-11-05）。行数が合わないときは、そのまとまりだけ1つずつ訳し直す。2026-11-12から、設定の「同時に訳す数」（既定4）の流れで同時に訳し、訳し終わった流れにはすぐ次のまとまりを入れる。このときは行をつながず、1片を1回で訳すので、行数のずれによる訳し直しは起きない。長いブロックは文の切れ目で約150字ずつの片に分けて、ほかの流れでも訳す。Discordのボットの長文のような長い片が1本の流れを使っている間も、短い投稿の訳がほかの流れで進む（`docs/03_翻訳コア.md`「複数の文を同時に訳す」）。

2026-11-12に、Chrome拡張（PLaMo翻訳、`dotfiles/brave/plamo-translate`）で足された対策を持ち込んだ（作者の採用。`TranslationChecks`）。

- 行数が合っても、原文のまま写した行・日本語の字が1つも無い行は、その行だけ訳し直す。言語の混ざったまとまりで、0.8Bが2言語目以降を写すため。3語以下・24字以下の英字は原文のままでよいので除く。
- 同じ並びを3回繰り返して止まらなくなった生成は、訳文が原文の1.2倍＋16字を超えたら打ち切る。
- 同じ原文は1回だけ訳し、同じ文のまとまりすべてに配る。
- 1200字を超えるまとまりは文の切れ目で分けて訳し、つなぐ。
- 控え（メモリ・データベース）の当たり方と、訳し直し・打ち切りの数をログ（「まとめ訳し:」）に出す。

同じ原文の訳は500件まで控え、撮り直したときに使い回す。原文の言語を変えたときと、翻訳モデルを切り替えてエンジンが変わったときは作り直す（`BatchTranslator.reuseOrCreate`。2026-11-06、エンジンを見ずに使い回して、閉じたエンジンで訳し続けて失敗した）。`selectTargets` と `BatchTranslator` はカメラ翻訳も使う（`docs/10_カメラ翻訳.md`）ので、変えるときはカメラ翻訳への影響も見る。

### 訳の控え

画面翻訳の訳は、メモリの控え（500件）に加えて端末のデータベース（SQLite、`TranslationCache`）にも残し、画面翻訳を終えても、アプリを起動し直しても使う（2026-11-12、作者の要望「拡張機能と同じように、データベースに保存して次回起動時にも活かす。設定から削除もできるように」）。

- 鍵は、原文の言語（自動は `auto`）・訳す先・背景（context）・原文。翻訳モデルは鍵に入れず、訳の確かさの順位（0.8B＜2B、`TranslationModel.cacheRank`）を列に持つ（2026-11-12、作者の指示）。
  - 引くときは、自分以上のモデルの訳だけを使う。2Bは0.8Bの訳を当てにせず訳し直し、0.8Bは2Bの訳があればそのまま使う。
  - 書くときは、自分より確かなモデルの訳があれば書かない。2Bで訳すたびに0.8Bの訳を上書きしていく。同じ原文に残る訳は1つ。
- 訳す前に、メモリに無い原文をデータベースからまとめて引く。訳し終えた文は、まとめ訳しのまとまりごとに1つのトランザクションで書く。空の訳は控えない。
- 2万件を超えたら、最後に使った時刻の古いものから消して1万8千件にする。2万件はChrome拡張と同じ値。1件は原文・訳・鍵と索引で数百バイトなので約5〜10MBで、引くのは主キーの索引なので件数が増えても1回の画面翻訳の読み書きは数ミリ秒で済む。画面翻訳は1回に約20件なので、新しい文ばかりでも約1000回分を覚えていられる。
- 設定の画面の「画面翻訳の訳の控え」に件数を出し、確かめてから全部消せる。消したら、動いている画面翻訳のメモリの控えも次の翻訳で捨てる（消した回数 `generation` を見る）。
- カメラ翻訳と評価（`BenchActivity`）はデータベースを使わない。カメラは読み揺れで似た文が大量にでき、評価は控えの効果を測らないため。
- 原文のまま返った訳はデータベースに残さない（メモリには残す）。2Bが「Sounds good」を訳さずに返し、それが2Bの訳として控えられて、0.8Bでも原文のまま出続けた（2026-11-12）。
- 実機（REDMAGIC、2026-11-12）：Discord風の画面で、1回目は2.2秒かかった翻訳が、アプリを止めて起動し直した後は15片すべてデータベースから出て0.05秒。2Bに切り替えると0.8Bの控えを使わずに全14片を訳し、0.8Bに戻すと2Bの訳13片を使った。設定の画面で件数（48件）と削除（0件になる）を確かめた。
- 同じ考え方のChrome拡張（PLaMo翻訳）は、IndexedDBに2万件、0.3秒ためてまとめて書く。

## 訳文の重ね表示

| 項目 | 内容 |
| --- | --- |
| 権限 | `SYSTEM_ALERT_WINDOW`（設定画面で作者が許可する） |
| 窓 | `TYPE_APPLICATION_OVERLAY` の小さな窓を、訳1つにつき1つ置く（全画面の窓だと下のアプリを操作できない）。撮影画像と同じ座標に置くため `fitInsetsTypes = 0`・切り欠き領域も使う設定にする |
| 触れたとき | 訳の枠の窓は `FLAG_NOT_TOUCHABLE` で、触れた操作は奥のアプリへ届く（2026-11-12、作者の指摘「枠を1つずつタップで消すより、字幕の上をスワイプして奥の投稿をスクロールできる方がよい」。それまでの、タップで半透明にする機能はやめた）。Android 12以降は、ほかのアプリの重ね表示を通り抜ける操作は、窓の不透明度がシステムの上限（`InputManager.maximumObscuringOpacityForTouch`、既定0.8）を超えると捨てられる。そのため枠の窓の不透明度を上限に合わせ、原文がわずかに透ける。設定の画面で「訳の枠を透かさない」をオンにし、ユーザー補助を有効にすると透けなくなる（「透けない訳の枠」） |
| 枠の大きさ | 認識した枠を左右4dp・上下2dp広げ、原文の端を隠す（`OverlayStyle.padded`） |
| 色 | 背景色と文字色を元の画面にそろえる（`ColorSampler`）。背景は枠を少し広げた外周の最頻色、文字は枠の中で背景から十分に離れた画素の中央値。読みやすさのために文字色を直す（`ColorSampler.readable`、2026-11-12、作者の指摘「漫画の白背景の小さな黒い文字の訳が読みにくい。特に文字色が灰色っぽいとき」）：彩度0.25未満の灰色っぽい文字は背景に合わせて黒か白にし、色の付いた文字は色味を残してコントラスト比7（WCAGのAAA）まで黒か白へ寄せる。以前はコントラスト比3未満だけ直していて、小さい文字の縁のぼけた画素から灰色が選ばれ、透けた元の文字と同じ濃さになっていた。背景は不透明に塗るが、窓ごと上の上限（0.8）まで透ける |
| 文字の形 | 太字にし、背景色でぼかした縁取り（影、半径2.5dp）を付ける（`OverlayStyle.applyHalo`、2026-11-12）。透けた元の文字の線と訳の線を見分けやすくする。実機の横書き・縦書きと評価の描画（`BenchActivity`）で同じ値を使う |
| 吹き出しまで広げる | 浮遊ボタンの長押しの「訳の枠」で「吹き出しいっぱいに広げる」を選ぶと、訳の枠を文字を囲む吹き出しの内側まで広げる（`BubbleFit`、2026-11-12、作者の採用）。文字の周りの背景色の範囲を格子の上で塗りつぶし、探す窓（元の枠の長い辺の0.8倍まわり）の端や画面の外に届いたら「開いている」として広げない。DiscordやゲームのUIのように背景色が一面に続く画面では広がらない。閉じていて元の枠の6倍以内なら、その範囲に収まる長方形（四辺のます目がすべて内側になるまで縮める）を枠にする。楕円の吹き出しで、外接する長方形まで広げると四隅が線の外へはみ出し、訳の字が線にかかった。広げた枠がほかの文字（訳さない日本語も含む）にかかるなら広げない。広げた枠は余白を足さず、横書きは真ん中に寄せる |
| 横書き | 独自View（`HorizontalTextView`）で、枠に収まる最大の大きさ（7〜22sp、1sp刻み）を二分探索で選び、上下の真ん中に描く（`Yokogaki`）。訳が流し込まれて文字が増えるたびと、枠の大きさが変わるたびに選び直す。評価の描画（`BenchActivity`）も同じ `Yokogaki` を使う。2026-11-12に `TextView` の自動縮小から替えた（作者の指摘「2行分の高さがないのに2行になって見切れる」「長文を訳している間、大きい文字で見切れたままがしばらく続く」）。`TextView` の自動縮小は、大きさの決まった窓では `append()` で文字が増えても大きさを計算し直さない。そのため、流し込みの最初の短い訳で決めた大きな文字のまま、増えた分が枠からはみ出していた |
| 透けない訳の枠 | 設定の画面の「訳の枠を透かさない」をオンにし、ユーザー補助の「PLaMo翻訳（画面翻訳の訳の枠）」を有効にすると、訳の枠をユーザー補助の重ね表示（`TYPE_ACCESSIBILITY_OVERLAY`）で置く（`OverlayAccessibilityService`、2026-11-12、作者の採用）。この窓は通り抜けの不透明度の制限を受けないので、不透明のまま触れた操作を下のアプリへ通せる。窓はユーザー補助のサービスの `WindowManager` からしか置けないので、枠の View もそのサービスを Context にして作る。サービスは、ほかのアプリの画面の切り替わり（`TYPE_WINDOW_STATE_CHANGED`）も受け、訳している途中か訳を出していれば取り消す。画面の文字は読み取らない（`canRetrieveWindowContent="false"`）。オンでもユーザー補助が有効でなければ、今までどおり不透明度0.8で置く。使う人は最初に1回、アプリ情報の︙から「制限付き設定を許可」（Android 13以降、ストア以外から入れたアプリ）、ユーザー補助の設定でオン、「デバイスのフル コントロール」の確認で許可、の3つを行う（設定の画面に手順とボタンを出す）。端末によっては強制終了や電池の最適化でオフに戻ることがある。実機（REDMAGIC、2026-11-12）で、作者がユーザー補助を有効にした後、Discord風の画面で元の文字が透けなくなり、訳の枠の上のスワイプで下のページがスクロールし、止まった後に訳し直した |
| 縦書き | 縦書きの原文には縦書きで描く（`Tategaki`）。右の列から左へ、句読点は右上に寄せ、長音・ダッシュ・波線・三点リーダーは90度回し、括弧は縦書き用の字形にする（W3C JLReqの縦組みに合わせた）。文字の大きさは横書きと同じ範囲 |
| 表示の順序 | 空の枠を先に並べ、訳し終わった部分から流し込む |

## 評価

### 方法

作者のスクリーンショットを `tools/testdata/ocr/<画面集>/` に置き、デバッグビルドの `BenchActivity` で画面翻訳と同じ処理をかける。漫画など著作物を含むため、画像と結果はGitに入れない（`.gitignore`）。`tools/run-bench.ps1` が、端末への転送・実行・取り出し・採点までを行う。

```powershell
./tools/run-bench.ps1 -Set 2026-11-05 -Label <名前>                 # 自動
./tools/run-bench.ps1 -Set 2026-11-05-en -Label <名前> -Lang ENGLISH  # 言語を指定
```

結果は `tools/testdata/ocr/<画面集>-out/<名前>/` に、画像ごとの所要時間と訳（`results.jsonl`）と、訳を元の位置に描いた画像（PNG、半分の大きさ）として残る。正解（`truth.json`：吹き出しの位置と原文）がある画像は、`tools/eval-screen.py` が次の観点で採点する（作者の希望、2026-11-05）。

| 観点 | 数え方 |
| --- | --- |
| 認識率 | 正解の吹き出しのうち、訳が1つ以上入った割合（セリフを全部認識できたか） |
| 一まとまり率 | 正解の吹き出しのうち、訳がちょうど1つ入った割合（吹き出しを1まとまりで訳せたか） |
| 欠け | 最小の文字（7sp）でも枠に収まらなかった訳の数と、9sp未満の訳の数（重ねた訳に欠けがないか） |
| 文字の正解率 | 正解の原文と読み取った原文の一致の割合（正解に原文があるページだけ） |

漫画用OCRなどの候補をPCで比べるときは `tools/ocr-spike.py`、合成した英語の画面と正解を作るときは `tools/make-en-screen.ps1` を使う（`docs/06_開発環境.md`「画面翻訳の評価」）。

## 残る問題

- 訳の枠は触れた操作を通すために不透明度0.8にしているので、下の原文がうっすら透ける（特に白い字の上）。設定の「訳の枠を透かさない」とユーザー補助で消せるが、使う人ごとに設定の手間がかかる。
- 言語の違う隣の行（中国語の行と韓国語の行、英語の行と韓国語の行）が1つのまとまりに束ねられ、まとめて訳される（2026-11-12の縁取りの試験の画面）。束ね方（`LineClusterer`）は仮名の有無だけで分けている。変えるなら評価（画面集）で前後を比べる。
- 白縁の文字で、最小値の画像の方が正しくても点が同じだと置き換わらない（「白縁の文字」）。

- 評価画像30枚のうち7枚目（上の表で正解率がいちばん低い1枚）に残る読み違い：スマホ画面内の小さな横書き（「事情结束了？我在楼梯口等你呢」が「肉技口你呪」）。縦の長音「—」、「嘟」の片方の読み落とし。
- 英語の漫画は、作者の実機での確認がまだ。正解も無く、点数で追えていない。
- 英語の漫画を自動判定で読むと、ローマ字の名前の一部を韓国語の認識器がハングルとして拾うことがある（「SHOUTAROU」→「SHO니TARO니」）。英語を指定すると正しく読める。
- 翻訳が、まれに訳文へ別の文字種を混ぜる（「SASA-SHOUTAROU-KUN」→「笹เจ้า太郎くん」。タイ文字が混じった）。原文は正しく読めているので、翻訳側の問題。
